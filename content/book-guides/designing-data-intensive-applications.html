  2. Mark each file as system of record or derived data in a comment at the top of formulaite_tools.py.
  3. Delete the supplier-page cache and rerun; confirm the drawer comes out the same.

Steps for rung 2: Safe concurrent drawer writes in Firestore

  1. Give every research run a request_id in agent.py and log it in the first Glass Box event.
  2. Store each drawer with a version number and write only if the stored version is unchanged.
  3. Start two agents on Glycerin at once and watch one of them re-read and retry.
  4. After each write, read the drawer back from the same client and assert the version matches.
  5. Choose a partition key for per-user data and write down why it is not the INCI name.

Steps for rung 3: Derived views and audits from a Glass Box change log

  1. Write every Glass Box event to an append-only log with a per-run sequence number.
  2. Build one consumer that derives the drawer view and one that fills the memory store from the log.
  3. Deliver the same event twice and inject a supplier timeout; confirm both consumers stay correct.
  4. Add a nightly batch that rebuilds ingredient embeddings from the log into a new versioned folder.
  5. Add an audit job that recomputes each drawer from its trace and alerts on any difference.

01Trade-offs, not answers ch 1

No database or architecture is best for everything. Each choice buys one property and pays for it with another. The book teaches you which questions to ask, not which product to pick. Write the trade-off down before you decide.

Picture it: Choosing a preservative: broad protection costs skin tolerance, mildness costs shelf life. There is no free option, only a fit for this product.
The trap: Copying a big company's architecture because it is famous, not because your load and your team match theirs.
In Formulaite: models.py keeps ScriptedModel and ClaudeModel behind one interface so the offline-versus-online trade-off is a flag, not a rewrite.
02System of record versus derived data ch 1

A system of record holds the one true copy of a fact. Derived data is anything computed from it: caches, indexes, summaries, trained models. If derived data is lost you rebuild it from the source. Knowing which is which makes a messy architecture readable.

Picture it: Your master formula sheet is the record. The printed batch card on the bench is derived; if it gets wet you print another one.
def get_page(url):
    if url in cache:                 # derived: safe to lose
        return cache[url]
    text = fetch(url)
    cache[url] = text                # rebuildable from the source
    return text
The cache is never the truth; a miss just falls back to the source.
The trap: Editing a derived copy by hand, so the record and the copy quietly disagree forever.
In Formulaite: formulaite_tools.py treats catalogue.json as the system of record and the supplier-page files as a derived cache.
03Percentiles and tail latency ch 2

Response time is a spread of values, not one number. The median (p50) tells you the typical wait. The p95 and p99 tell you how bad the slow cases are. Slow cases matter because one slow call makes the whole request slow.

Picture it: Ten batches of the same cream: most set in 20 minutes, one takes an hour. The average hides the hour; the customer waiting for that batch does not.
import statistics
times = sorted(run_ms)                 # one number per research run
q = statistics.quantiles(times, n=100)  # 99 cut points
p50, p95, p99 = q[49], q[94], q[98]
print(f"p50={p50:.0f}ms p95={p95:.0f}ms p99={p99:.0f}ms")
Report three numbers, never just the mean; never average percentiles from different machines.
The trap: Averaging p99 values from several servers, which the book calls mathematically meaningless.
In Formulaite: glassbox.py events carry timestamps, so a run's p50 and p99 can be computed from the trace without new instrumentation.
04Fault versus failure ch 2

A fault is one part misbehaving: a disk, a machine, a supplier's website. A failure is the whole system no longer doing its job. Fault tolerance means faults happen without becoming failures. You choose which faults to tolerate, never all of them.

Picture it: One heating element in the kettle dies (fault). If the batch still reaches temperature on the other elements, no failure.
The trap: Treating every supplier timeout as a failed run instead of a fault the agent can route around.
In Formulaite: In agent.py a read_supplier_page error is a tool_result the model can work around; the run fails only if no drawer passes the gate.
05Retry storms and backoff ch 2

When a service slows down, clients time out and resend. The extra requests make it slower still. The book calls this a metastable failure: the system stays broken even after load drops. Exponential backoff with random jitter, circuit breakers and load shedding break the loop.

Picture it: Everyone in a queue phoning the same shop at once because nobody answered the first time. The line never clears.
import random, time
def fetch_with_backoff(url, attempts=4, base=0.5, cap=8.0):
    for n in range(attempts):
        try:
            return http_get(url, timeout=5)
        except TransientError:
            delay = min(cap, base * 2 ** n)
            time.sleep(random.uniform(0, delay))   # full jitter
    raise ToolError("supplier unreachable")
The wait doubles each time and is randomised, so a hundred agents do not retry in step.
The trap: Retrying immediately and unboundedly inside every layer, so one slow supplier becomes a hundred stuck agents.
In Formulaite: tools.py is the one place to wrap read_supplier_page with backoff and a circuit breaker for the whole lab.
06Operability, simplicity, evolvability ch 2

Most of the cost of software is maintenance, not building. The book names three goals: operability (easy to run and watch), simplicity (easy to understand, usually through good abstractions) and evolvability (easy to change). Evolvability mostly means avoiding irreversible steps.

Picture it: A lab that labels every bottle, keeps one method per product, and can undo a batch is cheaper to run than a clever one nobody else understands.
The trap: Adding automation until nobody can tell what the system is doing when it goes wrong.
In Formulaite: glassbox.py is Formulaite's operability tool: every run is replayable, so operations means reading a trace, not guessing.
07Normalise with IDs, hydrate on read ch 3

Normalised data stores each human-readable fact once and refers to it by ID. Denormalised data copies the text into every record. Copies read fast but drift when the fact changes. The X timeline stores only post IDs and looks up the text at read time; the book calls this hydrating.

Picture it: Write the ingredient code on the batch card, not its full supplier name. When the supplier renames the product, one master entry changes.
SELECT d.section, d.text, i.inci_name, i.cas_number
FROM   drawer_sections d
JOIN   ingredients i ON d.ingredient_id = i.id
WHERE  d.drawer_id = 42;
The join resolves the ID to the current name; the drawer never stores a stale copy.
The trap: Pasting the ingredient name, supplier and price into every drawer, then fixing a typo in one place and not the other ninety.
In Formulaite: drawer.py sections should reference the catalogue entry by ID and hydrate the name from formulaite_tools.catalogue_lookup when rendered.
08Schema-on-read versus schema-on-write ch 3

Relational tables check the shape of data when it is written. Document stores like Firestore check nothing; the reading code assumes a shape. The book calls the second schema-on-read: the schema still exists, it just lives in your code. Old documents keep their old shape forever.

Picture it: A labelled tray with fixed slots versus a drawer where anything fits. The drawer is flexible until you need to find the pipette.
def load_drawer(doc: dict) -> Drawer:
    # documents written before v2 have no "sources" list
    if "sources" not in doc:
        doc["sources"] = [doc.pop("source_url", "")]
    doc.setdefault("schema_version", 1)
    return Drawer.from_model(**doc)
One function absorbs every old document shape so the rest of the app sees one schema.
The trap: Calling Firestore schemaless and then crashing on the first document written before last week's field rename.
In Formulaite: drawer.py's dataclass is the real schema; a loader like this belongs next to Drawer.from_model so old Firestore documents still parse.
09Event sourcing and CQRS ch 3

Store every change as an immutable event in an append-only log. Derive the read-optimised views from that log. If a view is wrong, delete it and replay the events with fixed code. Events say why something happened, not just which row changed.

Picture it: A lab notebook where you never erase; the current formula is worked out by reading the entries in order.
def rebuild_drawer(events):
    drawer = {}
    for e in events:                 # same order, same code, same result
        if e.kind == "section_filled":
            drawer[e.section] = e.text
        elif e.kind == "section_cleared":
            drawer.pop(e.section, None)
    return drawer
The view is a pure function of the log; nothing else may edit it.
The trap: Letting a consumer reject or edit an event; validation belongs before the event is written, never after.
In Formulaite: glassbox.py already records every step as an Event; the drawer in drawer.py is the materialised view derived from that log.
10Append-only log and the index trade-off ch 4

The simplest database appends every write to a file and reads the last matching line. Writes are fast; reads scan everything. An index fixes reads but costs space and slows every write. LSM-trees keep sorted immutable segments and merge them; B-trees overwrite fixed pages in place.

Picture it: A running list of every weighing versus a card index by ingredient. The list is quick to add to; the cards are quick to search but must be kept up to date.
def db_set(key, value):
    with open("database", "a") as f:
        f.write(f"{key},{value}\n")     # append only, never overwrite

def db_get(key):
    latest = None
    for line in open("database"):
        k, v = line.rstrip("\n").split(",", 1)
        if k == key:
            latest = v                  # last write wins
    return latest
The book's two-line bash database in Python: append is O(1), lookup is O(n) until you add an index.
The trap: Indexing every field by default, then wondering why writes got slow.
In Formulaite: The supplier-page cache in formulaite_tools.py wants exactly one index, by INCI name, and the Glass Box log wants none.
11Vector embeddings and semantic search ch 4

An embedding model turns text into a list of numbers. Similar meanings land close together in that space. A vector index finds the nearest neighbours of a query vector. Flat indexes are exact but slow; IVF and HNSW are fast but approximate.

Picture it: Sorting ingredients by feel rather than by name: two humectants sit near each other even if their names share no letters.
import math
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b))
    return dot / norm

best = max(memory_notes, key=lambda n: cosine(embed(query), n.vector))
A flat index is just this loop; swap it for pgvector or HNSW when the notes outgrow a list.
The trap: Expecting an approximate index to return exactly the same neighbours every time.
In Formulaite: The future memory store in memory.py would embed past drawer notes so 'gentle humectant for dry skin' finds Glycerin without the word.
12Backward and forward compatibility ch 5

Old and new code run at the same time during a rollout. Backward compatibility: new code reads old data. Forward compatibility: old code reads new data and keeps fields it does not understand. Data outlives code, so both matter.

Picture it: A new batch card layout must still be readable by staff on the old form, and the old form must not throw away the new allergen box.
from dataclasses import dataclass, field

@dataclass
class DrawerDoc:
    inci: str
    sections: dict
    extra: dict = field(default_factory=dict)   # keep unknown fields

def decode(raw: dict) -> DrawerDoc:
    known = {k: raw[k] for k in ("inci", "sections") if k in raw}
    unknown = {k: v for k, v in raw.items() if k not in known}
    return DrawerDoc(**known, extra=unknown)
Unknown fields ride along in extra so an old reader does not delete a new writer's data.
The trap: Reading a document into a fixed object, writing it back, and silently dropping the field the newer app added.
In Formulaite: drawer.py and glassbox.py both need a schema_version and an extra bag so traces from last month still load after a field rename.

01Replication lag and eventual consistency ch 6

One leader takes all writes and streams them to followers. Reads can go to any follower, but a follower may be behind. That gap is replication lag. Eventual consistency means the followers catch up if writes stop, with no promise of when.

Picture it: Head office updates the price list; the branch copies arrive by post. For a day, two shops quote different prices.
The trap: Coding as if replication were instant, then debugging a bug that only appears under load.
In Formulaite: Firestore replicas and any read cache in front of the catalogue are followers; formulaite_tools.py should say which reads may be stale.
02Read-your-writes ch 6

A user who just saved something must see it on the next read. Eventual consistency does not promise this. Fixes: read anything the user may have edited from the leader, or remember the write's timestamp and only read from a replica that has caught up.

Picture it: You update your own formula and reload the page. Seeing the old version looks like data loss even if it is only lag.
ref = db.collection("drawers").document(run_id)
ref.set(drawer.as_dict())
fresh = ref.get()                      # same client, server read
assert fresh.get("version") == drawer.version
Read the record you just wrote from the source, not from a cache that may lag.
The trap: Serving the drawer list from a cache right after the agent writes a new drawer, so the user's run appears to vanish.
In Formulaite: After agent.py's gate passes, the app must read the new drawer from Firestore itself, not from the in-memory list in memory.py.
03Sync engines and local-first apps ch 6

A sync engine keeps a full copy of the user's data on the device and syncs in the background. Every device is a leader, so this is multi-leader replication with lag of hours. Offline is just a very long network delay. Conflicts between devices must be resolved.

Picture it: Editing the same formula on your phone in the lab and on the laptop at home, then both syncing overnight.
The trap: Downloading the whole ingredient catalogue to every device; sync engines suit the user's own data, not everyone's.
In Formulaite: Firestore's offline mode makes formula drafts local-first; drafts are per user and small, so they fit the pattern the book describes.
04Last write wins loses data ch 6

When two leaders accept concurrent writes, the simplest fix keeps the write with the newest timestamp and discards the other. The winner is effectively random and the loser's work vanishes silently. Use it only for insert-once data. Otherwise keep both versions or merge per field.

Picture it: Two formulators edit the same draft while offline. LWW keeps whichever phone's clock was ahead and throws the other's afternoon away.
The trap: Trusting device clocks to decide which edit is newer.
In Formulaite: Formula drafts need field-level merging or version history in Firestore; the Glass Box log is insert-only, so LWW is harmless there.
05Sharding key and hot spots ch 7

Sharding splits data across nodes by a partition key. Every record with the same key lands on one shard. Key-range sharding keeps order for range scans; hash sharding spreads load evenly. A hot key, like a celebrity, can still overload one shard; salt it or give it its own shard.

Picture it: Filing ingredient cards by first letter puts every 'Poly-' ingredient in one overstuffed drawer.
import hashlib

def shard_for(partition_key: str, n_shards: int = 16) -> int:
    h = hashlib.md5(partition_key.encode()).hexdigest()
    return int(h, 16) % n_shards

shard_for("user:soma")        # per-user data lands in one shard
shard_for("inci:glycerin")    # a hot ingredient may need a salt
Hash of the key, modulo a fixed shard count; change the count and every key moves.
The trap: Sharding before a single machine is actually full; the book calls sharding a heavyweight solution.
In Formulaite: Formulaite's natural partition key is the user, not the INCI; Glycerin is a hot key that thousands of users research.
06Sharding for multitenancy ch 7

Give each customer their own shard, or group small customers together. You get resource isolation, permission isolation, per-tenant backup and restore, and easy GDPR export or deletion. The cost is that cross-tenant features need cross-shard joins.

Picture it: One labelled shelf per client: nothing gets mixed up, and returning a client's samples means clearing one shelf.
The trap: Storing every user's drafts in one collection with a user_id column and hoping the access rules never have a bug.
In Formulaite: Firestore collections per user for drafts, drawers and memory items give permission isolation for free and make 'delete my account' one operation.
07Atomicity means abortability ch 8

A transaction groups several writes so that either all commit or none do. If a crash or error hits halfway, the database undoes the partial writes. So the application can retry safely without duplicating work. The book says abortability would be a better word.

Picture it: Weighing five ingredients into one beaker: if the scale dies after three, you tip it out and start again, not guess what went in.
batch = db.batch()
batch.set(db.document(f"drawers/{run_id}"), drawer.as_dict())
batch.set(db.document(f"traces/{run_id}"), box.as_dict())
batch.commit()          # both land, or neither does
The drawer and its trace are written together so a trace never points at a drawer that does not exist.
The trap: Writing the drawer, then the trace, in two calls, and leaving an orphan when the second call fails.
In Formulaite: agent.py's RunResult should reach Firestore as one batched write of drawer plus Glass Box trace.
08Snapshot isolation ch 8

Read committed only hides uncommitted writes. Snapshot isolation goes further: a transaction sees the whole database as it was at one moment. Implemented with multiversion concurrency control, keeping old versions until nobody needs them. It prevents read skew but not write skew.

Picture it: Photographing the whole shelf once, then doing your stock count from the photo while colleagues keep moving bottles.
The trap: Assuming 'repeatable read' means the same thing in every database; MySQL, PostgreSQL and Oracle differ.
In Formulaite: A Firestore transaction that reads the catalogue entry and the existing drawer sees one consistent snapshot before the gate compares them.
09Lost updates and compare-and-set ch 8

Read a value, change it, write it back. Two clients doing this at once lose one change. Fixes: an atomic update in the database, an explicit lock, or a conditional write that succeeds only if the value or version is unchanged. Retry when it fails.

Picture it: Two people update the same stock card from memory; the second overwrites the first's deduction.
UPDATE catalogue
SET    notes = 'humectant, use 2-5%', version = version + 1
WHERE  inci = 'Glycerin' AND version = 7;
-- 0 rows updated: someone else got there first, re-read and retry
The version in the WHERE clause is the whole trick; check the row count after the update.
The trap: Letting an ORM load the object, mutate it, and save the whole thing back.
In Formulaite: Two agent runs enriching the same catalogue entry must write through a version check in formulaite_tools.py, never a plain overwrite.
10Write skew ch 8

Two transactions read the same rows, decide something is safe, and each update a different row. Both commit; the rule both checked is now broken. Snapshot isolation does not catch this. You need serializable isolation, an explicit lock on the rows you read, or a constraint the database enforces.

Picture it: Two on-call doctors both see 'two on call' and both go home. The rule 'at least one' was true when each looked.
-- one open draft per formula, enforced by the database
CREATE UNIQUE INDEX one_open_draft
    ON drafts (formula_id) WHERE status = 'open';
-- a second concurrent INSERT now fails instead of slipping through
A partial unique index turns a check-then-insert race into a constraint the database polices.
The trap: Checking 'no open draft exists' in application code and inserting; two concurrent runs both pass the check.
In Formulaite: gates.py rules like 'only one accepted drawer per ingredient per user' must live as a constraint in Firestore rules or a transaction, not only as a Python check.
11Durable execution workflows ch 5

A workflow is a graph of tasks across services. A durable execution engine logs every call and state change. If a task crashes, the engine replays the workflow but returns logged results for steps already done. Steps must be deterministic and external calls idempotent.

Picture it: A batch record that ticks each step: if the power cuts, you resume at the first unticked step instead of remaking the whole batch.
@workflow.defn
class ResearchWorkflow:
    @workflow.run
    async def run(self, inci: str) -> Drawer:
        entry = await workflow.execute_activity(
            catalogue_lookup, inci, start_to_close_timeout=timedelta(seconds=15))
        page = await workflow.execute_activity(
            read_supplier_page, entry.url, start_to_close_timeout=timedelta(seconds=30))
        return await workflow.execute_activity(fill_drawer, entry, page)
Each awaited activity is logged; on replay finished activities return their stored result.
The trap: Reordering or adding a call in an old workflow's code, which breaks replay of runs already in flight.
In Formulaite: A long ingredient-research run in agent.py maps onto a workflow whose activities are the three tools in formulaite_tools.py.

01A timeout tells you nothing ch 9

On a network, a missing reply has three causes: the request was lost, the server is down, or the reply was lost. You cannot tell which. A timeout is the only detector, and after it fires you still do not know if the work happened. Retry only what is safe to repeat.

Picture it: You post an order and hear nothing. Did it arrive, did they close, or did their reply get lost? Sending it again might double the order.
try:
    text = http_get(url, timeout=8)
except TimeoutError:
    box.log("tool_timeout", url=url)   # unknown: lost, dead, or slow
    if tool.idempotent:                 # a read is safe to repeat
        text = http_get(url, timeout=8)
    else:
        raise
Reads are retried; anything with a side effect needs an idempotency key first.
The trap: Picking one timeout for every tool and treating it as proof of failure.
In Formulaite: tools.py should mark each tool idempotent or not, so agent.py knows whether a timed-out fill_drawer may be retried.
02Clocks lie, use logical order ch 9

Time-of-day clocks drift, jump backwards and disagree between machines. Ordering events by their timestamps can put an effect before its cause. Monotonic clocks are safe for measuring durations only. For ordering, use a logical clock: a counter that only goes up.

Picture it: Two lab timers set by hand; the one that is three seconds fast makes it look as if the cream set before it was poured.
import itertools, time
seq = itertools.count()          # logical clock: ordering only

t0 = time.monotonic()            # durations: never jumps back
work()
elapsed = time.monotonic() - t0

event = Event(seq=next(seq), at=time.time(), took=elapsed)
Three clocks, three jobs: seq orders, monotonic measures, time-of-day is for humans.
The trap: Sorting a merged trace from two machines by wall-clock timestamp and trusting the order.
In Formulaite: glassbox.py should stamp every Event with a per-run sequence number, not rely on time.time() to order the replay.
03Fencing tokens for leases ch 9

A lease lets one node act as the owner for a while. A paused node may wake up believing it still owns the lease. A fencing token is a number that grows with every grant. Storage rejects any write carrying a token lower than one it has already seen, so the zombie cannot corrupt data.

Picture it: Numbered batch tickets: the filling line only accepts the highest ticket it has seen, so a stale ticket from a returning worker is refused.
lease = lock_service.acquire("research:glycerin", ttl=30)   # token 34
drawer = research("Glycerin")
store.write(drawer, fencing_token=lease.token)
# the store refuses any write whose token is below the last one it saw
The check happens at the storage side; the client's belief about its lease is irrelevant.
The trap: Assuming a lock service alone is enough and never checking the token where the write lands.
In Formulaite: If several workers pick up research jobs, the Firestore write in agent.py should carry the job's token so a paused worker cannot overwrite a newer drawer.
04Safety versus liveness ch 9

A safety property says nothing bad ever happens; once broken, it stays broken. A liveness property says something good eventually happens. Design so safety holds in every fault scenario and liveness holds when the network recovers. Eventual consistency is a liveness property.

Picture it: Safety: the label never lies about the preservative. Liveness: the batch eventually ships. You may delay shipping; you may never mislabel.
The trap: Sacrificing a safety check to make the run finish faster under load.
In Formulaite: gates.py is safety: no drawer without sources ever ships. agent.py's max_steps is liveness: the loop always ends.
05Deterministic simulation and fault injection ch 9

Distributed bugs hide in rare timings. Fault injection breaks real things on purpose: kill a process, drop a link. Deterministic simulation replaces network, clock and I/O with mocks driven by a seed, so a failing run replays exactly. Both find bugs that hand-written tests miss.

Picture it: Rehearsing a power cut in the lab on a quiet Tuesday, then rerunning the exact same rehearsal after a fix.
class FlakyPages:
    def __init__(self, seed): self.rng = random.Random(seed)
    def read(self, url):
        if self.rng.random() < 0.3:
            raise TimeoutError(url)          # same seed, same failures
        return real_read(url)

for seed in range(200):
    result = run_agent("Glycerin", pages=FlakyPages(seed))
    assert result.drawer is None or gate(result.drawer).passed
The seed makes every failure reproducible; the assertion is the safety property.
The trap: Testing only the happy path and calling the flaky supplier 'rare'.
In Formulaite: models.py's ScriptedModel plus a seeded flaky read_supplier_page in formulaite_tools.py is the lab's deterministic simulator.
06Linearizability and its cost ch 10

Linearizability makes a replicated system look like one copy of the data with atomic operations. After a write completes, every reader sees it. It is the simplest model for programmers and the slowest in practice: response time grows with network uncertainty, and partitioned replicas must refuse requests.

Picture it: One shared whiteboard everyone reads: never stale, but everyone waits their turn to walk to it.
The trap: Using CAP's 'pick two' as a design rule; the book calls the theorem unhelpful.
In Formulaite: Firestore document reads are strongly consistent, so a single drawer read is linearizable; queries over a cache are not, and memory.py must not assume they are.
07Consensus and coordination services ch 10

Leader election, locks, unique IDs and atomic commit are all the same problem: several nodes agreeing on one value despite crashes. Consensus algorithms like Raft solve it with majorities. Do not write your own; use a coordination service such as etcd or ZooKeeper, or a database that embeds one.

Picture it: A committee that only acts when a majority signs. No single absent member can block or fork the decision.
The trap: Hand-rolling failover with timeouts; the book says such systems are likely to be unsafe.
In Formulaite: If Formulaite ever runs several research workers, the 'who owns this job' decision belongs in Firestore transactions or a coordination service, not in memory.py.
08Batch jobs on immutable inputs ch 11

A batch job reads read-only input and writes fresh output every run. No side effects, so a bad run is fixed by correcting the code and rerunning. Keep old outputs to switch back. Push results to serving systems through a stream or a bulk load, not one record at a time.

Picture it: Reprinting the whole price list from the master sheet each night, keeping yesterday's copy in case the new one has a typo.
traces = read_all("traces/2026-09-07/*.json")          # immutable input
embeddings = [(t.inci, embed(t.summary)) for t in traces]
write_all(f"embeddings/v{run_id}/", embeddings)          # fresh output
promote("embeddings/current", f"embeddings/v{run_id}")   # atomic switch
Versioned output plus a pointer swap gives rollback for free.
The trap: Writing batch results straight into the production database row by row, overwhelming it and leaking half-finished output.
In Formulaite: A nightly job over Glass Box traces can rebuild memory.py's embeddings and the eval scores without touching the live catalogue.
09Change data capture instead of dual writes ch 12

Writing to the database and then to the search index from application code races: two clients can leave the two stores permanently different. Instead, let one store be the leader and read its change log. Every derived system becomes a follower applying changes in the same order.

Picture it: One person updates the master sheet; the noticeboard, the price list and the order form are copied from it, never edited directly.
def on_change(change):
    if change.type in ("ADDED", "MODIFIED"):
        search_index.upsert(change.document)
        memory_store.remember(change.document)

db.collection("drawers").on_snapshot(on_change)   # followers of one leader
One writer, many followers; the order comes from the leader's log.
The trap: Updating the drawer, the index and the memory store in three separate calls from the agent.
In Formulaite: Firestore's change stream lets the search index and memory.py follow the drawers collection instead of agent.py writing to all three.
10Exactly-once through request IDs ch 13

A retry after a lost reply can perform an operation twice. Neither TCP nor database transactions stop this end to end. Give each request a unique id at the client and make the database refuse a second insert with the same id. The operation becomes idempotent across every hop.

Picture it: Every purchase order carries a number; the supplier ships an order number once, no matter how many times the fax arrives.
ALTER TABLE requests ADD UNIQUE (request_id);
BEGIN;
INSERT INTO requests (request_id, inci, user_id)
  VALUES ('0286FDB8-D7E1-423F-B40B-792B3608036C', 'Glycerin', 7);
INSERT INTO drawers (request_id, sections) VALUES ('0286FDB8-D7E1-423F-B40B-792B3608036C', '{...}');
COMMIT;   -- a retry with the same id aborts instead of duplicating
The uniqueness constraint does the deduplication; the requests table doubles as an event log.
The trap: Relying on a stream processor's 'exactly-once' setting and forgetting the user's browser can resubmit the form.
In Formulaite: agent.py should mint one request_id per research run and use it as the Firestore document id for drawer, trace and any memory writes.
11Audit derived data end to end ch 13

Hardware corrupts, software has bugs, and constraints get misused. Do not assume the data is right; read it back and check. Event logs make this cheap: rerun the derivation and compare. End-to-end checks cover every disk, network and service on the path at once.

Picture it: Recounting the stock room against the ledger every month, not because you expect theft, but because errors creep in.
def audit(run_id):
    trace = load_trace(run_id)
    rebuilt = rebuild_drawer(trace.events)
    stored = load_drawer(run_id)
    if rebuilt != stored:
        alert("drawer drifted from its trace", run_id)
A derived view is only trusted while it matches a fresh derivation from the log.
The trap: Believing a backup exists because the job says it ran, without ever restoring one.
In Formulaite: A weekly job that replays each Glass Box trace through drawer.py and gates.py and diffs the result is Formulaite's audit.
12Data minimisation and deletion ch 14

Storing data has costs beyond the bill: leaks, subpoenas, fines, and harm to the people described. Keep only what has a stated purpose and delete it when the purpose ends. Immutable logs make deletion hard; per-user logs or encrypting with a key you can destroy make it possible again.

Picture it: Not keeping a client's skin-condition notes after the consultation ends: nothing to leak, nothing to be asked for.
from dataclasses import dataclass
from datetime import datetime

@dataclass
class MemoryItem:
    text: str
    source: str
    user_id: str
    expires_at: datetime          # default: 90 days after creation

def forget_user(user_id: str) -> None:
    delete_where(MemoryItem, user_id=user_id)   # one shard per user makes this cheap
expires_at and a per-user key make 'forget me' a real operation instead of a promise.
The trap: Speculatively storing every supplier page and chat turn 'in case it is useful later'.
In Formulaite: memory.py's future long-term store needs source, user_id and expires_at on every item, and per-user collections so deletion is one call.

Everything on one sheet.

Vocabulary

TermMeans
System of recordThe one authoritative copy of a fact; everything else is derived from it.
Derived dataCaches, indexes, views, models: rebuildable from the record, safe to lose.
Tail latencyThe slow end of the response-time spread (p95, p99); one slow call slows the whole request.
Fault vs failureA part misbehaving vs the whole system missing its job; tolerance stops the first becoming the second.
Replication lagThe delay before a follower reflects a write made on the leader.
Read-your-writesA user always sees their own latest write, whatever other replicas show.
Last write winsConflict rule that keeps the newest timestamp and silently drops the other write.
Partition keyThe field that decides which shard a record lives in.
Hot keyOne key with far more load than the rest; it can overload a single shard.
AtomicityAll of a transaction's writes commit or none do; a failed one can be retried.
Snapshot isolationA transaction reads the database as it was at one instant, via old versions kept around.
Write skewTwo transactions read the same rows, update different rows, and break a rule both checked.
Compare-and-setWrite only if the value or version is still what you read; otherwise retry.
IdempotentDoing it twice has the same effect as doing it once; the basis of safe retries.
Fencing tokenAn ever-increasing number on each lease; storage rejects writes with an older one.
LinearizabilityThe replicated system behaves like a single copy with atomic operations; a recency guarantee.
ConsensusSeveral nodes agreeing on one value despite crashes; behind leader election and locks.
Change data captureReading a database's change log and feeding it to other systems in the same order.
Event sourcingStoring every change as an immutable event and deriving current state from the log.
Schema evolutionChanging a data format while old and new readers and writers keep working.

The pattern

  1. Write each fact once, in the system of record: catalogue, drawer, Glass Box trace.
  2. Stamp every write with a request id and a version; retries then cannot duplicate or clobber.
  3. Append events to a log with sequence numbers; never edit history.
  4. Derive every other view from that log: cache, search index, memory store, evals.
  5. Read your own writes from the source; accept lag everywhere else and say so.
  6. When a view is wrong, delete it and replay the log with fixed code.
  7. Audit by re-deriving and comparing; keep only data with a purpose and an expiry.

Skeletons

Versioned drawer write (compare-and-set)

def save_drawer(db, run_id, drawer, expected_version):
    ref = db.document(f"drawers/{run_id}")
    @firestore.transactional
    def txn(t):
        snap = ref.get(transaction=t)
        if snap.exists and snap.get("version") != expected_version:
            raise Conflict("drawer changed under us")
        t.set(ref, {**drawer.as_dict(), "version": expected_version + 1})
    txn(db.transaction())      # retry from a fresh read on Conflict

Idempotent log consumer

def apply_events(events, view, state):
    for e in events:
        if e.seq <= state.last_seq:      # already applied: skip
            continue
        view.apply(e)                    # deterministic step
        state.last_seq = e.seq           # saved with the view
    return view

Append-only Glass Box log with replay

import itertools, json
class Log:
    def __init__(self, path):
        self.path, self.seq = path, itertools.count()
    def append(self, kind, **meta):
        rec = {"seq": next(self.seq), "kind": kind, **meta}
        with open(self.path, "a") as f:
            f.write(json.dumps(rec) + "\n")
    def replay(self):
        for line in open(self.path):
            yield json.loads(line)

Fault-injecting supplier reader

class FlakyPages:
    def __init__(self, seed, p=0.3):
        self.rng, self.p = random.Random(seed), p
    def read(self, url):
        if self.rng.random() < self.p:
            raise TimeoutError(url)
        return real_read(url)

for seed in range(100):
    r = run_agent("Glycerin", pages=FlakyPages(seed))
    assert r.drawer is None or gate(r.drawer).passed

Before you ship

  • Every store in Formulaite is labelled system of record or derived, with a rebuild path for each derived one.
  • Every research run carries a request id that is the document id for drawer, trace and memory writes.
  • Every drawer document has a version, and writes go through a compare-and-set transaction.
  • Glass Box events carry a sequence number and an event timestamp, and the log is append-only.
  • The search index and memory store follow the drawers change stream; the agent writes to one place.
  • The gate's 'only one' rules are enforced by a constraint or transaction, not only in Python.
  • Supplier reads use timeouts, jittered backoff and a circuit breaker; non-idempotent tools are never auto-retried.
  • Memory items have source, user_id and expires_at, and 'forget me' is one per-user delete.
06 · You're done when…
  1. Point at each Formulaite data store and say which one is the system of record, which are derived, and how each derived one is rebuilt.
  2. Run two research agents on the same ingredient at once and show that the drawer store rejects the stale write instead of losing an update.
  3. Replay a Glass Box change log into a fresh drawer view and memory store, deliver one event twice, and show both views end up correct.
