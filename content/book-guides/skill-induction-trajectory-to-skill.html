Skill Induction: Trajectory-to-Skill Learning

DeepLearning.AI × Oracle · Building Adaptive AI Agents, Lesson 3 · 6:07 video + L2.ipynb

An AI assistant that makes the same mistake every morning is not learning; it is just working. This lesson shows the one mechanism that turns a repeated mistake into a written rule the assistant follows next time — with a person, not the model, deciding whether the rule is allowed in. Start on the Walkthrough tab — it tells the whole story in plain English before a single technical term appears.

From the same wrong turn to a card on the shelf

Step through it. Eight frames, each one written out. It runs in plain English by default — the whole thing told as an assistant with a diary, a clerk, and a shelf of recipe cards — and the toggle switches to the technical version whenever you want the real names.

The same story in one line

Traces in, one reviewed skill out. The engine drafts, a human approves, and only then does the agent's behaviour change. In code: run_dream proposes a pending v2 from one topic's episodes; approve_skills flips it active and the old version superseded; search_skill_box on the same task now returns v2.

When a repeated mistake is worth a written rule

Skill induction is a heavy tool with a human in the middle. It pays for itself only when the shape of the problem matches. The lesson is explicit about the shape.

It applies when the same failure shows up in more than one past run on the same kind of job — in the lesson, three separate episodes on the topic run_test_suite all ran bare pytest and all hit ModuleNotFoundError. The fix is procedural: a sequence of steps a person could write down (“read the Makefile, use make test, never bare pytest”). And you have the raw material: recorded traces, not a memory of what went wrong.In code: a failure becomes a skill only when it repeats across episodes on one topic; induce_skill refuses mixed topics with ValueError.
It does not apply when the error happened once — nothing repeated, nothing to generalise. Or when the fix is not a procedure at all: a bug in the code itself, a timing problem, something slow. Writing “do X then Y” does not repair those. And it does not apply anywhere you would not be prepared to read the model's draft line by line before approving it — because in this design approval is the moment behaviour changes.In code: the lesson's payoff is a retrieval change on a fixed task (before_hit → after_hit). If you cannot state such a task, you cannot tell whether induction worked.
A useful test before you start: could you write the improved skill by hand from the traces? If yes, the engine is a time-saver and the human gate is a safety check. If no — if you would be trusting the model to tell you what happened — you are not ready to approve anything it proposes.

Three questions, in order

  • Does it repeat? Same topic, more than one episode, same error string. The lesson counts three.
  • Is the fix a procedure? In the lesson it is four imperative steps and one prohibition.
  • Who will read the draft? Name the reviewer before running the engine. The slide's third risk is ACCOUNTABILITY: every active skill has an owner, a reason, and a date.

How a trace becomes an active skill, in five stages

Every piece of the lesson's code sits in one of these five stages. Knowing them tells you where to look when a proposal is wrong, missing, or invisible.

Eight practices, from one lesson

Read the weights honestly. This guide is built from a single source — one 6-minute lesson and its notebook. Every practice below therefore rests on one source, and the Desk's usual rule applies: say so plainly. What varies is not how many people agree but which artefacts inside the lesson back it: a transcript timestamp, a slide frame, a notebook cell. Filter by evidence type to see which practices you could verify by watching, by looking, or by running the code.
01One topic in, one skill out.1 sourcetranscript 0:22–0:30cell 12

The engine reads every episode about one kind of job and produces exactly one skill for it. Mixing jobs produces a recipe that fits none of them.

In practice: Filter first, then induce. Cell 12 does exactly this — run_test_episodes = [e for e in episodes if e["topic"] == "run_test_suite"] — before calling induce_all. Mixed topics raise ValueError.

02Keep provenance — never accept a skill that cannot name its episodes.1 sourcetranscript 0:44–1:25cell 20

Proposals carry evidence for each change. The episode ids are how a reviewer checks the clerk's working, and how an approved skill can later be traced back if it turns out wrong.

In practice: The v2 proposal lists ep-run_test_suite-001 .. -006. The notebook's wrap-up names provenance as one of the things the engine must distill. An empty provenance list is a decline.

03Decline with a reason — the reason is the training signal.1 sourcetranscript 1:10–1:25slide 3cell 15

The transcript: “decline, giving the skill induction engine a reason so that it can generate a better proposed enhancement.” Slide 3's DECLINE pill reads “back to the engine, with a reason”.

In practice: The review app in cell 15 has a Review reason box above Approve and Reject. The reason is passed as feedback into the next induce_skill call and appended to the prompt: “A human reviewer rejected the previous version with this feedback; revise the skill to address it.” Rejecting without a reason wastes the loop.

04Never approve a non-latest version.1 sourcetranscript 4:27–4:59cell 16–17

Approval is a state machine, not a copy. Approving v2 flips v1 to superseded. Approving an older version out of order would leave the topic with the wrong recipe active.

In practice: The governance module guards this: you cannot approve a non-latest version and you cannot approve something already active — both raise ValueError. Cell 16 then re-indexes to “confirm the enhanced skill is now active, replacing the previous version.”

05Only active is retrievable — the box is a search index, not a folder.1 sourceslide 1cell 9–10

Slide 1 draws PENDING HUMAN REVIEW outside the SKILL BOX. A pending or rejected skill exists in storage but the agent cannot find it.

In practice: Cell 10: index_active_skills(connection=conn, mem=mem) builds the store from active skills only, then search_skill_box(skill_box, PAYOFF_TASK, k=1). If a skill is not showing up, check its status before you check the search.

06Run the engine outside the agent's working path.1 sourcetranscript 0:44–1:10cell 13

The transcript: “Now outside of the main agent's working path, we then run the skill induction engine.” It does not slow the agent down and it does not edit live behaviour.

In practice: Cell 13's run_dream(mem, run_test_episodes, complete=night, connection=conn) is that separate pass; OracleSaver checkpoints the candidate and it lands pending. The agent keeps using v1 until a human acts.

07Quote the real error string — describe the bug the traces describe.1 sourceslide 1cell 6

The lesson's failure is ModuleNotFoundError: No module named 'app' (wrong interpreter): bare pytest picked up the wrong Python. An earlier summary of this lesson described it as a missing PATH entry and taught a fix for a bug that never happened.

In practice: Cell 6's show_recurring_failure() shows the real error before anything is induced. The v2 skill's errors_and_fixes entry quotes it. If your skill's error field does not match a string in the traces, the model has paraphrased.

08Measure the payoff as a retrieval change on a fixed task.1 sourcetranscript 5:11–5:44cell 19

“Behaviour adaptation” is operationally this: the same query returns a different skill. Not a feeling that the agent got better.

In practice: Cell 10 captures before_hit; cell 19 re-indexes, captures after_hit on the identical PAYOFF_TASK, and retrieval_improvement_html puts them side by side. Before: v1, bare pytest, error. After: v2, make test, 212 passed.

The actual v1 → v2 diff

This is the lesson's punchline, quoted from the fixtures as the chapter spec recorded them. v1 is deliberately generic. v2 is what the engine drafted from six episodes on the topic.

BEFORE STATUS ACTIVE VERSION v1
BASE_SKILLS["run-the-tests"] 
find the test command -> run it -> report the result

Three steps. Nothing about which command, nothing about what went wrong last time. Slide 1's card adds the red note: - bare pytest chosen.

AFTER VERSION v2 pending → active on approval
data/engine_outputs/night2.json["run_test_suite"] 
name: run_project_test_suite
1. Read the Makefile to locate the canonical test command if unknown
2. Invoke the project's test command (make test), forwarding any filters such as -k
3. Report the numeric result or failure summary
4. Never invoke bare pytest or pytest directly on this repository
errors_and_fixes: 3 entries, one per repeat offence
provenance: ep-run_test_suite-001 .. -006

Four steps — the video calls out “four steps” at 4:17 — plus three errors_and_fixes entries and six provenance ids. The first error entry, as the gap report quotes it: ran bare pytest, hit ModuleNotFoundError because the wrong interpreter/environment was used → do not run bare pytest; use the project's test command (make test), which runs the project venv.

Glossary for this block: a Makefile is a project's file of named shortcuts, so make test runs whatever test command the project chose. A venv is the project's private copy of Python and its add-ons; running bare pytest outside it is why the code could not be found. -k is a filter that runs only tests whose names match.

Why a human in the loop? Four things that can happen at the gate

Slide 3 of the lesson draws one card, two pills and three risks. The same proposal can go four ways depending on what the reviewer does — and on what was in the traces. Step through all four.

The three risks, in the slide's words. BAD SKILLS COMPOUND — “an approved mistake is retrieved on every matching task, forever”. MEMORY POISONING — “incorrect or planted traces must not write themselves into behaviour”. ACCOUNTABILITY — “every active skill has an owner, a reason, and a date”.
Why decline is not a bin. The reason typed into the review box is appended to the next induction prompt — “A human reviewer rejected the previous version with this feedback; revise the skill to address it: <reason>” — and the lesson ships a fixture, reflected.json, showing the revised output differs. In code: induce_skill(..., feedback=reason). The correction is text, applied at the next pass — the Reflexion pattern.

Five anti-patterns

Each of these was either warned against in the lesson or committed by an earlier summary of it that the gap report audited.

  1. Approving without reading. Approval turns a proposal into behaviour the agent reuses on every matching task. The review screen puts v1 and v2 side by side for a reason. If you did not compare them, you did not review.
  2. Describing the bug as a missing PATH when it is the wrong interpreter. The trace says ModuleNotFoundError: No module named 'app' (wrong interpreter). An earlier chapter invented a skill that exported a PATH entry — a fix for a bug that never happened. Quote the error string; do not infer the cause from a half-built slide.
  3. Treating the skill box as a folder. It is an indexed retrieval surface built from active skills. Pending and rejected skills are not in it. Approval is a state change (pending → active, active → superseded), not a file copy.
  4. Rejecting without a reason. The reason is appended to the next induction prompt. A bare reject throws away the only signal the engine gets from a human.
  5. Letting the model set topic. induce_skill sets topic from the episodes it was given. If the model could relabel what it was generalising from, one topic's skill could quietly claim another topic's jobs.

The one-turn action card

If you take one thing from this guide into a project instructions file, take this.

  1. Does the failure repeat across episodes on one topic, with the same error string? If not, stop — fix it by hand.
  2. Gather that topic's episodes only. Never mix topics into one induction call.
  3. Run the engine outside the live path. Check the draft has all nine fields, a non-empty provenance, and an errors_and_fixes entry that quotes the real error.
  4. Read v1 beside v2. Confirm the draft's topic was set by code, not by the model.
  5. Approve or decline — and write the reason either way. Decline's reason feeds the next draft; approve's reason is the accountability record.
  6. Re-index. Re-run the same fixed task. Compare before_hit with after_hit. If retrieval did not change, behaviour did not change.
