01 · Where this is going

An agent is not one clever prompt; it is a handful of named patterns, chained, routed, reflected, gated and remembered, that you compose like bricks.

Read this book when: Open it once you know what an agent loop is and want a name, a shape and a rule of thumb for each piece you are about to add.

The one picture that holds the whole book. Every chapter adds a box or an arrow to it; nothing later replaces it.

flowchart TD
  U[Goal] --> P[Planning - list the steps]
  P --> R[Routing - choose a path]
  R --> C[Prompt chaining - one step at a time]
  R --> X[Parallelization - independent steps together]
  C --> T[Tool use - catalogue lookup, supplier page]
  X --> T
  T --> K[Knowledge retrieval - grounded facts]
  K --> D[Draft drawer]
  T --> D

  F -->|reasons| D
  F --> G[Guardrails and gate]
  G -->|unsafe or unsure| H[Human in the loop]
  G -->|pass| O[Answer]
  M[Memory - session state] --- D
  E[Evaluation - trajectory and cost] --- O
02 · Build ladder

Three things to build, in order

Each rung is a Formulaite feature. Click a rung for its steps. Do rung 1 after the Foundation cards, rung 2 after Intermediate, rung 3 after Advanced.

Rung 1 · Simple

Chain, tool, critic: the drawer pipeline

A fixed three-step chain (catalogue lookup, supplier page, fill drawer) where every tool is described by its docstring and a deterministic gate plays the critic.

~2 hours
Rung 2 · Intermediate

Router, fan-out, state and fallbacks

A router in front of the loop, three supplier pages fetched at once, a session state dict beside the chat, and a fallback path when a page fails.

~half a day
Rung 3 · Advanced

Guardrails, MCP tools, cost routing and evals

Formulaite tools served over MCP, a before-tool allow-list, a cheap-model pre-screen of supplier pages, model routing by task, a human approval step and a ten-ingredient eval set.

~2 days

Steps for rung 1: Chain, tool, critic: the drawer pipeline

  1. Write the drawer job as a chain in SYSTEM_PROMPT: catalogue_lookup, then read_supplier_page, then fill_drawer.
  2. Register both tools with @registry.tool so the docstring becomes the description the model reads.
  3. Make fill_drawer the only way to answer, so the output is structured, never prose.
  4. Run run_gates on the drawer and send the reasons back as a REJECTED tool_result.
  5. Log every model reply, tool call and verdict in the Glass Box and replay one run.
Chapters 1, 4, 5, 22 · Agent Lab files: agent.py · tools.py · formulaite_tools.py · gates.py · glassbox.py · ~2 hours

Steps for rung 2: Router, fan-out, state and fallbacks

  1. Add a rule-based router before Agent.run: banned ingredient stops, unknown asks, known researches.
  2. Fetch three supplier pages with asyncio.gather and merge them into one draft grounded only on those pages.
  3. Keep ingredient, current step and sources found in a state dict, separate from the message list.
  4. On a failed supplier page, fall back to the catalogue and mark the source as catalogue-only.
  5. Turn REQUIRED_SECTIONS into the goal checklist and stop only when it is ticked or max_steps ends.
Chapters 2, 3, 6, 8, 11, 12, 14 · Agent Lab files: agent.py · memory.py · formulaite_tools.py · drawer.py · glassbox.py · ~half a day

Steps for rung 3: Guardrails, MCP tools, cost routing and evals

  1. Serve catalogue_lookup and read_supplier_page from a FastMCP server and consume them with a tool_filter.
  2. Screen every supplier page with a small cheap model for injection before it reaches the main model.
  3. Add a before-tool check in ToolRegistry.call that blocks any tool or argument outside the allow-list.
  4. Route simple lookups to the cheap model and full drawers to the strong one; log the model name and tokens.
  5. Require a human approval tool before a drawer is written to the live catalogue.
  6. Build a ten-INCI eval set with the expected tool order; compare trajectory and gate pass rate after every change.
Chapters 7, 10, 13, 16, 18, 19 · Agent Lab files: formulaite_tools.py · tools.py · gates.py · glassbox.py · models.py · ~2 days

01Prompt chaining ch 1

One big prompt makes the model juggle too much. It skips instructions, loses context and passes early errors forward. Prompt chaining splits the job into small prompts. Each one does one thing and hands its output to the next.

Picture it: A lab bench with stations: weigh, mix, check pH. Nobody tries to do all three in one bowl.
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
prompt_extract = ChatPromptTemplate.from_template(
    "Extract the technical specifications from:\n\n{text_input}")
prompt_transform = ChatPromptTemplate.from_template(
    "Turn these specs into JSON with cpu, memory, storage keys:\n\n{specifications}")
extraction_chain = prompt_extract | llm | StrOutputParser()
full_chain = ({"specifications": extraction_chain}
              | prompt_transform | llm | StrOutputParser())
print(full_chain.invoke({"text_input": input_text}))
LangChain LCEL: the | pipe feeds one step's output into the next; the dict maps it onto the next prompt's variable.
The trap: Passing loose prose between steps, so a wobbly step-one answer breaks step two.
In Formulaite: agent.py — SYSTEM_PROMPT already is a chain: catalogue_lookup, then read_supplier_page, then fill_drawer, one step per turn.
02Context engineering ch 1

Prompt engineering polishes the question. Context engineering builds the whole picture the model sees: system prompt, retrieved documents, tool outputs and who the user is. The book says output quality depends more on this context than on the model.

Picture it: A good brief for a freelance chemist: the target product, the supplier sheet, the banned list and last month's notes, not just 'make a moisturiser'.
The trap: Rewording the prompt ten times while the model still cannot see the supplier page.
In Formulaite: memory.py — Conversation is the context: request, tool results and gate feedback assembled before every model call.
03Reflection loop ch 4

The first draft is rarely right. Reflection adds a feedback loop: produce, critique, refine, repeat. A stop phrase or a maximum number of rounds ends the loop. It costs more calls but gives better output.

Picture it: You write the label copy, a colleague marks it up in red, you fix only the red bits, and you stop after three passes.
message_history = [HumanMessage(content=task_prompt)]
for i in range(max_iterations):
    if i > 0:
        message_history.append(HumanMessage(
            content="Please refine the code using the critiques provided."))
    response = llm.invoke(message_history)
    current_code = response.content
    message_history.append(response)
    critique = llm.invoke(reflector_prompt(task_prompt, current_code)).content
    if "CODE_IS_PERFECT" in critique:
        break
    message_history.append(HumanMessage(content=f"Critique:\n{critique}"))
LangChain: one llm, two roles; the critic's stop phrase CODE_IS_PERFECT and max_iterations are the two exits.
The trap: No max_iterations, so a picky critic keeps the loop and the bill running.
In Formulaite: agent.py — the REJECTED-by-gate tool_result is the critique; the model refines and calls fill_drawer again, capped by max_steps.
04Producer and critic ch 4

One agent writes, a different agent reviews. The critic has its own persona and criteria, so it is not fooled by the producer's confidence. The book calls this Generator-Critic. The critic's output is structured: a status plus reasons.

Picture it: The formulator who mixed the batch does not sign off the QC sheet; a second person with a checklist does.
from google.adk.agents import SequentialAgent, LlmAgent
generator = LlmAgent(name="DraftWriter",
    instruction="Write a short, informative paragraph about the user's subject.",
    output_key="draft_text")
reviewer = LlmAgent(name="FactChecker",
    instruction="""Read state key 'draft_text'. Verify every claim.
    Output a dict with "status": "ACCURATE" or "INACCURATE" and "reasoning".""",
    output_key="review_output")
review_pipeline = SequentialAgent(name="WriteAndReview_Pipeline",
                                  sub_agents=[generator, reviewer])
Google ADK: output_key saves each agent's reply into shared state; the reviewer reads draft_text and writes review_output.
The trap: Letting the producer grade its own work with the same prompt and the same blind spots.
In Formulaite: gates.py — run_gates is the critic with no model at all: fixed checks, PASS or FAIL, a reasons tuple.
05Tool use in six steps ch 5

The model cannot fetch or act. It reads tool descriptions, decides a tool is needed, and emits a structured call with arguments. Your framework runs the function and returns the result. The model then answers or calls again.

Picture it: A chef who cannot leave the kitchen writes a shopping note; the runner buys the items and brings back the receipt.
from langchain_core.tools import tool as langchain_tool
from langchain.agents import create_tool_calling_agent, AgentExecutor
@langchain_tool
def search_information(query: str) -> str:
    """Provides factual information on a given topic."""
    return simulated_results.get(query.lower(), simulated_results["default"])
agent_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    ("human", "{input}"), ("placeholder", "{agent_scratchpad}")])
agent = create_tool_calling_agent(llm, [search_information], agent_prompt)
agent_executor = AgentExecutor(agent=agent, tools=[search_information])
LangChain: the docstring is what the model reads; agent_scratchpad is where tool calls and results accumulate.
The trap: A vague docstring, so the model never picks the tool or calls it with the wrong argument.
In Formulaite: tools.py — @registry.tool turns catalogue_lookup's signature and docstring into the input_schema the model sees.
06Tools raise, they do not return error strings ch 5

The CrewAI example returns a float or raises ValueError. A raised error is a clear signal the agent can handle. An error hidden in a string looks like data. The task description then tells the agent what to do on failure.

Picture it: A thermometer that beeps when the probe is broken is safer than one that quietly shows 20 degrees.
from crewai import Agent, Task, Crew
@tool("Stock Price Lookup Tool")
def get_stock_price(ticker: str) -> float:
    """Fetches the latest simulated stock price. Raises ValueError if not found."""
    price = simulated_prices.get(ticker.upper())
    if price is not None:
        return price
    raise ValueError(f"Simulated price for ticker '{ticker.upper()}' not found.")
analyze_task = Task(
    description="Find AAPL's price. If the ticker is not found, report that clearly.",
    expected_output="One clear sentence with the price, or that it could not be found.",
    agent=financial_analyst_agent)
CrewAI: the tool is plain Python; role, goal and backstory live on the Agent, the failure rule lives in the Task.
The trap: Returning 'error: not found' as a string, which the model may read as a real value.
In Formulaite: tools.py — ToolError is raised by the registry; agent.py turns it into an is_error tool_result so the model can recover.
07System prompt, delimiters and examples ch 22

Be clear, specific and concise. Tell the model what to do, not what to avoid. Put standing rules in a system prompt. Mark sections with delimiters such as XML tags. Add three to five examples when the format matters.

Picture it: A recipe card: title, an ingredients box, a method box, and a photo of the finished cream.
<instruction>Summarize the following article, focusing on the main
arguments presented by the author.</instruction>
<article>
[Insert the full text of the article here]
</article>
A prompt, not Python: the tags are delimiters so the model cannot confuse instructions with the article text.
The trap: A wall of negative constraints, so the model focuses on avoiding rather than doing.
In Formulaite: agent.py — SYSTEM_PROMPT is four positive numbered rules plus one output rule; the numbering is the delimiter.
08Pydantic parses the model's JSON ch 22

Ask for JSON, then parse it into a Pydantic model. One call checks the shape and the types and converts strings to dates. Bad output raises ValidationError, which you catch and retry. The book calls this 'parse, don't validate' at the boundary.

Picture it: A customs form with fixed boxes: the officer rejects it at the border instead of discovering a missing field three offices later.
from pydantic import BaseModel, EmailStr, Field, ValidationError
class User(BaseModel):
    name: str = Field(..., description="The full name of the user.")
    email: EmailStr
    interests: List[str] = Field(default_factory=list)
try:
    user_object = User.model_validate_json(llm_output_json)
    print(user_object.name, user_object.interests[0])
except ValidationError as e:
    print("Failed to validate JSON from LLM.")
    print(e)
Plain Pydantic: model_validate_json parses and validates in one step; the Field descriptions double as the schema you show the model.
The trap: Trusting json.loads alone, so a missing key crashes three steps later.
In Formulaite: drawer.py — IngredientDrawer.from_model_input plus missing() play the same role for the fill_drawer call.
09ReAct: thought, action, observation ch 22

ReAct interleaves reasoning and acting. The model writes a thought, picks an action such as a tool call, and reads the observation that comes back. Then it thinks again. The loop ends with a Final Answer.

Picture it: Troubleshooting a separated emulsion: think about the cause, run one test, look at the result, think again.
Thought: The user wants the capital of France and its population.
Action: Search({"query": "capital of France"})
Observation: Paris
Thought: Now I need the population of Paris.
Action: Search({"query": "current population of Paris"})
Observation: About 2.1 million people in 2023.
Final Answer: The capital of France is Paris, population about 2.1 million.
An illustrative trace, not Python: every Observation line is written by your code, never by the model.
The trap: Letting the model write its own Observation line, so it hallucinates tool output.
In Formulaite: agent.py — Agent.run is the ReAct loop: model_reply is thought and action, the tool_result is the observation.

01Routing ch 2

A chain always takes the same path. Routing adds a decision: look at the input, pick a handler. The router can be an LLM prompt that outputs one word, an embedding match, a rule, or a small trained classifier. Unclear inputs go to a clarify branch.

Picture it: A pharmacy counter: prescriptions go left, advice goes right, anything odd goes to the pharmacist.
from langchain_core.runnables import RunnablePassthrough, RunnableBranch
coordinator_router_prompt = ChatPromptTemplate.from_messages([
    ("system", "Output ONLY one word: 'booker', 'info', or 'unclear'."),
    ("user", "{request}")])
coordinator_router_chain = coordinator_router_prompt | llm | StrOutputParser()
delegation_branch = RunnableBranch(
    (lambda x: x["decision"].strip() == "booker", branches["booker"]),
    (lambda x: x["decision"].strip() == "info", branches["info"]),
    branches["unclear"])   # default branch
coordinator_agent = ({"decision": coordinator_router_chain,
                      "request": RunnablePassthrough()} | delegation_branch)
LangChain: the LLM only picks a label; RunnableBranch does the if/elif/else, and the last entry is the default.
The trap: No default branch, so one unexpected label crashes the whole request.
In Formulaite: agent.py — a rule-based router before Agent.run: banned ingredient stops, unknown asks, known researches.
02Parallelization ch 3

Independent steps should not wait for each other. Run them at once and merge the results in a final step. This cuts latency most when steps wait on APIs. The book notes asyncio gives concurrency on one thread, not true parallelism.

Picture it: Three assistants each phone one supplier at the same time; you write the comparison when all three hang up.
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
map_chain = RunnableParallel({
    "summary": summarize_chain,
    "questions": questions_chain,
    "key_terms": terms_chain,
    "topic": RunnablePassthrough(),   # keep the original input
})
full_parallel_chain = map_chain | synthesis_prompt | llm | StrOutputParser()
async def run_parallel_example(topic: str) -> None:
    response = await full_parallel_chain.ainvoke(topic)
    print(response)
asyncio.run(run_parallel_example("The history of space exploration"))
LangChain: a dict of runnables runs concurrently; the synthesis prompt receives all the keys at once.
The trap: Parallelising steps that secretly depend on each other, then debugging a race.
In Formulaite: formulaite_tools.py — read_supplier_page for three suppliers at once, merged into one drawer draft.
03Fan out, then merge ch 3

ADK gives this shape names. A ParallelAgent runs sub-agents concurrently; each writes to state under its output_key. A SequentialAgent then runs a merger agent that reads those keys. The merger is told to use only the provided summaries.

Picture it: Three scouts report to the same whiteboard; the writer is only allowed to use what is on the board.
from google.adk.agents import LlmAgent, ParallelAgent, SequentialAgent
parallel_research_agent = ParallelAgent(
    name="ParallelWebResearchAgent",
    sub_agents=[researcher_agent_1, researcher_agent_2, researcher_agent_3])
merger_agent = LlmAgent(name="SynthesisAgent", model=GEMINI_MODEL,
    instruction="""Combine the research summaries into a report.
    Your entire response MUST be grounded exclusively on the Input Summaries:
    {renewable_energy_result} {ev_technology_result} {carbon_capture_result}""")
sequential_pipeline_agent = SequentialAgent(
    name="ResearchAndSynthesisPipeline",
    sub_agents=[parallel_research_agent, merger_agent])
Google ADK: {renewable_energy_result} is filled from session state written by a researcher's output_key.
The trap: A merger prompt that lets the model add outside knowledge, so the report contains facts nobody fetched.
In Formulaite: gates.py — check_has_sources is the 'grounded exclusively' rule made deterministic.
04Planning: discover the how ch 6

Planning turns a goal into ordered steps the agent invents at run time. Use it when the path is unknown. When the recipe is known and repeatable, a fixed workflow is safer and more predictable. A good plan adapts when a step fails.

Picture it: Organising a team offsite needs a plan; restocking the same ten raw materials every month needs a checklist.
from crewai import Agent, Task, Crew, Process
planner_writer_agent = Agent(role="Article Planner and Writer",
    goal="Plan and then write a concise, engaging summary on a specified topic.",
    backstory="You create a clear, actionable plan before writing.", llm=llm)
high_level_task = Task(
    description=f"1. Create a bullet-point plan for a summary on: '{topic}'.\n"
                f"2. Write the summary based on your plan, around 200 words.",
    expected_output="### Plan\n- bullets\n\n### Summary\n- the summary",
    agent=planner_writer_agent)
crew = Crew(agents=[planner_writer_agent], tasks=[high_level_task],
            process=Process.sequential)
result = crew.kickoff()
CrewAI: the plan is forced by the task description and expected_output; plan and execution stay in one agent.
The trap: Using a planning agent for a job you already know how to do, trading predictability for nothing.
In Formulaite: agent.py — SYSTEM_PROMPT is a fixed plan on purpose; planning would only enter for a new ingredient class with no known recipe.
05Session, state and memory ch 8

ADK splits memory into three. A Session is one chat thread with its events. State is that thread's scratchpad dict. Memory is a searchable store across sessions. Key prefixes user:, app: and temp: say how long a value lives.

Picture it: A lab notebook page (session), the sticky notes on it (state), and the filing cabinet in the corridor (memory).
def log_user_login(tool_context: ToolContext) -> dict:
    """Updates the session state upon a user login event."""
    state = tool_context.state
    login_count = state.get("user:login_count", 0) + 1
    state["user:login_count"] = login_count
    state["task_status"] = "active"
    state["user:last_login_ts"] = time.time()
    state["temp:validation_needed"] = True
    return {"status": "success",
            "message": f"User login tracked. Total logins: {login_count}."}
Google ADK: state changes happen inside a tool via ToolContext, so they are recorded as events and persisted.
The trap: Editing session.state directly after fetching it, which skips the event log and may never be saved.
In Formulaite: memory.py — Conversation is the session; a state dict for ingredient, step and sources would sit beside it.
06Three kinds of long-term memory ch 8

Semantic memory is facts, like a user profile. Episodic memory is past experiences, often reused as few-shot examples. Procedural memory is the rules: the system prompt itself, which an agent can rewrite by reflection. LangGraph stores all three as JSON under a namespace and key.

Picture it: What you know about a client, what happened last time you worked together, and your own house rules.
from langgraph.store.memory import InMemoryStore
store = InMemoryStore(index={"embed": embed, "dims": 2})
namespace = ("my-user", "chitchat")
store.put(namespace, "a-memory",
          {"rules": ["User likes short, direct language",
                     "User only speaks English & python"],
           "my-key": "my-value"})
item = store.get(namespace, "a-memory")
items = store.search(namespace, filter={"my-key": "my-value"},
                     query="language preferences")
LangGraph: namespace is the folder, key is the filename; search combines a filter with vector similarity.
The trap: Stuffing every past chat into the prompt instead of storing facts and retrieving the few that matter.
In Formulaite: memory.py — a namespace per formulator holding known-good use levels would be the semantic layer next to Conversation.
07Goal setting and monitoring ch 11

State the goals as a checklist. Generate, ask for feedback against the checklist, then ask one yes-or-no question: are the goals met? Loop until True or the attempt limit. The book warns that a model judging its own work may not notice it is off course.

Picture it: A spec sheet taped above the bench: pH 5.5, viscosity in range, no separation at 40 degrees. Every batch is tested against it.
def run_code_agent(use_case: str, goals_input: str, max_iterations: int = 5) -> str:
    goals = [g.strip() for g in goals_input.split(",")]
    previous_code, feedback = "", ""
    for i in range(max_iterations):
        prompt = generate_prompt(use_case, goals, previous_code, feedback)
        code = clean_code_block(llm.invoke(prompt).content.strip())
        feedback = get_code_feedback(code, goals).content.strip()
        if goals_met(feedback, goals):     # LLM answers only True or False
            break
        previous_code = code
    return save_code_to_file(add_comment_header(code, use_case), use_case)
LangChain + OpenAI: goals_met reduces the judge to one word so the loop has a clean exit; max_iterations is the safety net.
The trap: Trusting the model's own True, so 'goals met' means 'the model thinks so' and nothing was ever run.
In Formulaite: drawer.py — REQUIRED_SECTIONS is the goal checklist; gates.py decides met-or-not without asking a model.
08Exception handling and recovery ch 12

Three stages. Detect: bad tool output, API error codes, timeouts, nonsense replies. Handle: log, retry, fall back, degrade gracefully, notify. Recover: roll back state, diagnose, replan or escalate. Never retry the same invalid action forever.

Picture it: The supplier site is down: note it, try once more, use last month's data sheet marked as stale, and tell the formulator.
from google.adk.agents import Agent, SequentialAgent

09RAG: chunk, embed, retrieve, augment ch 14

Split documents into chunks. Turn each chunk into an embedding, a list of numbers that captures meaning. Store them in a vector database. At question time, embed the question, fetch the closest chunks, and paste them into the prompt. Answers become grounded and citable.

Picture it: Instead of reading the whole 50-page manual, you look up the one troubleshooting page and quote it.
from langchain.text_splitter import CharacterTextSplitter

                                      embedding=OpenAIEmbeddings(), by_text=False)
retriever = vectorstore.as_retriever()
def retrieve_documents_node(state: RAGGraphState) -> RAGGraphState:
    documents = retriever.invoke(state["question"])
    return {"documents": documents, "question": state["question"], "generation": ""}
LangChain + LangGraph: retrieve is one graph node, generate is the next; the prompt says 'if you don't know, say so'.
The trap: Chunks so big or so small that the answer is split across two of them and the retriever fetches neither.
In Formulaite: formulaite_tools.py — read_supplier_page would become retrieve_supplier_chunks over an embedded library of data sheets.
10Agentic RAG ch 14

Plain RAG accepts whatever comes back. Agentic RAG puts a reasoning step in front: check the source date, prefer the authoritative document, reconcile two numbers that disagree, split a big question into sub-queries, and call a web search when the store has a gap. It adds latency and can itself go wrong.

Picture it: Two data sheets give different use levels; the agent picks the 2025 supplier sheet over a 2020 blog post and says why.
The trap: Adding the reasoning layer without a loop limit, so the agent keeps re-searching a question it cannot answer.
In Formulaite: gates.py — check_use_level_in_range is a one-rule reconciler: the catalogue beats the supplier page when they disagree.

03Learning and adaptation ch 9

An agent adapts when it changes its behaviour from experience. Methods run from reinforcement learning to simple memory-based learning. SICA edits its own source code, keeps an archive of versions with scores, and an overseer LLM watches for loops. AlphaEvolve evolves programs against an evaluator.

Picture it: Keeping a scored log of every batch and reusing the settings of the best one next time.
The trap: Letting an agent change its own prompt without a benchmark, so 'improvement' is just drift.

04MCP versus function calling ch 10

Function calling is one app telling one model about its own tools. MCP is an open standard: a server exposes tools, resources and prompts, and any client can discover and call them. MCP only wraps an API; if the API returns PDFs the agent cannot read, MCP does not fix that.

Picture it: Custom-built tools in your own workshop, versus a standard power socket any maker's tool can plug into.

The trap: Wrapping a one-record-at-a-time legacy API in MCP and expecting the agent to summarise thousands of records.
In Formulaite: formulaite_tools.py — catalogue_lookup and read_supplier_page behind a FastMCP server, so any client agent can use them.

07Resource-aware routing ch 16

Not every step needs the big model. Classify the request first: simple, reasoning, or needs search. Send simple ones to a cheap fast model and hard ones to the strong one. Keep a fallback model for when the first is down. A critic agent later flags bad routing choices.

Picture it: You do not send a routine pH check to the external lab; you send the stability study.
def generate_response(prompt: str, classification: str, search_results=None):
    if classification == "simple":
        model = "gpt-4o-mini"
    elif classification == "reasoning":
        model = "o4-mini"
    elif classification == "internet_search":
        model = "gpt-4o"
        prompt = f"Use the following web results to answer:\n{search_results}\n{prompt}"
    response = client.chat.completions.create(
        model=model, messages=[{"role": "user", "content": prompt}])
    return response.choices[0].message.content, model
OpenAI SDK: classify_prompt first returns {'classification': ...} as JSON; the model name is returned so you can log cost.
The trap: Routing on query length alone, so a short but hard question gets the weak model.
In Formulaite: models.py — ScriptedModel for the cheap path, ClaudeModel for the full drawer; log the model name in the Glass Box.
08Reasoning techniques and the thinking budget ch 17

Chain-of-Thought makes the model write its steps before the answer. Tree-of-Thought explores several branches and backtracks. Self-correction reviews a draft against the original brief. The Scaling Inference Law says a smaller model given more thinking time can beat a bigger one.

Picture it: A junior formulator who writes out the reasoning and tries two routes often beats a senior one guessing fast.
The trap: Buying a bigger model before trying a reflection step or a few more iterations.
In Formulaite: agent.py — max_steps is the thinking budget; raising it for hard ingredients is the cheapest experiment.
09Guardrails as layers ch 18

No single guardrail is enough. Layer them: sanitise input, check output, constrain behaviour in the prompt, restrict tools, add external moderation, keep a human for critical calls. A small cheap model can pre-screen inputs. Validate tool arguments in a callback before the tool runs.

Picture it: Gloves, fume hood, labelled bottles and a locked cabinet: none of them is enough alone.
def validate_tool_params(tool: BaseTool, args: Dict[str, Any],
                         tool_context: ToolContext) -> Optional[Dict]:
    """Validates tool arguments before execution."""
    expected_user_id = tool_context.state.get("session_user_id")
    actual_user_id_in_args = args.get("user_id_param")
    if actual_user_id_in_args and actual_user_id_in_args != expected_user_id:
        return {"status": "error",   # returning a dict blocks the tool
                "error_message": "Tool call blocked: User ID validation failed."}
    return None                      # None lets the call proceed
root_agent = Agent(model="gemini-2.0-flash-exp", name="root_agent",
    before_tool_callback=validate_tool_params, tools=[...])
Google ADK: before_tool_callback runs on every call; return None to allow, a dict to block with a message.
The trap: Relying on the system prompt to stop injection hidden in a supplier page the model was told to trust.
In Formulaite: tools.py — ToolRegistry.call is where an allow-list and argument check belong, before the function runs.
10Engineer agents like software ch 18

Treat the agent as a complex system. Checkpoint validated states and roll back on failure, like a database transaction. Keep agents small and separate. Log the whole chain of thought, tools and confidence. Give each agent the minimum permissions it needs.

Picture it: You would not run a new batch process without a stop button, a logbook and a locked chemical store.
The trap: A monolithic do-everything agent with every tool, so one prompt injection reaches everything.
In Formulaite: glassbox.py — GlassBox.save is the checkpoint; max_steps in agent.py and the checks in gates.py are the fault tolerance.
11Evaluate the trajectory, not just the answer ch 19

Agents are probabilistic, so pass/fail tests are not enough. Compare the sequence of steps to an ideal one: exact, in-order or any-order match. Track latency and tokens per call. Use an LLM as a judge with a rubric for subjective qualities. ADK ships evalset files and adk eval.

Picture it: Grading a lab report on the method as well as the final number: did they calibrate the meter first?
class LLMInteractionMonitor:
    def __init__(self):
        self.total_input_tokens = 0
        self.total_output_tokens = 0
    def record_interaction(self, prompt: str, response: str):
        input_tokens = len(prompt.split())     # placeholder for a real tokenizer
        output_tokens = len(response.split())
        self.total_input_tokens += input_tokens
        self.total_output_tokens += output_tokens
    def get_total_tokens(self):
        return self.total_input_tokens, self.total_output_tokens
Plain Python: swap the split() placeholder for the API's usage counts; the book's exact-match accuracy example fails on a paraphrase.
The trap: An exact string match as the metric, so 'Paris is the capital' scores zero against 'The capital is Paris'.
In Formulaite: glassbox.py — GlassBox.replay is the trajectory; an eval set of ten INCI names with the expected tool order lives beside it.
12Prioritisation ch 20

With many possible actions, rank them. Define criteria: urgency, importance, dependencies, resources, cost and benefit. Score each task, pick the next one, and re-rank when something changes. The book's project-manager agent maps 'urgent' to P0 and defaults the rest.

Picture it: A stability failure jumps the queue ahead of a label typo, even though the typo came in first.

13Exploration: generate, debate, evolve ch 21

Some tasks have no known answer. Google's Co-scientist uses a supervisor and specialist agents: generate hypotheses, reflect like a peer reviewer, rank them in an Elo tournament, evolve the best, cluster similar ones, and meta-review. More test-time compute gives better hypotheses. Humans steer it.

Picture it: Brainstorming ten new actives, having a critic shred them, keeping the top three and refining those.
The trap: Trusting a ranked hypothesis without the wet-lab step; the system inherits the model's hallucinations.
In Formulaite: formulaite_tools.py — a candidate-ingredient generator gated by the same run_gates before anything reaches the drawer.
14Composing patterns ch 29

The value is in the mix. The book's research assistant uses Planning to structure, Tool Use to gather, Multi-Agent to split researcher and writer, Reflection with a critic, and Memory to hold state throughout. Each pattern is a separate piece you can test on its own.

Picture it: A finished cream is a recipe of named steps; you can change the emulsifier without touching the preservative.
The trap: Reaching for every pattern at once instead of adding one, measuring, then adding the next.
In Formulaite: agent.py — chain, tool use, reflection via the gate and memory are already composed; routing and evals are the next two boxes.
05 · Cheat sheet

Agentic Design Patterns — cheat sheet

Everything on one sheet.

Vocabulary

TermMeans
patterna named, reusable shape for one recurring agent problem
prompt chainingone focused prompt per step; output of one is input of the next
routingclassify the input, then send it to the right chain, tool or agent
parallelizationrun independent steps at once, then merge
reflectionproduce, critique, refine, repeat, with a stop rule
producer-criticone agent writes, a different agent with its own criteria reviews
tool use / function callingthe model emits a structured call; your code runs the function
planninginvent the ordered steps at run time when the how is unknown
multi-agent collaborationspecialised roles handing work to each other or to a supervisor
session statethe scratchpad dict for one conversation thread
long-term memoryfacts, experiences and rules stored outside the context and searched back in
RAGchunk, embed, retrieve the closest chunks, paste them into the prompt
embeddinga list of numbers that places a text by meaning
MCPan open standard for a server to expose tools that any client can discover
A2A / agent cardagents on any framework talk over HTTP; the card is the JSON identity they publish
guardraila layer that screens input, output, tool calls or behaviour
human-in-the-loopa person reviews, corrects or approves at a defined escalation point
trajectorythe sequence of steps an agent took, compared against an ideal one
LLM-as-a-judgea model scoring another model's output against a written rubric
router agenta first cheap step that decides which model or path a request deserves

The pattern

  1. plan = planner(goal) # Planning: what steps, only if the how is unknown
  2. for step in plan: # Prompt chaining: one focused prompt each
  3. path = route(step) # Routing: tool, model or sub-agent
  4. facts = run_tools(path) # Tool use / RAG: grounded, cited facts
  5. draft = produce(facts, state) # Memory: session state between steps
  6. verdict = critic(draft) # Reflection + guardrail + deterministic gate
  7. if not verdict.ok: retry, fall back or escalate # Exception handling / human in the loop
  8. log trajectory, tokens, verdict # Evaluation and monitoring

Decisions

WhenUseNot
each step needs the previous step's outputprompt chainingparallel branches
steps are independent and wait on APIsparallelization with a merge stepone long sequence
inputs come in several kindsrouting with a default branchone chain that handles everything
quality matters more than speed and costreflection with a separate critica single pass
the how is unknown or changes per requestplanninga fixed workflow
you have a few fixed tools in one appfunction callingan MCP server
agents on different frameworks must cooperateA2A with agent cardsMCP, which is for tools
a mistake is costly or irreversiblehuman-in-the-loop approvalfull autonomy

Rules of thumb

DoDon't
Give each step one focused prompt and pass JSON to the next.One monolithic prompt that summarises, extracts and drafts at once.
Use a separate critic with its own criteria.Let the writer grade its own work with the same prompt.
Use a fixed workflow when the recipe is known.Give a planning agent a job you could write as five lines.
Make tools raise clear errors and tell the agent what to do on failure.Return 'error: not found' as a string the model may read as data.
Update state through tools or events so it is logged and persisted.Edit session.state directly and hope it sticks.
Give each agent the minimum tools and permissions for its task.Hand every tool to every agent.
Layer guardrails: input screen, output check, tool callback, human.Rely on the system prompt alone to stop injection.
Classify first and send simple steps to a cheap model.Run every step on the biggest model you can afford.
Put a max_iterations on every loop and a default branch on every router.Assume the critic will eventually say perfect.
Evaluate the trajectory, tokens and latency, not just the final text.Grade with an exact string match.

Before you ship

  • Every step's output is JSON that a parser or Pydantic model checks before the next step.
  • A critic or deterministic gate reviews every drawer before it leaves the loop.
  • Every loop has a max_iterations and every router has a default branch.
  • Every tool raises on failure and the agent has a logged fallback path.
  • Tool calls pass an allow-list callback; each agent has only the tools it needs.
  • Retrieved chunks carry their source and the prompt says 'if you don't know, say so'.
  • A fixed eval set runs after every prompt change; trajectory, tokens and latency are logged.
  • A human approval step sits before any irreversible or catalogue-writing action.
