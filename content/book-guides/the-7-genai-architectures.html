01Level Inflation ch 1

Level Inflation is an architecture chosen by hype, a framework default or a misread problem statement. It is not a bad decision. It is the absence of a decision procedure, so nobody can argue with it. The architecture layer is the only layer with no eval and no feedback loop, so an over-built system just looks like a working system.

Picture it: A three-role crew that was mostly fed one-line machine alerts. The service name was already in the string, so a dictionary lookup did the job. Nobody had asked what fraction of inputs actually needed the crew.
ROLES: dict[str, str] = {
    "investigator": ("You are an incident investigator. Given an alert, find the root "
                     "cause using the tools provided. Hand off to the remediator ..."),
    "remediator": ("You are a remediation engineer. Given a diagnosis, propose a fix "
                   "and a rollback plan. Hand off to the reviewer."),
    "reviewer": ("You are a staff engineer reviewing a proposed fix. Approve it, or "
                 "hand back to the investigator with what you would need to see."),
}
# What the crew overwhelmingly received:
#   alert: http_5xx_rate > 0.4 for 5m on checkout-api
Nothing in the roles is stupid; the mistake is that nobody counted how many inputs were plain alert lines.
The trap: Justifying a design with capability language ('it handles complex cases') that names no property of the input you can count.
In Formulaite: Before adding a research agent to Formulaite, write down which ingredient requests need it; catalogue_lookup in formulaite_tools.py already answers the known ones.
02The Escalation Ladder ch 2

Eight architectures, Level 0 to Level 7, ordered by cost rather than by containment. Each level adds exactly one capability the level below structurally cannot provide. You do not climb from the bottom; you eliminate from the top with yes-or-no questions about the task. The default outcome is the floor.

Picture it: A price list, not a career ladder. 'We are still on RAG' is like saying 'we are still on the cheap shampoo' - the cheap one may be the right one.
@dataclass(frozen=True)
class Gate:
    """One rung boundary: the question, and the answer that stops the descent here."""
    level: int
    architecture: str
    question: str
    field: str
    stops_when: bool
    climb_when: str          # the receipt that would justify this rung
LADDER: tuple[Gate, ...] = (
    Gate(level=7, architecture="Multi-Agent System",
         question="Has specialization been measured to win on this task?", ...),
Each gate is data: a question, the answer that stops you there, and climb_when - the receipt that would justify the rung above.
The trap: Assuming Level 4 contains Level 2; a tool-using system with no retriever still cannot read a runbook.
In Formulaite: Formulaite has several request types on different rungs: a known INCI is Level 0, a new ingredient is Level 4, and agent.py should not run for both.
03The Floor Test ch 2

Ask: can I write a unit test that fully specifies the correct output for any input? If yes, no model belongs on that path. The test is about the output, not the input source. Code that reads a database or an API can still be on the floor. Run it first, every time, per request type.

Picture it: Routing 'alert: http_5xx_rate > 0.4 on checkout-api' to the payments rota is a dictionary lookup. Asking a model to do it adds latency, spend and a vendor outage to your paging path.
def floor_test(profile: TaskProfile) -> bool | None:
    """The Level 0 diagnostic. True means no model belongs on this path."""
    return profile.output_fully_specifiable

def recommend_rung(profile: TaskProfile) -> Recommendation:
    floor = floor_test(profile)
    if floor is None:
        return _refuse(profile, FLOOR)        # unanswered: stop the design review
    if floor is FLOOR.stops_when:
        return _decide(profile, FLOOR)        # short-circuit: Level 0, done
    for gate in LADDER:                       # then eliminate from the top down
        ...
The Floor Test short-circuits before any ladder question is asked; None means 'not established' and refuses rather than guessing.
The trap: Asking 'is the code deterministic?' instead of 'can I specify the correct output for a hundred real inputs?'.
In Formulaite: gates.py and catalogue_entry in formulaite_tools.py are the floor: pH range, max use level and banned status are lookups, never model calls.
04The Failure Receipt ch 2

To climb a rung you need a receipt: a reproducible input, the actual bad output the lower rung produced, and the name of the missing capability. Not a missing quality. If you sit down to write one and cannot, the finding is that you do not need to climb. An unconvincing receipt is a result, not a formality.

Picture it: Like a returns desk: you need the item and the fault, not 'it felt wrong'. 'The rules cannot read this prose report' is a receipt; 'the rules are not good enough' is not.
@dataclass(frozen=True)
class Recommendation:
    """A rung, the question that decided it, and what would justify the next one."""
    request_type: str
    level: int | None
    architecture: str | None
    decided_by: str          # so the answer can be argued with
    escalate_when: str | None  # the receipt the next rung would need

# Printed receipt, Chapter 3:
#   INC-1042 UNROUTABLE - needs a human because: the report is prose, not an alert line
#   Missing capability: language understanding over an input no test can specify.
escalate_when carries the receipt specification, so every recommendation comes with its own expiry condition.
The trap: Writing 'the answers were not good enough' - that is a prompt or eval problem, not a capability gap.
In Formulaite: Log a failure_receipt event in glassbox.py for each ingredient the catalogue could not fill, with the input and the refusal text; that is what earns the model call.
05Level 0 - Deterministic Code ch 3

Level 0 is the floor, not a rung: rules, thresholds and lookup tables with no model. Its price is that you must enumerate the cases. The one rule that matters is refuse, never default. An else branch that returns a fallback turns 'I do not know' into a confident wrong answer that nothing downstream can detect.

Picture it: The strawman router answered six of six alerts and got one right, flagging none. The honest router routed two and refused four by name - worse coverage, enormously better truthfulness.
def route(incident: Incident) -> RoutingDecision:
    """Route one incident, or refuse. There is no default branch."""
    signal = parse_alert(incident.report)
    if signal is None:
        return _unroutable(incident, "the report is prose, not an alert line")
    service = owner_for(signal.service)
    if service is None:
        return _unroutable(incident, f"no rota owns service {signal.service!r}")
    severity = severity_for(signal, service)
    return RoutingDecision(incident_id=incident.incident_id, rota=service.rota,
        severity=severity, needs_human=False,
        decided_by=f"{signal.metric} > {signal.threshold} on {signal.service}")
Two named refusals and no else; every exit carries decided_by so the page can be argued with at 3am.
The trap: Writing else: return DEFAULT because 'the path must always produce something' - it must produce something honest.
In Formulaite: catalogue_lookup(inci) in formulaite_tools.py should return a named refusal for an unknown INCI, never a guessed entry.
06The Zero Row ch 3

The Zero Row is the measured cost and the measured failure rate of the deterministic version, taken before any model exists. It is the denominator for every later claim. Teams record the cost half and skip the failure half. The failure half is the one that decides whether you climb.

Picture it: Routing took 2.5 microseconds and zero tokens, and refused four of six incidents. 'Level 0 handles a third of reports' justifies a specific escalation; 'our rules are not good enough' justifies anything.
@register_rung("Level 0: Deterministic Code")
def run(incident: Incident) -> CostLedger:
    """Rung entry point. Measured, so the Zero Row is measured rather than assumed."""
    ledger = CostLedger()

    @measured("rules.route", ledger)
    def _run_once() -> RoutingDecision:
        return route(incident)

    _run_once()
    return ledger      # zero model calls, zero tokens - recorded, not hard-coded
The same @measured decorator prices every rung, so the baseline and the model rows are comparable.
The trap: Never computing the baseline, so 'the model made it better' has no denominator.
In Formulaite: Record in glassbox.py how many drawers the catalogue fills with zero model calls, and how many it refuses; that is Formulaite's Zero Row.
07Level 1 - The Prompt Application ch 4

One model call, structured output, no external state. It adds language understanding over input you already have, and nothing else. The schema is the architecture and the prompt is configuration. Put the contract in a type the API enforces, and the string-parsing repair layer disappears.

Picture it: A prose incident report says 'their card was charged but the order page spun forever'. No regex maps that to payment-gateway; one typed call does, in four seconds.
class Classification(BaseModel):
    """What one model call is allowed to return."""
    service: Literal["checkout-api", "payment-gateway",
                     "notification-worker", "search-api", "unknown"]
    severity: Literal["SEV1", "SEV2", "SEV3"]
    summary: str
    evidence: str          # a verbatim quote, checked by code
    needs_human: bool      # the escape hatch: an enum with no way out is a default branch

def triage(incident: Incident, completer: Completer) -> RoutingDecision:
    """Classify a report and turn the result into a page, or refuse."""
    return decide(incident, classify(incident, completer))
Closed enums plus an 'unknown' member; classify (model-facing) and decide (routing) stay separate functions.
The trap: Keeping the contract in the prompt and parsing free text, then adding retries and repair prompts for six weeks.
In Formulaite: drawer.py's as_tool_schema and fill_drawer in formulaite_tools.py are this rung: one typed call that fills the drawer from a supplier page.
08The Format Illusion ch 4

A validated response is not a verified response. A schema validates the shape of the output and never its truth. Only enums are enforced while tokens are generated; lengths, ranges and patterns are demoted to descriptions and enforced by raising after you paid. The tighter the schema, the stronger the illusion.

Picture it: Two of four severities came back wrong while every response validated, quoted real evidence and set needs_human=False. The parse-rate dashboard stayed green.
class Draft(BaseModel):
    severity: Literal["SEV1", "SEV2", "SEV3"]
    summary: str = Field(max_length=200)
    confidence: float = Field(ge=0.0, le=1.0)

# What the SDK actually transmits - your caps became sentences:
#   "summary":    {"type": "string", "description": "{maxLength: 200}"}
#   "confidence": {"type": "number", "description": "{maximum: 1.0, minimum: 0.0}"}
# Only the enum is enforced during generation. Pydantic raises later,
# after the tokens are billed.
Print the transmitted schema once in a test; put real constraints in enums and verify everything else yourself.
The trap: Adding a confidence field - it is generated by the same process as the answer and is not a probability.
In Formulaite: gates.py exists because a drawer that validates is not a drawer that is true; the gate compares the drawer against the catalogue entry.
09The verbatim evidence quote ch 4

Ask the model for something checkable instead of something self-reported. Require a quote copied character for character from the input, then check it with two lines of ordinary code. Invention becomes a hard fail rather than a score. It catches made-up evidence; it does not catch a real quote reasoned about wrongly.

Picture it: A page arrives at 3am with the sentence that caused it attached. The on-call can read it and disagree. A confidence of 0.95 gives them nothing to disagree with.
def _normalized(text: str) -> str:
    return " ".join(text.split()).casefold()

def evidence_supported(claim: Classification, incident: Incident) -> bool:
    """Is the model's quote actually in the report?"""
    quote = _normalized(claim.evidence)
    return bool(quote) and quote in _normalized(incident.report)

# in classify(): a declared refusal is honoured first, then the quote is checked
if not evidence_supported(claim, incident):
    return _unknown(f"quoted evidence not in the report: {claim.evidence!r}")
Whitespace and case are forgiven, nothing else; the check runs before anything is paged and costs nothing.
The trap: Checking the quote before honouring needs_human, which files every honest refusal under 'invented evidence'.
In Formulaite: Add an evidence field per drawer section in drawer.py and a check in gates.py that the quote appears in the supplier page text the tool returned.
10The Completer seam ch 4

Every model call goes through one narrow Protocol. A rung asks for typed output and gets back either the parsed object or a failure string, never an SDK exception. A recorded implementation replays committed responses, keyed on a hash of the exact prompt. Tests run with no key, and a prompt edit turns them red on purpose.

Picture it: One door to the vendor. Metering, tracing and replay all wrap that door, and none of the eight rungs knows they exist.
@dataclass(frozen=True)
class Completion(Generic[T]):
    """One call's typed result, its bill, and why it failed if it did."""
    parsed: T | None
    usage: Usage
    failed: str | None = None

class Completer(Protocol):
    """What a rung is allowed to ask a model for. Deliberately narrow."""
    def parse(self, *, system: str, user: str, schema: type[T],
              effort: str = "low") -> Completion[T]: ...
# RecordedCompleter replays by prompt_key = sha256(system + user)[:12]
No exceptions in the contract; every vendor failure is translated once into the failed field, so nothing above catches SDK errors.
The trap: Keying the fake on the incident id, so tests stay green after the prompt that production depends on has changed.
In Formulaite: models.py's ModelClient Protocol with ScriptedModel (offline) and ClaudeModel (online) is Formulaite's Completer seam.

01Level 2 - Retrieval with a relevance floor ch 5

RAG adds facts that are in neither the request nor the model. It has two quality surfaces, retrieval and generation, and the retrieval one fails silently. A top_k with no floor always returns k passages, so it cannot say 'nothing here' - it is the default branch relocated into a ranking function. Set the floor above the best score of queries the corpus cannot answer.

Picture it: A question about a leaking coffee machine scored 3.80 against the escalation policy on the word 'floor'. FLOOR = 6.0 sits above that whole band and refused six of six off-topic queries at no cost in recall.
def search(index: Index, query: str, *, limit: int = LIMIT,
           floor: float = FLOOR) -> tuple[Hit, ...]:
    query_terms = terms(query)
    hits: list[Hit] = []
    for position, passage in enumerate(index.passages):
        score = _bm25(index, position, query_terms)
        if score < floor:
            continue                    # a limit says how many; a floor says whether any
        hits.append(Hit(passage, score, ...))
    hits.sort(key=lambda hit: (-hit.score, hit.passage.passage_id))
    return tuple(hits[:limit])          # empty tuple = "this corpus does not answer that"
The empty tuple is the load-bearing return value; no passages means no model call is made at all.
The trap: Splitting two-hundred-word runbooks on headings: the symptom chunk matches the query and the fix chunk holds the answer.
In Formulaite: Supplier pages retrieved in formulaite_tools.py need a floor: an ingredient the page set does not cover must refuse, not send three irrelevant pages to the model.
02The Substitution Test ch 5

One run that locates a fault in a retrieval system. Hand the generator the documents you know are correct and rerun. If the answer becomes right, retrieval is broken. If it stays wrong, generation is broken. No labels, no judge. Substitute the query instead of the documents and it proves whether a better query could have reached the corpus.

Picture it: Like swapping in a known-good battery to see if the torch or the battery is dead - one swap, one answer, before you spend a week on the wrong half.
The trap: Spending a week tuning prompts against a retrieval fault because the prompt is the half that feels adjustable.
In Formulaite: When a drawer is wrong, feed the model the correct supplier page by hand through read_supplier_page's stub and rerun; if the drawer is fixed, the page selection was at fault.
03Level 3 - The LLM Workflow ch 6

Several model calls in a sequence you control and can draw before the run starts. Run the Floor Test on every stage, not once on the system: three of five stages here are plain code and cost 0.2 milliseconds. The capability the rung adds is a stage whose input is an earlier stage's output - in this book it is an f-string.

Picture it: classify, extract, retrieve, draft, route. The extract stage that fixes the unsolvable incident is one line: prepend the classified service name to the report before searching.
STAGES: tuple[tuple[str, StageKind], ...] = (
    ("classify", "model"),
    ("extract", "code"),
    ("retrieve", "code"),
    ("draft", "model"),
    ("route", "code"),
)

def extract(claim: Classification, incident: Incident) -> str:
    return f"{claim.service} {incident.report}"   # the whole capability, no model
# A model-written query scored 0.75 against this f-string's 1.00 and cost a call.
If you can enumerate the stages at import time you can draw them; a branch whose arms are written in the source is still Level 3.
The trap: Replacing the report with the classification as the query: a summary is lossy and it broke another incident.
In Formulaite: Formulaite's research is drawable: catalogue_lookup, then read_supplier_page, then fill_drawer, then run_gates - agent.py could be a fixed pipeline for most ingredients.
04The Downstream Veto ch 6

A later stage that receives an earlier stage's output as a claim, and can see the original input, can overrule it. That is why a well-built pipeline scores its worst stage, not the product of all stages. The structural prerequisite is the report re-sent at every stage; the prompt sentence 'this may be wrong' turned out to do nothing on its own.

Picture it: Stage 1 said checkout-api. Stage 4 read the passages against the report and corrected it to payment-gateway. Drop the report from stage 4's prompt and it can no longer disagree with anything.
DRAFT_SYSTEM = """You triage production incident reports for an on-call rota ...
An earlier stage has already classified this report. Its classification is
given to you, and IT MAY BE WRONG. ...
- Judge the passages against the REPORT, not against the classification."""

def build_user(incident, claim, hits) -> str:
    return ("Retrieved passages:\n\n" f"{context_block(hits)}\n\n"
            "An earlier stage classified this report as:\n"
            f"  service: {claim.service}\n  severity: {claim.severity}\n\n"
            "Classify the incident report between the markers ...\n\n"
            f"<report>\n{incident.report}\n</report>")   # the original, every time

    for module, level in RUNG_LEVEL.items():
        for imported in imports_of(module):          # parsed with ast, never imported
            if RUNG_LEVEL.get(imported, -1) > level:
                edges.append((module, imported))
    return tuple(edges)

The four seams that paid - result contract, call seam, capability menu, execution seam - were adopted for correctness, testability, security and reversibility, never for extensibility.
The trap: Widening a seam by replacing a type-enforced rule with a list somebody maintains.

13The Removal Receipt ch 16

Climbing needs one case; removal is a universal claim about traffic you have not seen. Four clauses authorize a descent. State the population before you read the counter. Show a decision counter that read zero across it. State the smallest effect that population could detect. Take a first step that can be undone without a deploy. Unroute first, then let the shortened ladder produce the evidence.

Vocabulary

Removal ReceiptStated population, a counter at zero, the smallest detectable effect, and an undoable first step.

Format IllusionBelieving a validated response is a verified one; a schema checks shape, never truth.
Downstream VetoA later stage shown the original input can overrule an earlier stage's claim.
Blame SinkThe reporting stage is the last one able to detect a fault, not the one that caused it; record origin too.
Blast Radius SchemaWhat a system can cause is a property of its tool schemas, computable before any tool is written.

Context RatchetState inside a run only accumulates; what you carry sets the cost slope and hardens early mistakes.
Refusal PremiumAt an unbounded rung failures run longest, so cost runs inversely to value.
unreachableThe give-up field that lets an agent say 'never', read before the evidence check.

Refusal CascadeTry the cheapest rung and climb on a refusal, only where the failed attempt is free.
Effective LevelThe rung whose single-rung cost equals your mean cost per request, read off the cost curve.
Scoring SurfaceA place a claim can be wrong independently of the answer; the count is the eval difficulty.
Instrumentation LevelThe highest contiguous rung whose failures your record alone can localize.

The pattern

  1. Pick ONE request type. Run the Floor Test: if a test can specify the output, no model.
  2. Eliminate from Level 7 down with yes-or-no questions about the task; refuse if any answer is unknown.
  3. Build the lowest rung nothing forced you past; every exit refuses by name, never defaults.
  4. Measure cost and refusal rate on the same columns as the Zero Row.
  5. Write the Failure Receipt: input, actual output, missing capability. No receipt, no climb.
  6. Climb one rung; keep the cheap path alive as code and route in front of mixed rungs.
  7. Descend only with a Removal Receipt: state the population, unroute first, unbuild later.

A rate, not an assertion

@dataclass(frozen=True)
class Rate:
    passes: int
    n: int
    @property
    def interval(self) -> tuple[float, float]:   # Wilson, 95 percent
        if not self.n:
            return (0.0, 1.0)                    # no samples = no information
        z = NormalDist().inv_cdf(0.975); p, n = self.passes / self.n, self.n
        centre = (p + z * z / (2 * n)) / (1 + z * z / n)
        spread = z * ((p * (1 - p) / n + z * z / (4 * n * n)) ** 0.5) / (1 + z * z / n)
        return (max(0.0, centre - spread), min(1.0, centre + spread))

Before you ship

  • Every request type has a written rung and the question that decided it; none is justified by capability language.
  • The Zero Row is measured: cost and refusal rate of the deterministic path, with a counter per refusal reason.
  • Every exit refuses by name; no default branch, no top_k without a floor, no enum without an unknown member.
  • Every model claim carries a verbatim quote or value that code checks against the input or a tool result.
  • Every tool has consequence set, the default menu's blast radius is asserted empty, and no tool takes a timestamp.
  • The loop has an unreachable field read before the evidence gate, three named bounds, and a journal entry per run.
  • Rates are reported with intervals and n; refusals and unmeasured cases return None, never zero.
  • The cheap path still exists as code, no rung imports a rung above it, and the last-rung counter has an N chosen in advance.
