01One call to the Messages API ch 1

Everything in the book starts with one request to a hosted model. You send a list of messages and read back a list of content blocks. The reply text sits in response.content[0].text. The wording varies on every run, and that is normal.

Picture it: Like phoning a knowledgeable supplier rep: you ask one question, they answer in their own words, and you write down what they said.
import os
from anthropic import Anthropic
from dotenv import load_dotenv
load_dotenv()
client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=300,
    messages=[{"role": "user", "content": "Suggest one cold coffee drink for a hot afternoon."}],
)
print(response.content[0].text)
content is a list of blocks, so [0].text reads the first one; the key comes from .env, never from the file.
The trap: Pasting the API key into the script; keep it in .env with chmod 600 and a .gitignore line.
In Formulaite: models.py: ClaudeModel.complete() wraps exactly this call so agent.py never touches the SDK directly.
02stop_reason and usage ch 1

The response carries more than text. stop_reason says why the model stopped: end_turn, max_tokens, stop_sequence, or later tool_use. usage holds input and output tokens, which drive cost and latency. Record both on every call.

Picture it: A delivery note tells you not just what arrived but whether the order was complete and what it weighed.
print(response.model)
print(response.stop_reason)
print(response.usage.input_tokens, response.usage.output_tokens)
# claude-sonnet-5
# end_turn
# 19 42
max_tokens in stop_reason means the reply was cut short; check it before trusting the output.
The trap: Trusting a truncated reply because it parsed; a stop_reason of max_tokens means half a sentence went to the customer.
In Formulaite: glassbox.py: every model reply is logged as an Event with its stop reason and token counts so a run can be replayed.
03Standing instructions live in system ch 2

The system parameter carries what is true for every conversation: who the assistant is, its tone, its limits and its fallback. A user message carries only this moment's question. The model weighs the two differently, so keep them apart.

Picture it: The lab's standard operating procedure is pinned to the wall; the day's batch sheet is the message.
SHOP_BRIEF = (
    "We are the assistant for Daily Grind, a neighbourhood coffee shop. "
    "Every reply stays short, warm, and practical, and never exceeds three sentences. "
    "When a customer asks for something we do not serve, we say so plainly "
    "and offer the closest match from our own menu. "
    "We never invent a product, a price, or an ingredient."
)
response = client.messages.create(
    model=MODEL, max_tokens=300, system=SHOP_BRIEF,
    messages=[{"role": "user", "content": question}],
)
The brief names what to do when unsure (offer the closest match); a brief with no stated limits invites invention.
The trap: Stuffing one customer's details into system, or leaving out the boundaries so the model improvises confidently.
In Formulaite: agent.py: the Agent's system brief tells the model it must fill the Ingredient Drawer and must not invent an INCI name or a use level.
04The API remembers nothing ch 2

Each request is complete in itself. The service keeps no memory between calls. To hold a conversation you resend the whole history every time, as user and assistant turns that alternate. That costs tokens but gives total control over what the model sees.

Picture it: A pen-friend with amnesia: every letter must quote the earlier letters, or they have no idea what you are talking about.
messages = [
    {"role": "user", "content": "What do you have that is cold?"},
    {"role": "assistant", "content": "Our cold brew and iced americano both work well."},
    {"role": "user", "content": "Which of those carries less caffeine?"},
]
Roles alternate user, assistant, user; the model reads the whole list and continues it.
The trap: Sending only the latest question and wondering why 'which of those' gets a confused answer.
In Formulaite: memory.py: Conversation keeps that list well-formed, with tool results always inside a user turn, so agent.py resends it on every step.
05Tokens and the context window ch 2

A token is a chunk of characters, about four letters of English. Billing is per token, input and output priced separately. The context window is the token ceiling for one request: system, history and reply together. count_tokens measures a prompt for free before you send it.

Picture it: A shipping crate: every item you pack has a weight, you pay by weight, and the crate has a fixed limit.
estimate = client.messages.count_tokens(
    model=MODEL,
    system=SHOP_BRIEF,
    messages=messages,
)
print(estimate.input_tokens)   # 47
The count includes role markers and the system brief, which is why a short question measures longer than it looks.
The trap: Never measuring, so a prompt silently doubles and the surprise arrives on the invoice.
In Formulaite: memory.py: Conversation.token_estimate() (len(text) // 4) is the cheap budget signal the lab reads before each step.
06Temperature ch 2

Temperature controls how adventurously the model picks the next token. At 0.0 it takes the most likely option every time, so the same input gives the same output. Use 0.0 for anything a program will parse. Use around 0.7 for wording that should feel fresh.

Picture it: A recipe followed by the book versus a chef improvising; you want the book when the batch must be reproducible.
response = client.messages.create(
    model=MODEL,
    max_tokens=300,
    temperature=0.0,
    system=SHOP_BRIEF,
    messages=[{"role": "user", "content": "List our three most popular hot drinks."}],
)
print(response.content[0].text)
Run it twice and get the same wording; leave top_p at its default and change only one knob.
The trap: Extracting structured data at a warm temperature and then blaming the parser for random failures.
In Formulaite: models.py: ClaudeModel calls at temperature 0 because the drawer is data another program reads, not prose.
07Prefilled assistant turn ch 2

You may end the message list with an assistant turn you wrote yourself. The model continues from there as if the words were its own. A prefill of '1.' forces a list. A prefill of '{' forces JSON with no polite preamble.

Picture it: Handing someone a form with the first box already filled in; they carry on in the same format.
response = client.messages.create(
    model=MODEL, max_tokens=200, temperature=0.0, system=SHOP_BRIEF,
    messages=[
        {"role": "user", "content": "List three iced drinks from our menu."},
        {"role": "assistant", "content": "1."},
    ],
)
print("1." + response.content[0].text)
Your code must prepend the prefill again before parsing, because the reply starts after it.
The trap: Forgetting to add the '{' back before json.loads, so every reply fails to parse.
In Formulaite: formulaite_tools.py: fill_drawer uses tool use instead of a '{' prefill, but the idea is the same: force the shape, do not ask nicely for it.
08Retry with exponential backoff ch 2

Four failures cover almost everything: rate limit 429, overloaded 529, a network fault, and a malformed request 400. The first three clear with a wait. The last never will. Retry only the temporary ones, waiting longer each time plus a little random jitter.

Picture it: A busy supplier phone line: call back after 1, 2, 4 minutes rather than redialling instantly, and do not redial at all if you dialled a wrong number.
import random, time
import anthropic

def ask(messages, attempts=4, **options):
    for attempt in range(attempts):
        try:
            return call_model(messages, **options)
        except (anthropic.RateLimitError, anthropic.APIStatusError):
            if attempt == attempts - 1:
                raise
            time.sleep((2 ** attempt) + random.random())
**options forwards temperature and max_tokens without repeating them at every layer; the jitter stops many clients retrying in unison.
The trap: One broad except that retries a 400 four times, wasting quota on a request that will fail forever.
In Formulaite: models.py: ClaudeModel.complete() is where the backoff belongs, so a busy API slows the research run instead of killing it.
09Four parts of a prompt ch 3

A prompt that behaves carries four parts: role, context, task, constraints. Most bad replies trace to a missing part, not a weak model. Invented prices mean context was missing. Rambling means the constraint was missing. Put constraints last, where they land hardest.

Picture it: A lab work order: who you are, the raw materials on the bench, the one job, and the safety limits written at the bottom.
RECOMMENDATION = """A customer at Daily Grind has asked the following.
{question}
Our current menu is below.
{menu}
We reply in at most three sentences.
We name the price of anything we suggest.
We recommend only products that appear on the menu above.
"""
Question, then context, then the constraints at the very end; a number (three sentences) beats an adjective (brief).
The trap: Burying the format rule between two long blocks and concluding the model ignores instructions.
In Formulaite: agent.py: the system brief plus the catalogue entry plus the drawer schema are exactly role, context, task and constraints.
10Few-shot turns ch 3

A demonstration teaches tone, length and edge cases in two lines where a description takes a paragraph. Examples travel as ordinary user and assistant turns placed before the real question. Two or three are enough. One refusal example teaches more than three happy ones.

Picture it: Showing a new formulator one filled-in ingredient card beats a page of instructions about how cards should look.
FEW_SHOT = [
    {"role": "user", "content": "Something warm but not too milky."},
    {"role": "assistant", "content": "A flat white keeps the milk light at 3.40. Our filter coffee at 2.60 is lighter still."},
    {"role": "user", "content": "Do you sell bubble tea?"},
    {"role": "assistant", "content": "We do not serve bubble tea. Our iced latte at 3.80 is the closest sweet cold option."},
]

def recommend(question):
    messages = FEW_SHOT + [{"role": "user", "content": question}]
    return ask(messages, temperature=0.3)
The second pair carries most of the value: it shows how to refuse briefly and offer an alternative.
The trap: Adding ten examples; beyond five they rarely help and every one costs tokens on every call.
In Formulaite: agent.py: one example drawer for a known ingredient, shown as a prior turn, teaches the model the drawer's register.
11Prompt templates with a version ch 3

Small wording changes cause real behaviour changes, so prompts are source code. Keep them in one module with named placeholders. Give each template a version constant and keep the old wording. Log the version with every reply so a change in quality points at an edit.

Picture it: Formula revisions: you never overwrite v2 with v3, you keep both so you can see what changed when a batch goes wrong.
PROMPT_VERSION = "recommendation-v2"

RECOMMENDATION_V1 = """A customer at Daily Grind has asked the following.
{question}
We reply briefly and helpfully.
"""

def render(template, **values):
    return template.format(**values)
v1 sits above v2 in the file; the difference (no menu, no limit) explains the invented prices it produced.
The trap: Editing a prompt in place on Friday and having no idea on Monday which words changed.
In Formulaite: glassbox.py: log the prompt version on every run so a Glass Box trace can be compared across prompt edits.
12Pydantic schema as one source of truth ch 4

Valid JSON is not correct JSON. A renamed key, a quantity spelled as a word, or an invented milk all pass json.loads. A Pydantic class states the shape once: names, types, allowed values, defaults. Enums inheriting from str name every permitted option. model_json_schema() turns the class into the prompt text.

Picture it: A batch record template with fixed fields and drop-down options; you cannot write 'venti' in a box that only accepts small, regular, large.
from enum import Enum
from pydantic import BaseModel, Field
class Milk(str, Enum):
    whole = "whole"
    oat = "oat"
    soy = "soy"
    none = "none"
class Order(BaseModel):
    drink: str = Field(description="The drink name exactly as written on the menu")
    milk: Milk = Milk.whole
    quantity: int = Field(default=1, ge=1, le=20)
SCHEMA_BLOCK = json.dumps(Order.model_json_schema(), indent=2)
Field descriptions double as prompt text; ge/le stop a four-hundred-coffee order; the enum rejects 'almond'.
The trap: Checking only that the braces matched and finding the renamed key three functions downstream.
In Formulaite: drawer.py: IngredientDrawer is the schema; as_tool_schema() plays the role of model_json_schema() and gates.py validates against it.
13Feed the validation error back ch 4

A failed validation names the field and the reason. Do not throw that away and retry blindly. Append the bad reply and the error as new turns and ask again. Three attempts, then raise so the caller decides. Most corrections succeed on the second try.

Picture it: Returning a form with the wrong box circled in red, rather than silently handing over a blank one.
from pydantic import ValidationError
def extract_order(sentence, attempts=3):
    messages = [{"role": "user", "content": sentence}]
    for attempt in range(attempts):
        raw = "{" + call_model(messages + [{"role": "assistant", "content": "{"}],
                               temperature=0.0, system=ORDER_INSTRUCTIONS)
        try:
            return Order.model_validate_json(raw)
        except (ValidationError, json.JSONDecodeError) as error:
            messages.append({"role": "assistant", "content": raw})
            messages.append({"role": "user", "content": f"That reply failed validation.\n\n{error}\n\nWe return corrected JSON only."})
    raise ValueError("The order could not be validated after three attempts.")
The error text becomes the next user turn; a failure surviving three corrections is a prompt problem, not bad luck.
The trap: Retrying with the same prompt and no error report, then giving up after the same mistake three times.
In Formulaite: agent.py: a FAIL verdict from gates.py goes back to the model as a tool_result with the reasons; this is the evaluator-optimizer loop.
14A Conversation object owns the history ch 4

Memory is bookkeeping, not intelligence. One small class holds the customer id, the system brief and the message list. reply() appends the question, calls the model, appends the answer. The rest of the code never touches a raw list again. Trimming and saving attach to the same object.

Picture it: One project folder per client that every colleague adds to, instead of loose notes on five desks.
class Conversation:
    def __init__(self, customer_id, system=SHOP_BRIEF):
        self.customer_id = customer_id
        self.system = system
        self.messages = []
    def add_user(self, content):
        self.messages.append({"role": "user", "content": content})
    def reply(self, question, temperature=0.3):
        self.add_user(question)
        result = ask(self.messages, temperature=temperature, system=self.system)
        self.messages.append({"role": "assistant", "content": result})
        return result
trim() drops the oldest pair while over budget; compact() summarises older turns, keeping any stated allergy; save() and load() persist one JSON per customer.
The trap: Trimming from the front and losing the allergy the customer stated in turn one.
In Formulaite: memory.py: Conversation is this class for the agent loop, with add_user, add_assistant, add_tool_results and as_api().

01DSPy: declare the task, compile the prompt ch 5

A hand-tuned prompt hides which word fixed which case. DSPy separates what a task takes in and returns (a Signature) from how it is phrased. A Module wraps the signature with a strategy such as ChainOfThought. An optimizer then searches for wording and examples that score well on a metric you wrote, and saves the compiled prompt to disk.

Picture it: You write the spec for a label; a copywriter tries thirty drafts and keeps the ones your checklist passes.
import dspy
class Recommend(dspy.Signature):
    """Recommend one drink from the Daily Grind menu."""
    menu: str = dspy.InputField(desc="The shop menu with prices")
    question: str = dspy.InputField(desc="What the customer asked for")
    suggestion: str = dspy.OutputField(desc="At most three sentences, naming the price")
def grounded(example, prediction, trace=None):
    reply = prediction.suggestion.lower()
    return any(item in reply for item in MENU_ITEMS) and reply.count(".") <= 3
optimizer = BootstrapFewShot(metric=grounded, max_bootstrapped_demos=4)
tuned = optimizer.compile(ShopAssistant(), trainset=trainset)
tuned.save("tuned_assistant.json")
Held-out score went from 62.5 to 93.8 with no change to the model; only the prompt changed. Compile in the release step, not at start-up.
The trap: Compiling a task with no mechanical metric (seasonal marketing copy); whatever you cannot score, a machine cannot optimise.
In Formulaite: gates.py: the gate checks are already a mechanical metric, so a drawer-filling prompt could be compiled against them later.
02Embedding: meaning as position ch 6

An embedding is a list of numbers that stands for meaning. Phrases with similar meaning land close together even with no shared words. Cosine similarity compares direction, so a six-word question compares fairly with a forty-word description. Embedding calls are cheap; generation calls are not.

Picture it: Ingredients arranged on a shelf by function: two emollients sit together even if their INCI names look nothing alike.
import numpy as np
import voyageai
vo = voyageai.Client(api_key=os.environ["VOYAGE_API_KEY"])
def embed_documents(passages):
    return vo.embed(passages, model="voyage-3", input_type="document").embeddings
def embed_query(question):
    return vo.embed([question], model="voyage-3", input_type="query").embeddings[0]
def cosine(first, second):
    first, second = np.array(first), np.array(second)
    return float(np.dot(first, second) / (np.linalg.norm(first) * np.linalg.norm(second)))
input_type differs for storing versus searching; a ranking always returns something, so treat a top score below about 0.3 as 'nothing relevant'.
The trap: Trusting the top hit for 'parking' because it is the top hit; ranking has no idea of relevance in the absolute.
In Formulaite: formulaite_tools.py: catalogue_lookup is exact today; a vector index over supplier pages would let read_supplier_page find passages by meaning.
03A vector collection with upsert ch 6

An in-memory list works for three products and fails for three thousand. A collection stores each vector with its wording, an id and metadata. upsert inserts what is new and replaces what changed, so running it twice is safe. The library returns distance, where smaller is closer.

Picture it: A card index where every card has a fixed number: refiling a corrected card replaces the old one instead of adding a duplicate.
import chromadb
chroma = chromadb.PersistentClient(path="vectors")
collection = chroma.get_or_create_collection("menu")

def index_products():
    passages = [describe(product) for product in PRODUCTS]
    collection.upsert(
        ids=[product["id"] for product in PRODUCTS],
        documents=passages,
        embeddings=embed_documents(passages),
        metadatas=[{"name": p["name"], "price": p["price"]} for p in PRODUCTS],
    )
Stable ids make reindexing idempotent; metadata lets you filter before the vector comparison for free.
The trap: Mixing the two conventions: cosine similarity (bigger is closer) and Chroma distance (smaller is closer) gives inverted rankings.
In Formulaite: formulaite_tools.py: the catalogue is a dict loaded from data/catalogue.json today; a collection is its natural next home.
04Grounded prompt with a named fallback ch 7

RAG is three steps: retrieve passages, format them as context, generate from that context only. The prompt must do three jobs: supply the material, forbid anything outside it, and say what to do when the material falls short. Leave out the fallback and the model invents one.

Picture it: A reference librarian who answers only from the books on the desk, and says 'let me fetch a colleague' when the desk has nothing.
GROUNDED_REPLY = """A customer at Daily Grind has asked the following.
{question}
The shop records below are the only material we may use.
{context}
We reply in at most three sentences.
We use only what these records state, and we cite the number of any record we rely on.
When the records do not cover the question, we say so plainly and offer to fetch a colleague.
We never guess a price, an ingredient, or an opening time.
"""
Question above, context in the middle, constraints last; temperature 0 because a grounded reply should repeat the records, not vary.
The trap: Retrieving the right passage and then losing to the model's general knowledge because the wording was soft.

05Numbered citations ch 7

def format_context(items):
    return "\n\n".join(
        f"[{position + 1}] {item['source']}. {item['passage']}"

06Distance threshold before the model ch 7

A ranking always fills the requested slots, so weak matches appear when strong ones run out. Drop anything beyond a distance limit before building the prompt. If nothing survives, refuse before spending a token. Tune the threshold first; treat the count (3 to 5) as a ceiling.

Picture it: A sieve before the mixer: if nothing passes the mesh, you do not start the batch.
DISTANCE_LIMIT = 0.75

def respond(question, n_results=4):
    items = [item for item in retrieve(question, n_results=n_results)
             if item["distance"] <= DISTANCE_LIMIT]
    if not items:
        return "We do not have that in our records, though a colleague at the counter can help."
    prompt = render(GROUNDED_REPLY, question=question, context=format_context(items))

07Clean, then chunk by paragraph ch 8

Loaders leave four kinds of damage: non-breaking spaces, hyphenated line breaks, blank-line runs, repeated spaces. Repair those and nothing else; do not lowercase or strip punctuation. Then split on paragraph boundaries with a character ceiling (900) and about 15% overlap so a fact spanning a boundary survives.

Picture it: Cutting a supplier data sheet along its own section headings, not every ten centimetres with a ruler.
def chunk_by_paragraph(content, max_chars=900, overlap=150):
    blocks = [block.strip() for block in content.split("\n\n") if block.strip()]
    chunks, current = [], ""
    for block in blocks:
        if current and len(current) + len(block) + 2 > max_chars:
            chunks.append(current)
            current = current[-overlap:] if overlap else ""
        current = f"{current}\n\n{block}".strip()
    if current:
        chunks.append(current)
    return chunks
The ceiling is a limit not a target: a 200-character policy stays whole. Carry the nearest heading into each chunk for cheap context.
The trap: Chunking at a fixed 500 characters and embedding one vector for four unrelated subjects.
In Formulaite: formulaite_tools.py: read_supplier_page returns raw page text; a clean-and-chunk step is what turns it into passages a drawer can cite.
08Fingerprint refresh: embed only what changed ch 8

Re-embedding everything on every run is simple and wasteful. Hash each passage's wording and store the hash in metadata. Next run, embed only passages whose hash differs. Delete ids that vanished from the sources; that is the step everybody forgets. The whole refresh is one idempotent command.

Picture it: Checking a stock list against last week's: reorder only what changed and remove the lines for discontinued items.
import hashlib
def fingerprint(content):
    return hashlib.sha256(content.encode("utf-8")).hexdigest()[:16]

def sync(passages):
    stored = collection.get(include=["metadatas"])
    known = {entry: meta.get("fingerprint")
             for entry, meta in zip(stored["ids"], stored["metadatas"])}
    incoming = {row["id"]: {**row, "fingerprint": fingerprint(row["content"])} for row in passages}
    changed = [row for key, row in incoming.items() if known.get(key) != row["fingerprint"]]
    removed = [key for key in known if key not in incoming]
    return changed, removed
Stable ids like 'handbook::3' mean an edit at the end re-embeds only the tail. A second run prints 'embedded 0, removed 0'.
The trap: Withdrawing a product from the menu but leaving its vector, so the assistant keeps recommending it.
In Formulaite: formulaite_tools.py: the local pages under data/pages are the sources; a fingerprint sync keeps a supplier index fresh without re-reading every page.

11The agent loop ch 11

An agent is a loop. Call the model with the tool list. If stop_reason is not tool_use, return the text. Otherwise append the assistant content, run each tool_use block, append a user turn of tool_result blocks keyed by tool_use_id, and go round again. Fifteen lines. Your code never decides which tool runs or in what order.

Picture it: A junior researcher who keeps coming back to your desk: 'I need the catalogue', 'now I need the supplier page', until they hand in the finished card.
def act(question, max_steps=5):
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        response = client.messages.create(model=MODEL, max_tokens=600, temperature=0.0,
                                          system=SHOP_BRIEF, tools=TOOLS, messages=messages)

01Three limits on every agent ch 11

Flexibility and unpredictability arrive together, so every agent gets three limits. A step ceiling: five is plenty, more means confusion. Picture it: A trainee with a five-call budget, a timesheet, and a list of which instruments they may touch.
def run_tool(name, arguments):
    handler = HANDLERS.get(name)
    if handler is None:
        return f"No tool called {name} exists. Available tools are {', '.join(HANDLERS)}."
    try:
        return handler(**arguments)
    except TypeError as error:
        return f"The arguments were wrong for {name}. {error}"

02A confirmation ticket for write tools ch 11

Read tools run freely. A tool that spends money or changes records must never fire from the model's wording alone. The write tool prepares the action and returns a ticket. A separate function performs it only when handed that exact ticket. pop() makes the ticket single-use, so a duplicate confirmation refuses.

Picture it: A purchase order the buyer signs: the assistant drafts it, a human signs it, and a signed order cannot be paid twice.
import uuid
PENDING = {}
def prepare_order(drink, quantity):
    ticket = str(uuid.uuid4())[:8]
    PENDING[ticket] = {"drink": drink, "quantity": quantity}
    return f"Ready to place {quantity} x {drink}. Confirm with ticket {ticket}."

def confirm_order(ticket):
    order = PENDING.pop(ticket, None)
    if order is None:
        return "That ticket is unknown or already used."
    return f"Placed {order['quantity']} x {order['drink']}."
Not a phrase the model can produce triggers confirm_order on its own; the pop makes a network retry harmless.
The trap: Mixing read and write tools on day one and trying to retrofit the split once twenty tools exist across three apps.
In Formulaite: gates.py: a drawer is only written into the app after run_gates() returns PASS; a human-confirmed ticket would guard the final save-to-catalogue step.

05An eval case ch 12

Three questions typed by the prompt's author is the worst sampling method there is. A case carries the input, a category, must_contain phrases, must_avoid phrases and the expected source. blocking=True marks the cases that stop a release outright, such as allergens. Picture it: A stability panel: fixed samples tested the same way every time, so a drift shows up as a number rather than a feeling.

06Rules first, judge second ch 12

Score with rules wherever a rule can reach: required phrases present, forbidden phrases absent, expected source cited, every [n] maps to a passage. Free, instant, deterministic. Then a second, smaller model judges tone, helpfulness and clarity from 1 to 5 against a written rubric at temperature 0. Calibrate it against 20 hand scores before trusting it.

Picture it: A pH meter first; only then a trained sensory panel for the things a meter cannot measure.
def score_rules(case, reply, sources):
    failures = []
    lowered = reply.lower()
    for phrase in case.must_contain:
        if phrase.lower() not in lowered:
            failures.append(f"missing phrase: {phrase}")
    for phrase in case.must_avoid:
        if phrase.lower() in lowered:
            failures.append(f"forbidden phrase: {phrase}")
    if case.expected_source and case.expected_source not in sources:
        failures.append(f"expected source not cited: {case.expected_source}")
    return failures
Failures come back with reasons. A judge agreeing with you on 18 of 20 earns authority; 12 of 20 means the rubric is vague.
The trap: A 1-to-100 judge scale that sounds precise and is noise; use 1 to 5 and add cases instead.
In Formulaite: gates.py: run_gates() is score_rules for a drawer; a Verdict-style judge could rate the drawer's safety wording after the gate passes.
07Untrusted records and redaction ch 12

Retrieved passages come from supplier PDFs and websites you do not control. A planted 'ignore previous instructions' line arrives as ordinary context. Picture it: Quarantining incoming raw materials, and removing customer names from the batch log before it is filed.
import re
PATTERNS = {
    "card": re.compile(r"\bDG-\d{4}\b"),

}

The pattern

  1. system = who the assistant is and its limits; messages = the facts and the question.
  2. Retrieve 3 to 5 passages, number them [n] source, drop anything past the distance threshold.
  3. Ask for JSON at temperature 0 with a '{' prefill or a tool schema.
  4. Validate with Pydantic; on error, append the report as a turn and retry (3 tries, then raise).
  5. If stop_reason is tool_use: run the tool, return the result by id, loop (max 5 steps).
  6. Anything that spends money waits for a ticket a human confirms.
  7. Run 20 cases before shipping; log prompt version, steps, tokens and cost per request.

Before you ship

  • The key lives in .env with chmod 600 and a .gitignore line.
  • Every call records stop_reason, tokens and the prompt version.
  • Every grounded prompt names its fallback, and every citation maps to a passage you sent.
  • The loop has max_steps and a hand-over message; the dispatcher never raises.
  • Write tools need a single-use ticket; read tools are logged with name, arguments and duration.
  • 20 eval cases run as one command; no blocking failure; the pass count may drop by at most one.
  • Traces carry numbers only; PII is redacted before sessions, logs or eval output reach disk.
  • index_all() and the eval gate run in the same deploy step; /health checks the collection is not empty.

  3. You can run one command that scores 20 cases, appends a history line, and tells you whether the release is blocked.
