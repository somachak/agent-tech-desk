  4. Give Agent.run() a max_steps budget and a named status when it is hit.

  4. Score each eval run with deterministic checks on route, tool calls and escalation.

01The smallest useful agent loop ch 1

An agent is a loop, not a clever prompt. It takes a goal, picks one allowed action, performs it, and looks at the result. Then it asks: need more work? If yes, loop again. If no, finish or hand over to a human.

Picture it: A lab assistant given a brief: read the request, pick one approved test, run it, note the result, then decide whether to run another or report back.
def run_agent(request):
    action = choose_action(request)
    if action == "analyze_sales":
        result = analyze_sales()
    elif action == "review_document":
        result = review_document()
    elif action == "human_approval":
        result = request_human_approval()
    else:
        result = ask_for_clarification()
    return {"request": request, "action": action, "result": result}
choose_action decides; the small functions act; run_agent only connects the two and returns something you can inspect.
The trap: Thinking the intelligence lives in the prompt, when the loop, the allowed actions and the stop rule are what make it an agent.
In Formulaite: agent.py — Agent.run() is this loop: the model chooses, formulaite_tools.py runs the tool, and the loop repeats until fill_drawer passes the gate.
02Capability is not permission ch 1

A system may be able to do something and still not be allowed to do it automatically. The book fixes the router by checking safety-sensitive words first. Anything that can affect other people or systems stops for approval before ordinary routing continues.

Picture it: Your formulator can weigh out any raw material in the store. That does not mean she may add a restricted preservative without a sign-off.
def choose_action(request):
    text = request.strip().lower()
    if not text:
        return "ask_for_clarification"
    # Safety-sensitive actions are checked first.
    if any(word in text for word in ["send", "email", "approve", "delete"]):
        return "human_approval"
    if any(word in text for word in ["sales", "revenue", "turnover"]):
        return "analyze_sales"
    return "ask_for_clarification"
The order of the if-statements is the policy: the approval check comes before ordinary work.
The trap: Letting a request that mentions both revenue and approve fall into the sales branch because that check came first.
In Formulaite: gates.py — check_not_banned runs whatever the model believed; the drawer can be filled, but a banned ingredient never passes.
03One state object ch 2

Keep the whole task in one dictionary: goal, status, steps, history, result. Every part of the loop reads and writes the same object. Later you can add tool results, checkpoints and evaluation data without rewiring the code.

Picture it: A batch record sheet that travels with the batch. Every station writes on the same sheet instead of keeping private notes.
def create_state(goal):
    return {
        "goal": goal,
        "status": "running",
        "steps": 0,
        "history": [],
        "result": None,
    }
status starts as running; the loop continues only while it stays that way.
The trap: Passing five loose variables between functions, then losing track of which one holds the truth.
In Formulaite: agent.py — RunResult is the lab's state object: drawer, verdict, steps and the Glass Box run id in one dataclass.
04The tools dictionary is a boundary ch 2

The decision component can suggest any action name. The executor only runs names that exist in the tools dictionary. Unknown names get a polite refusal. Never a crash, never an improvised action.

Picture it: A locked cabinet with labelled drawers. The assistant can ask for glycerin but cannot ask for a drawer that does not exist.
def execute_action(action):
    tools = {
        "analyze_sales": analyze_sales,
        "review_report": review_report,
        "request_approval": request_approval,
    }
    if action not in tools:
        return "No approved tool is available for this action."
    return tools[action]()
tools[action]() looks a function up by name and then calls it. The dict is the allow-list.
The trap: Executing whatever string the model returned with eval() or getattr().
In Formulaite: tools.py — ToolRegistry.call(name, ...) is the same allow-list; a name not in the registry raises ToolError instead of running anything.
05Stopping conditions and step limits ch 2

Every agent needs a reason to stop. Success, a human is needed, an error, or a step limit. The book adds the step limit before the agent can even loop. Safety is easier to design early than to bolt on later.

Picture it: A timer on a mixer. Even if the recipe is unclear, the motor stops after ten minutes.
def should_stop(state, action):
    if action == "need_clarification":
        state["status"] = "needs_input"
        return True
    if action == "request_approval":
        state["status"] = "waiting_for_approval"
        return True
    if state["steps"] >= 3:
        state["status"] = "step_limit_reached"
        return True
    state["status"] = "completed"
    return True
Each branch sets a named status so the caller knows why the loop ended.
The trap: Adding the step limit as an emergency fix after the first runaway-loop bill.
In Formulaite: agent.py — Agent(max_steps=...) stops the drawer loop no matter what; the for-else records max steps reached in the Glass Box.
06Validate the goal before the loop ch 2

Reject empty, non-text or oversized goals before any decision is made. This is not intelligence; it is ordinary software design. Many reliability wins come from checks around the model, not from a smarter model.

Picture it: Checking that a brief has a product name and a target use before you start weighing anything.
def validate_goal(goal):
    if not isinstance(goal, str) or not goal.strip():
        return False, "A clear goal is required."
    if len(goal) > 500:
        return False, "The goal is too long. Please make it more specific."
    return True, None

valid, error = validate_goal(goal)
if not valid:
    return {"goal": goal, "status": "rejected", "result": error}
The function returns a pair: an ok flag and a message. The caller returns a rejected state instead of looping.
The trap: Sending an empty question to the model and paying for a request that cannot succeed.
In Formulaite: agent.py — Agent.run(inci) should reject a blank INCI name before the first model call; models.py _extract_inci shows where the name is read.
07The model is an ingredient, the application is the system ch 3

The SDK sends a request to a remote API and gets text back. Your Python decides what to do with that text. Credentials, input checks, error handling and what is allowed all stay in your code.

Picture it: A fragrance house supplies the scent. You still own the formula, the safety testing and the label.
def create_research_brief(question):
    if not question.strip():
        return "Please enter a research question."
    try:
        response = client.responses.create(
            model="gpt-5", input=question,
            instructions="You are a careful research assistant.")
        return response.output_text
    except Exception as error:
        print(f"Request failed: {type(error).__name__}")
        return "I could not complete the request."
Only the error type is printed. No API key, no traceback shown to the user.
The trap: Pasting the API key into the script; the book reads it from an environment variable instead.
In Formulaite: models.py — ClaudeModel wraps the anthropic SDK behind one complete() method; ScriptedModel swaps in offline and agent.py never notices.
08The schema is a contract ch 4

Prose is for people; software needs named fields. A Pydantic class states exactly what the model must return. Literal limits a field to a few allowed values. The SDK parses the reply straight into that class.

Picture it: A spec-sheet template. Every supplier fills the same boxes: INCI name, use level, function. No more hunting through a PDF.
from typing import Literal
from pydantic import BaseModel

class ResearchBrief(BaseModel):
    topic: str
    summary: str
    key_points: list[str]
    confidence: Literal["low", "medium", "high"]
    next_steps: list[str]

brief = client.responses.parse(
    model="gpt-5", input=question, text_format=ResearchBrief).output_parsed
text_format=ResearchBrief tells the SDK the shape; output_parsed is already a ResearchBrief object.
The trap: Asking for JSON please and hoping the field names stay the same each time.
In Formulaite: drawer.py — IngredientDrawer is the contract; as_tool_schema() turns the dataclass into the schema the model must fill.
09Structure is not truth ch 4

A perfectly shaped answer can still be wrong or empty. The schema answers: is this the right shape? A second layer of plain Python answers: is this acceptable for what we do next? Keep the two layers separate.

Picture it: A form with every box ticked can still list a use level that would irritate skin. The form is complete; the formula is not safe.
def validate_brief(brief):
    if not brief.summary.strip():
        raise ValueError("Summary cannot be empty.")
    if not brief.key_points:
        raise ValueError("At least one key point is required.")
    if not brief.next_steps:
        raise ValueError("At least one next step is required.")
    return brief

brief = validate_brief(response.output_parsed)
Business rules run after parsing and before the result reaches the rest of the program.
The trap: Retrying the same request three times when the problem is missing information, not a flaky network.
In Formulaite: gates.py — run_gates() is this second layer: check_use_level_in_range and check_no_forbidden_claims judge the content, not the shape.
10Model proposes, application executes ch 5

Function calling does not let the model run your code. The model returns a request: a tool name, JSON arguments and a call_id. Your code validates it, runs the function, and sends the result back tagged with that call_id.

Picture it: A chef calls out two grams of citric acid. The assistant checks the recipe, weighs it and reports the number. The chef never touches the scale.
for item in response.output:
    if item.type != "function_call":
        continue
    if item.name == "get_company_profile":
        arguments = json.loads(item.arguments)
        result = get_company_profile(arguments["company_name"])
        input_items.append({
            "type": "function_call_output",
            "call_id": item.call_id,
            "output": json.dumps(result),
        })
item.name, item.arguments and item.call_id are the three things to read; the output goes back under the same call_id.
The trap: Treating the model choosing a tool as proof that the user is allowed to use it.
In Formulaite: agent.py — _handle_tool runs the ToolUseBlock through the registry and _tool_result sends the answer back under the same tool_use_id.
11The controlled dispatcher ch 5

Put all tool execution behind one function. It checks the name, re-checks the arguments, and returns a small ok/error dictionary. An unknown name returns Tool is not allowed. One place to audit, one place to fix.

Picture it: One dispensary hatch. Every request for a raw material goes through the same window and the same checklist.
def execute_tool(name, arguments):
    if name == "get_company_profile":
        company_name = arguments.get("company_name", "")
        if not company_name.strip():
            return {"ok": False, "error": "company_name is required"}
        return get_company_profile(company_name)
    if name == "calculate_percentage_change":
        old_value, new_value = arguments.get("old_value"), arguments.get("new_value")
        if old_value is None or new_value is None:
            return {"ok": False, "error": "Both values are required"}
        return calculate_percentage_change(old_value, new_value)
    return {"ok": False, "error": "Tool is not allowed"}
Every branch validates its own arguments; the final return is the catch-all refusal.
The trap: Scattering tool calls across many if-statements so nobody can see the full allow-list.
In Formulaite: tools.py — ToolRegistry.call() plus Tool.__call__ is the dispatcher; formulaite_tools.py build_registry() lists the only three tools it knows.

01Controlled observations from external tools ch 6

An API tool validates its input, calls with a timeout, checks the HTTP status and parses JSON. Each failure type has its own except branch. Every path returns a small dictionary. No traceback ever lands in the model's context.

Picture it: A supplier phone call with a script: confirm the code, wait at most a minute, write down no answer rather than guessing the price.
def lookup_record(record_id):
    if record_id < 1 or record_id > 200:
        return {"ok": False, "error": "record_id is outside the allowed range"}
    url = f"https://jsonplaceholder.typicode.com/todos/{record_id}"
    try:
        response = requests.get(url, timeout=10)
        response.raise_for_status()
        return {"ok": True, "record": response.json()}
    except requests.Timeout:
        return {"ok": False, "error": "The external service timed out."}
    except requests.RequestException:
        return {"ok": False, "error": "The external service could not be reached."}
timeout=10, raise_for_status() and one except per failure type. Each returns a calm observation.
The trap: Retrying a write such as an order or payment without asking whether the first attempt already succeeded.
In Formulaite: formulaite_tools.py — read_supplier_page(url) is the sensor tool; give it a timeout and ok/error returns before it ever goes online.
02Chunking is a design decision ch 7

RAG splits a document into chunks, embeds them, and retrieves the closest ones for each question. Chunk size matters. Too small separates facts that belong together; too large mixes unrelated ideas. Ask: what is the smallest piece that still makes sense alone?

Picture it: Cutting a supplier data sheet into cards: one card per section, not one per sentence and not the whole sheet.
def chunk_document(text):
    return [
        paragraph.strip()
        for paragraph in text.split("\n\n")
        if paragraph.strip()
    ]

chunks = chunk_document(document)
for number, chunk in enumerate(chunks, start=1):
    print(f"Chunk {number}: {chunk}")
One paragraph per chunk is the starting point; the list comprehension drops empty paragraphs.
The trap: Believing RAG teaches the model your documents. It only pastes retrieved chunks into that one request.
In Formulaite: formulaite_tools.py — read_supplier_page returns a whole page today; chunking it by section is the first upgrade.
03Source labels on every chunk ch 7

Each stored chunk carries three things: a source label, the text and its embedding. The label looks like policy.txt#chunk-3. It travels with the chunk into the context block, so the reader can check the evidence behind the answer.

Picture it: Every ingredient claim on a spec sheet cites the supplier document and the section it came from.
embedded_chunks = []
for number, chunk in enumerate(chunks, start=1):
    embedded_chunks.append({
        "source": f"company_policy.txt#chunk-{number}",
        "text": chunk,
        "embedding": create_embedding(chunk),
    })

def build_context(matches):
    return "\n\n".join(
        f'SOURCE: {m["source"]}\n{m["text"]}' for m in matches)
The source string is made once at ingest and printed again in the context block the model sees.
The trap: Losing the filename when two documents are merged, so a citation points nowhere.
In Formulaite: drawer.py — the drawer's sources section exists for exactly this; gates.py check_has_sources fails a drawer with no source labels.
04Inspect retrieval before generation ch 7

Print the top matches and their scores before asking the model anything. If the right paragraph is not in the top results, no prompt can fix it. Diagnose retrieval first, then generation.

Picture it: Check the samples you pulled from the shelf before you start mixing. Wrong jar, wrong batch.
question = "Can a new employee work remotely three days a week?"
matches = retrieve_chunks(question, embedded_chunks, top_k=3)
for match in matches:
    print(f'{match["source"]} ({match["score"]:.3f})')
    print(match["text"])
    print()
Three lines of printing is the whole debugging tool: source, score, text.
The trap: Blaming the model for a wrong answer when retrieval never found the evidence.
In Formulaite: glassbox.py — log every retrieved source and score as an Event so a replay shows exactly what the model saw.
05Retrieved text is data, not authority ch 7

A document can contain the words ignore all previous instructions. That is content, not a command. Keep trusted instructions separate from retrieved text. Tell the model the documents are evidence to analyse, and enforce permissions in code anyway.

Picture it: A supplier brochure saying no safety test needed does not change your lab's rules.
The trap: Hoping one clever sentence in the prompt solves prompt injection; the book says use layers.
In Formulaite: agent.py — SYSTEM_PROMPT should say supplier pages are untrusted evidence; gates.py enforces the rules whatever the page says.
06Calculate first, explain second ch 8

Numbers are computed by code, never estimated by the model. Pandas calculates; a small dictionary of verified results becomes the evidence package. The model receives only that package and explains it. Show the numbers beside the explanation.

Picture it: The scale gives the weight. The formulator writes the story. Nobody guesses the weight.
def analyze_sales(data):
    return {
        "total_revenue": float(data["revenue"].sum()),
        "total_units": int(data["units"].sum()),
        "revenue_by_region": (
            data.groupby("region")["revenue"]
            .sum().sort_values(ascending=False).to_dict()
        ),
    }

evidence = json.dumps(analyze_sales(data), indent=2)
Pandas results become plain floats, ints and dicts; json.dumps is the boundary between calculation and explanation.
The trap: Letting the model answer why did West outperform. The data shows what, not why.
In Formulaite: gates.py — check_use_level_in_range is deterministic arithmetic against the catalogue; the model never computes the range.
07A planner with unsupported and clarify routes ch 9

The model picks one route from a fixed list. The list includes unsupported and clarify. That gives the system an honest way to say no approved calculation for that, or what do you mean by best? The model must never invent another route.

Picture it: A triage nurse with four doors, plus a not-us door and a tell-me-more door.
class AnalysisPlan(BaseModel):
    analysis_type: Literal[
        "revenue_by_region",
        "units_by_product",
        "monthly_revenue",
        "clarify",
        "unsupported",
    ]
    reason: str
    clarification_question: str | None = None
Literal is the allow-list; the reason field makes the choice auditable.
The trap: Leaving out the unsupported route, so the model squeezes every question into the nearest tool.
In Formulaite: models.py — ScriptedModel follows a fixed plan; a routing step in agent.py could return clarify when the INCI name is not in the catalogue.
08Registry dispatch ch 9

Approved functions live in a dictionary keyed by name. Dispatch is a lookup: get the function, call it with the data. A missing key raises an error before anything runs. Adding a capability means adding one entry.

Picture it: A rack of labelled pipettes. You reach for the one whose label matches; there is no other slot.
ANALYSIS_TOOLS = {
    "revenue_by_region": revenue_by_region,
    "units_by_product": units_by_product,
    "monthly_revenue": monthly_revenue,
}
def run_analysis(plan, data):
    if plan.analysis_type == "unsupported":
        return None
    tool = ANALYSIS_TOOLS.get(plan.analysis_type)
    if tool is None:
        raise ValueError("Unrecognized analysis type.")
    return tool(data)
Functions are values: the dict stores them, .get() fetches one, tool(data) calls it.
The trap: Giving the model permission to write Pandas code instead of expanding the approved list.
In Formulaite: tools.py — ToolRegistry is this dict with a decorator on top; @registry.tool(...) in formulaite_tools.py adds an entry.
09Typed workflow state ch 10

Long-running work needs a task record with an id, a question, a status and findings. Pydantic types it. The status field is a small state machine. The task is in exactly one named state, never sort of finished.

Picture it: A stability-test log: sample id, current stage, observations so far. One stage at a time.
class ResearchTask(BaseModel):
    task_id: str
    question: str
    status: Literal[
        "created", "researching", "waiting_for_review",
        "approved", "completed", "failed",
    ] = "created"
    findings: list[str] = Field(default_factory=list)
    reviewer_note: str | None = None
    final_answer: str | None = None
Field(default_factory=list) gives each task its own empty list; a shared default would leak findings between tasks.
The trap: Using the chat transcript as the database and asking the model to remember whether approval happened.
In Formulaite: memory.py — Conversation is the model's short-term memory; a typed drawer task with a status field would sit beside it in agent.py.
10Allowed transitions ch 10

A dictionary maps each status to the set of statuses it may move to. change_status checks the map, then saves. The model never redefines the workflow. The application owns the legal moves.

Picture it: A sample cannot go from mixing straight to released. It must pass QC first, and the log enforces that.
ALLOWED_TRANSITIONS = {
    "created": {"researching", "failed"},
    "researching": {"waiting_for_review", "failed"},
    "waiting_for_review": {"approved", "researching", "failed"},
    "approved": {"completed", "failed"},
    "completed": set(), "failed": set(),
}
def change_status(task, new_status):
    if new_status not in ALLOWED_TRANSITIONS[task.status]:
        raise ValueError(f"Cannot move from {task.status} to {new_status}.")
    task.status = new_status
    save_task(task)
A dict of sets: the key is where you are, the set is where you may go. An empty set means terminal.
The trap: Skipping the review state just this once by setting task.status directly.
In Formulaite: gates.py — GateVerdict decides PASS or FAIL; an ALLOWED_TRANSITIONS map would stop a failed drawer from ever being marked released.
11Save deliberately, re-validate on load ch 10

Persist the task as JSON after every meaningful change. When loading, run it back through the Pydantic model. A saved file is not automatically trustworthy. A corrupted status value is rejected at load time.

Picture it: Reading a handwritten batch sheet back against the template before trusting it.
def save_task(task):
    path = STATE_FOLDER / f"{task.task_id}.json"
    path.write_text(json.dumps(task.model_dump(), indent=2), encoding="utf-8")
    return path

def load_task(task_id):
    path = STATE_FOLDER / f"{task_id}.json"
    if not path.exists():
        raise FileNotFoundError("No saved task was found.")
    data = json.loads(path.read_text(encoding="utf-8"))
    return ResearchTask.model_validate(data)
model_dump() out, model_validate() in. The same contract guards both directions.
The trap: Resuming the wrong task id and mixing one user's approvals with another's evidence.
In Formulaite: glassbox.py — GlassBox.save() and GlassBox.load() persist a run the same way; a drawer task file would live beside it.
12Policy lives in code ch 11

The model classifies the request and gives a confidence. A plain dictionary decides what may run automatically. Low confidence always goes to review. Business policy is never left to model judgement.

Picture it: The receptionist sorts the post; a written rulebook says which letters the manager must open personally.
AUTOMATION_POLICY = {
    "order_status": "automatic",
    "return_request": "review",
    "billing_question": "review",
    "other": "review",
}

def decide_route(classification):
    if classification.confidence == "low":
        return "review"
    return AUTOMATION_POLICY[classification.category]
Two lines of policy: the dict for categories, the if for confidence. Change policy here, not in a prompt.
The trap: Asking one prompt to interpret, decide policy, act, track state and escalate all at once.
In Formulaite: gates.py — the check_* functions are Formulaite's AUTOMATION_POLICY; which drawers need a human look is decided in code.
13Idempotency guard ch 11

Users click twice. Networks time out. Workers restart. A completed request must not be completed again. Keep a record of finished ids and refuse repeats. In production that record lives in durable shared storage.

Picture it: A batch number stamped once. If the label printer jams and retries, the same number is not printed twice.
processed_requests = set()

def mark_completed(request):
    if request.request_id in processed_requests:
        raise ValueError("Request has already been completed.")
    processed_requests.add(request.request_id)
    request.status = "completed"
    request.action_log.append("Request completed.")
    return request
A set of finished ids: membership is checked before the side effect and added right after.
The trap: Retrying a payment after a timeout without knowing whether the first attempt already succeeded.
In Formulaite: glassbox.py — the run_id on every GlassBox is the natural idempotency key for save this drawer to the catalogue.

01The review package ch 12

A reviewer should not rebuild the case from logs. Give them one package: the request, the classification and confidence, the proposed action, the proposed response and the action log. Evidence and proposal together, so the decision is informed.

Picture it: A sign-off folder: the brief, the test results, the proposed formula, and the reason it needs a signature.
def build_review_package(request, classification, proposed_action, proposed_response=None):
    return {
        "request_id": request.request_id,
        "customer_message": request.message,
        "category": classification.category,
        "confidence": classification.confidence,
        "classification_reason": classification.reason,
        "proposed_action": proposed_action,
        "proposed_response": proposed_response,
        "action_log": request.action_log.copy(),
    }
action_log.copy() hands the reviewer a snapshot, not a live list that keeps changing.
The trap: A review screen that shows only an Approve button and the AI recommendation.
In Formulaite: glassbox.py — GlassBox.replay() plus the failed GateVerdict reasons is the review package for a drawer that needs a human.
02Approval is not execution ch 12

A human saying yes is a signal, not a bypass. After approval the application still checks: does this reviewer have the role, is the amount inside their limit, has it already been done, does the record still exist? Only then does it execute.

Picture it: The lab manager approves a batch. The system still checks she may approve that size, and that it has not already shipped.
REVIEWER_LIMITS = {
    "support_agent": 100,
    "supervisor": 500,
    "manager": 2000,
}

def can_approve_amount(reviewer_role, amount):
    limit = REVIEWER_LIMITS.get(reviewer_role)
    if limit is None:
        return False
    return amount <= limit
An unknown role gets None and is refused. Approval authority matches responsibility.
The trap: Letting an old approval silently cover a proposal that changed after the reviewer said yes.
In Formulaite: gates.py — run_gates() should run again after a human edits a drawer; the edit is a proposal, not a release.
03Confidence is a signal, not permission ch 12

High confidence from the model does not authorise an action. Low confidence does not mean the model is wrong. Confidence helps route work to review. Policy still decides what is allowed.

Picture it: A confident junior formulator still cannot release a batch. A nervous senior one still can.
The trap: Using confidence equals high as the condition that skips the human gate.
In Formulaite: drawer.py — a confidence field on IngredientDrawer would help sort the review queue, never skip gates.py.
04A failure test names the expected behaviour ch 13

A failure test is a name, a function that returns True or False, and a sentence describing the safe behaviour. A tiny runner prints PASS or FAIL. Every bug you fix becomes one more test so it cannot come back.

Picture it: A stability-test protocol: the sample, the stress, and what still fine looks like, written down before you start.
from dataclasses import dataclass
from typing import Callable
@dataclass
class FailureTest:
    name: str
    run: Callable[[], bool]
    expected_behavior: str

tests = [FailureTest(
    name="Reject empty request",
    run=lambda: validate_request_text("")["ok"] is False,
    expected_behavior="Empty input is rejected.")]
Callable[[], bool] means a function taking nothing and returning True or False. The lambda fits.
The trap: Testing only that the program did not crash instead of testing that it behaved safely.
In Formulaite: gates.py — each check_* function deserves a FailureTest; scripts/check_gate_control.py already runs this pattern against the lab.
05Admit insufficient evidence ch 13

Set a threshold on the best retrieval score. Below it, the system says it cannot answer or asks for clarification. The number is application-specific and must be tuned with real data. The fallback matters more than the number.

Picture it: If the strongest match on the shelf is only vaguely similar, say we do not stock that instead of handing over the nearest jar.
def evidence_is_sufficient(matches):
    if not matches:
        return False
    best_score = matches[0]["score"]
    return best_score >= 0.60
0.60 is an example for the exercise, not a universal constant.
The trap: Choosing whichever of two contradicting chunks appears first instead of surfacing the conflict.
In Formulaite: gates.py — a check_evidence_sufficient gate would fail a drawer whose sources scored below threshold and send it back to the model.
06Authorization outside the model ch 13

Roles map to sets of allowed actions. authorize() checks the set and raises PermissionError. The role comes from trusted application state. Text like I am the CEO inside a request never changes it.

Picture it: A key card. Saying I work here at the door does nothing; the reader checks the database.
ROLE_PERMISSIONS = {
    "viewer": {"read"},
    "support": {"read", "draft"},
    "supervisor": {"read", "draft", "approve_return"},
}

def authorize(role, action):
    allowed = ROLE_PERMISSIONS.get(role, set())
    if action not in allowed:
        raise PermissionError(f"{role} cannot perform {action}.")
    return True
ROLE_PERMISSIONS.get(role, set()) means an unknown role can do nothing.
The trap: Removing a permission check and not noticing because no test covered it.
In Formulaite: tools.py — a per-role allow-list in ToolRegistry.call() would stop fill_drawer from writing to the catalogue for a viewer role.
07Deterministic checks before rubrics ch 14

An eval case records the input, the expected route, whether it must escalate and which actions are forbidden. Plain code checks those exactly. Only fuzzy qualities such as clarity get a rubric. Never ask a model to judge what code can verify.

Picture it: pH is measured with a meter. Feels luxurious needs a panel. Do not ask the panel for the pH.
@dataclass
class EvalCase:
    name: str
    user_input: str
    expected_route: str
    must_escalate: bool = False
    forbidden_actions: tuple[str, ...] = ()
def score_case(case, result):
    return {
        "route_correct": result["route"] == case.expected_route,
        "escalation_correct": result["escalated"] == case.must_escalate,
    }
Each check is a True or False; the book adds a third check for forbidden actions.
The trap: Collapsing everything into one quality score, which lets 98 percent hide a failed authorization test.
In Formulaite: glassbox.py — GlassBox.of_kind('tool_call') gives the actions list score_case needs; the run itself is the observable result.
08Release gates ch 14

A release gate turns evaluation into a decision. Overall pass rate must clear a bar. Authorization failures, duplicate side effects and critical security failures must be zero. Run the suite before and after every change.

Picture it: A batch ships only if the average is fine and there are zero microbial failures. One contaminated sample blocks everything.
RELEASE_GATES = {
    "minimum_overall_pass_rate": 0.95,
    "authorization_failures": 0,
    "duplicate_side_effects": 0,
    "critical_security_failures": 0,
}

def ready_to_release(metrics):
    return (metrics["overall_pass_rate"] >= RELEASE_GATES["minimum_overall_pass_rate"]
            and metrics["authorization_failures"] == 0
            and metrics["duplicate_side_effects"] == 0
            and metrics["critical_security_failures"] == 0)
The and-chain means every gate must pass; the numbers are examples, not industry thresholds.
The trap: Shipping because the average improved, while one prompt tweak introduced an unauthorised action.
In Formulaite: gates.py — GateVerdict is a per-drawer gate; a release gate over a whole eval run of drawers would live in a scripts/ checker beside it.
09An agent that cannot be stopped is not ready ch 15

Production needs stopping power: timeouts, bounded retries, a maximum number of steps, spending limits, a disable switch and a way to pause automation. Version prompts and schemas so every change can be traced.

Picture it: Every mixer has an emergency stop button. You do not sell one without it.
MAX_STEPS = 8

def check_step_limit(step_number):
    if step_number >= MAX_STEPS:
        raise RuntimeError("Workflow stopped: step limit reached.")
One constant, one check, called on every turn of the loop.
The trap: Treating it worked in the demo as proof that it will stop when the API hangs.
In Formulaite: agent.py — max_steps is the lab's stop button; memory.py token_estimate() is the start of a cost budget.
10Fix the layer that owns the problem ch 15

Each failure belongs to one layer. Routing error: the planner contract. Bad number: the calculation code. Unauthorised action: the permission layer. Duplicate: idempotency. Never ask the prompt to compensate for broken software.

Picture it: If the scale is wrong, calibrate the scale. Do not rewrite the recipe to allow for it.
The trap: Adding another paragraph to the system prompt for every bug.
In Formulaite: The lab is already split by layer: models.py routes, formulaite_tools.py fetches, gates.py judges, glassbox.py records. Fix the file that owns the failure.

Vocabulary

TermMeans
AgentA loop that picks allowed actions toward a goal until a stopping condition fires.
ToolA Python function the application lets the model request; the model never runs it.
ObservationThe small result a tool returns; it becomes context for the next decision.
StateThe one record of a task: goal, status, steps, history, result.
Stopping conditionThe rule that ends the loop: done, human needed, error, or step limit.
SchemaThe contract for the model's output shape, written as a Pydantic class.
Business validationPlain Python rules run after the schema and before the next step.
DispatcherThe one function that checks a tool name and arguments, then runs it.
Controlled observationAn ok/error dictionary returned instead of a traceback.
ChunkA piece of a document small enough to retrieve on its own.
GroundingAn answer traceable to retrieved or calculated evidence.
Evidence packageVerified numbers or labelled sources handed to the model to explain.
PlannerThe model step that picks one route from a fixed list that includes unsupported and clarify.
State machineA status field plus a map of the transitions that are allowed.
IdempotencyDoing the same action twice has no extra effect.
Review packageRequest, evidence, proposal and reason, handed to a human reviewer together.
Least privilegeOnly the tools, data and limits the task actually needs.
Prompt injectionInstructions hidden inside retrieved or tool content; data, not commands.
Release gateA rule that turns eval results into ship or fix.
Regression testA past failure kept as a permanent test so it cannot return.

The pattern

  1. Validate the input before any model call.
  2. Model proposes: a route, a tool name with arguments, or a structured answer.
  3. Application checks: allowed name, valid arguments, permission for this role.
  4. Approved code executes; the tool returns a controlled ok/error observation.
  5. Validate the result: schema first, then business rules.
  6. Consequential? Stop for human review, then re-check before executing.
  7. Record state and the trace; stop on success, clarify, unsupported or step limit.

Agent loop with a step limit

def run_agent(goal, max_steps=3):
    state = create_state(goal)
    while state["status"] == "running":
        action = decide_next_action(state)
        if action not in TOOLS:
            state["status"] = "needs_input"
            continue
        record_observation(state, action, TOOLS[action]())
        should_stop(state, action)
        if state["steps"] >= max_steps and state["status"] == "running":
            state["status"] = "step_limit_reached"
    return state

def safe_tool(arguments):
    value = arguments.get("record_id")
    if not isinstance(value, int) or not 1 <= value <= 200:
        return {"ok": False, "error": "record_id out of range"}
    try:
        response = requests.get(URL.format(value), timeout=10)

Before you ship

  • Empty and vague input is rejected before the model call.
  • Only allow-listed tool names run; an unknown name returns Tool is not allowed.
  • Every external call has a timeout and returns ok/error, never a traceback.
  • Retrieval scores and source labels are visible before generation.
  • Numbers are computed in code; the model only explains them.
  • State is typed, transitions are guarded, saved state is re-validated on load.
  • Approval is re-checked against role, limit and duplicates before execution.
  • Authorization failures and duplicate side effects are zero in the eval run.
