01 · Where this is going

Decompose to the drawer's fixed sections, delegate each under a written contract, and put the human gate exactly where the write happens.

Read this book when: Open it when Formulaite's research loop needs to grow from one agent doing everything into briefed sub-tasks with a person approving the catalogue write.

The one picture that holds the whole book. Every chapter adds a box or an arrow to it; nothing later replaces it.

flowchart TD
  G[Research one ingredient] --> S[Scope and risk tier]
  S --> Q[Split into sub-questions from drawer sections]
  Q --> B[Delegation brief per sub-question]
  B --> A[Sub-agent or tool - read only]
  A --> H[Handoff packet back]
  H --> M[Coordinator merges the drawer]
  M --> D[Deterministic gate]
  D -->|fail with reasons| Q
  D -->|pass| R[Human review gate]
  R -->|approve| W[Catalogue write]
  R -->|reject or edit| Q
  M --> X[Glass Box trace]
  R --> X
02 · Build ladder

Three things to build, in order

Each rung is a Formulaite feature. Click a rung for its steps. Do rung 1 after the Foundation cards, rung 2 after Intermediate, rung 3 after Advanced.

Rung 1 · Simple

Scoped, decomposed research for one ingredient

A Formulaite run where the scope is one INCI, each drawer section is a written sub-question mapped to a tool, and the Glass Box shows which sub-question each step served.

~1 hour
Rung 2 · Intermediate

Briefed sub-runs with a human gate on the catalogue write

Read-only sub-runs that each get a Brief and return a Handoff packet, a coordinator that merges them, and an approve step before anything is written.

~half a day
Rung 3 · Advanced

Governed, drilled, measured agent that can take on new tools

A version-stamped Formulaite agent with a one-page policy the loop reads, a scenario folder that runs before every change, and a staged path for adding a live supplier fetch.

~2 days

Steps for rung 1: Scoped, decomposed research for one ingredient

  1. Write the one-sentence scope and check it matches Agent.run(inci).
  2. Turn REQUIRED_SECTIONS in drawer.py into a list of sub-questions.
  3. Map each sub-question to catalogue_lookup or read_supplier_page.
  4. Run the offline agent on Glycerin and open the saved Glass Box.
  5. Label each event with the sub-question it answered.
Chapters 1, 2, 3, 4 · Agent Lab files: drawer.py · formulaite_tools.py · agent.py · glassbox.py · ~1 hour

Steps for rung 2: Briefed sub-runs with a human gate on the catalogue write

  1. Add Brief and Handoff dataclasses next to drawer.py.
  2. Build a read-only ToolRegistry and give each sub-run its own max_steps.
  3. Write merge() that escalates on low confidence or open questions.
  4. Add approve() showing drawer, gate reasons and sources before the write.
  5. Log the human answer and the gate verdict as Glass Box events.
Chapters 5, 6, 7, 11, 12 · Agent Lab files: tools.py · gates.py · agent.py · glassbox.py · memory.py · ~half a day

Steps for rung 3: Governed, drilled, measured agent that can take on new tools

  1. Log a versions event with prompt, model, catalogue and gate versions on every run.
  2. Run the fail_first drill and assert one gate_fail event.
  3. Add a POLICY dict in gates.py and check it before each tool call.
  4. Build scenarios for happy, missing, contradicting and rejected paths.
  5. Add a live read_supplier_page at the sandbox stage and promote it only after scenarios pass.
Chapters 9, 13, 18, 19, 21, 22 · Agent Lab files: models.py · gates.py · agent.py · formulaite_tools.py · glassbox.py · ~2 days

01Scope statement ch 1

Before any decomposition, write one sentence that says what the agent is for. Formulaite's is: fill one Ingredient Drawer for one INCI name. Anything outside that sentence is out of scope. The sentence is what you later split into sub-questions.

Picture it: A lab work order names one product and one batch. Nobody starts weighing until the order is on the bench.
The trap: Starting with 'research cosmetics' and hoping the model narrows it down for you.
In Formulaite: agent.py: Agent.run(inci) takes exactly one INCI name; that argument is the scope statement made concrete.
02Risk tiers per action ch 1

Not every action carries the same risk. Sort each one by what happens if it is wrong. Reading a supplier page is cheap to undo. Writing a bad use level into the catalogue is not. The tier decides how much control the action gets.

Picture it: Tasting a sample is low risk. Shipping a batch is high risk. You check the second one far harder.
class Risk(Enum):
    READ = 1      # reversible, runs free
    PROPOSE = 2   # drawer draft, deterministic gate
    WRITE = 3     # catalogue write, human gate

RISK = {
    "catalogue_lookup": Risk.READ,
    "read_supplier_page": Risk.READ,
    "fill_drawer": Risk.PROPOSE,
    "catalogue_write": Risk.WRITE,
}
One tier per tool name; the loop looks the tier up before it runs anything.
The trap: Giving the whole agent one risk level, so reads get slowed down and writes get waved through.
In Formulaite: tools.py: add a risk field to Tool so gates.py and agent.py pick the control from the tier, not from the tool name.
03System surface map ch 2

List every place the agent can touch. For Formulaite that is the catalogue, the supplier pages, the drawer, the Glass Box file and, later, the live app. Each item is a place a sub-task can read or write. You cannot delegate safely until this list exists.

Picture it: Before a deep clean you walk the lab and list every bench, cupboard and drain. The list is the surface.
The trap: Mapping only the tools you wrote and forgetting the files and stores they write to.
In Formulaite: formulaite_tools.py names the surface: the catalogue JSON, the stubbed supplier pages and fill_drawer; glassbox.py adds the saved run file.
04Sub-questions from the drawer ch 2

Decomposition means turning one goal into small questions with a known answer shape. Formulaite already has the shape: the drawer's required sections. Each section becomes one sub-question. Each sub-question maps to one or two tools.

Picture it: A recipe card has fixed boxes: phase, percentage, pH. You fill boxes, you do not write an essay.
from agent_lab.drawer import IngredientDrawer

def sub_questions(inci: str) -> list[str]:
    return [f"{inci}: what is the {s.replace('_', ' ')}?"
            for s in IngredientDrawer.REQUIRED_SECTIONS
            if s != "sources"]

# ['Glycerin: what is the inci name?',
#  'Glycerin: what is the function?', ...]
The section list is the decomposition; no clever planner needed.
The trap: Letting the model invent its own sub-questions, so every run splits the work differently.
In Formulaite: drawer.py: REQUIRED_SECTIONS is the fixed list of sub-questions; missing() tells you which are still open.
05Delegate only independent parts ch 2

Split work only where the parts are independent. Function and pH range can be researched apart. Use level depends on function, so keep those two together. If sub-agents keep contradicting each other, the split was wrong.

Picture it: Two people can weigh the water phase and the oil phase at once. They cannot both stir the same pot.
The trap: Delegating dependent questions and then paying to reconcile the answers.
In Formulaite: drawer.py: group REQUIRED_SECTIONS into two or three briefs, keeping typical_use_level and use_level_pct in the same brief.
06Controls ranked by blast radius ch 3

You cannot check everything equally. Rank controls by how much damage a wrong action does. The strongest control goes where writes happen. Lighter checks cover proposals. Reads get logging and a step budget, nothing more.

Picture it: The fume cupboard gets the alarm. The pencil drawer does not.
The trap: Spending the review budget on harmless reads and leaving the write path with the least attention.
In Formulaite: gates.py holds the strong controls for the drawer; agent.py's max_steps is the light control on reads.
07Deterministic gate first ch 3

The first control on any proposal is plain code, not another model call. It compares the drawer to the catalogue and to fixed rules. It returns pass or fail with reasons. Only a passing drawer reaches a human. This keeps human time for real decisions.

Picture it: A sieve before the microscope. Lumps get caught by the mesh; only fine powder gets the expert's eye.
from agent_lab.gates import run_gates

verdict = run_gates(drawer, catalogue_entry=entry)
if not verdict:
    # send reasons back to the model and loop again
    print(verdict.reasons)
else:
    ask_human(drawer)   # only now
The verdict is truthy on pass; reasons are a plain list of strings.
The trap: Asking the model to review its own drawer and calling that a gate.
In Formulaite: gates.py: run_gates and the check_* functions; agent.py calls it every time fill_drawer is invoked.
08Step budget as a control ch 3

A budget is the simplest control. Each brief carries a maximum number of tool calls. When it runs out the sub-agent stops and reports what it has. A budget cannot be argued with, so it is the control you trust when nothing else fires.

Picture it: A timer on the mixer. It stops whether or not the cream looks ready.
The trap: One global budget for the whole run, so a slow sub-question starves the others.
In Formulaite: agent.py: max_steps is the budget; give each sub-run its own, smaller one.
09Role, context, constraints brief ch 4

The book's practice lab is one prompt shape: role, context, constraints. That shape is the input standard for every delegation. Role says who the sub-agent is. Context gives the facts it needs. Constraints say what it may not do and when to stop.

Picture it: A job sheet for a temp: what you are, what you are given, what you must not touch.
SYSTEM = """Role: ingredient researcher for Formulaite.
Context: INCI {inci}. Catalogue entry: {entry}.
Constraints:
- read only; never invent a number
- cite a source url for every section
- if the page contradicts the catalogue, stop and say so
- at most {budget} tool calls"""
Three labelled blocks; the constraints block is where control lives.
The trap: Writing a long friendly prompt with no constraints block, then blaming the model for over-reaching.
In Formulaite: agent.py builds the system prompt; make it these three blocks so every sub-run starts from the same standard.
10Delegation contract ch 4

Delegation is a contract, not a wish. Write down what goes out and what must come back. Out: the sub-question, the allowed tools, the step budget, the output shape. Back: values, sources, confidence, open questions. If a return does not match, the coordinator rejects it.

Picture it: A purchase order lists the item, the spec and the delivery date. The goods are checked against the order, not against memory.
@dataclass(frozen=True)
class Brief:                      # what goes out
    inci: str
    sections: tuple[str, ...]
    tools: tuple[str, ...] = ("catalogue_lookup", "read_supplier_page")
    max_steps: int = 4
@dataclass
class Handoff:                    # what must come back
    values: dict[str, str]
    sources: list[str]
    confidence: float
    open_questions: list[str] = field(default_factory=list)
Brief is frozen so a sub-agent cannot widen its own scope; Handoff is what comes back.
The trap: Delegating with a sentence of prose and accepting whatever text comes back.
In Formulaite: tools.py: a Tool's input_schema is the contract with the model; a Brief dataclass does the same job for a sub-agent run.
11Human review gate placement ch 5

A human gate is a checkpoint where a person must say yes before the agent continues. Put it where writes happen and nowhere else. One gate at the catalogue write is stronger than five gates on reads. Too many gates and the reviewer stops reading.

Picture it: One signature on the batch release form, not a signature every time someone opens a jar.
The trap: Putting a human gate on every step, which trains the reviewer to click approve without looking.
In Formulaite: agent.py: after run_gates passes and before any catalogue write, call an approve() function; gates.py stays deterministic.
12What the reviewer sees ch 5

A gate is only as good as the screen the human sees. Show the proposed drawer, the reasons the gate passed, the sources used, and what will change. Keep it to one screen. Offer three answers: approve, edit, reject with a reason.

Picture it: A pharmacist checks the label, the dose and the prescription side by side. Not a chat log.
def approve(drawer, verdict, box) -> bool:
    print("INCI:", drawer.inci_name)
    print("Use level:", drawer.typical_use_level)
    print("Sources:", *drawer.sources, sep="\n  ")
    print("Gate:", "PASS" if verdict else verdict.reasons)
    answer = input("approve / edit / reject: ").strip()
    box.log("human_gate", drawer.inci_name, answer=answer)
    return answer == "approve"
Everything the decision needs is printed before the question; the answer is logged.
The trap: Showing the human the raw conversation and calling that transparency.
In Formulaite: glassbox.py records the human answer as an Event; the Formulaite app renders the same fields as a review card.
13Least privilege per sub-task ch 6

Each sub-task gets only the tools it needs. Research sub-runs get read tools. Only the coordinator holds the write tool, and only after the human gate. Hardening access this way means a confused sub-agent cannot do damage.

Picture it: The intern has a key to the library, not to the raw-materials store.
from agent_lab.tools import ToolRegistry
from agent_lab.formulaite_tools import build_registry

full = build_registry()
read_only = ToolRegistry(*(t for t in full
                          if t.name != "catalogue_write"))

sub_agent = Agent(model=model, tools=read_only, max_steps=4)
A second registry built from the first; the write tool never reaches the sub-agent.
The trap: Handing every sub-agent the full registry because it is easier.
In Formulaite: tools.py: ToolRegistry accepts any subset of tools, so a read-only sub-run is a one-line filter.

01Save the trace before you act ch 7

Backup means you can get back to a known state. Save the Glass Box before any write. Keep the old catalogue entry beside the new one. If the write turns out wrong, you replay the run and restore the old entry.

Picture it: Photograph the formula sheet before you correct it in pen.
box.save(f"runs/{run_id}.json")          # before the write
old = catalogue_entry(drawer.inci_name)
backup[drawer.inci_name] = old
catalogue_write(drawer)

# rollback
catalogue_write_raw(backup[drawer.inci_name])
The save happens before the write, so a crash mid-write still leaves a trace.
The trap: Saving the trace only when the run succeeds, which loses exactly the runs you need.
In Formulaite: glassbox.py: GlassBox.save and GlassBox.load are the backup and the replay.
02Operational signals ch 8

Track a few numbers per run so drift is visible. Steps used, gate failures, retries, human override rate, tokens. A rising override rate means the drawers are getting worse. Alert on thresholds instead of reading every trace.

Picture it: Batch records track viscosity and pH each run. One number drifting tells you before a customer does.
The trap: Collecting a dashboard of twenty metrics that nobody reads.
In Formulaite: glassbox.py: count of_kind('gate_fail') and of_kind('human_gate') per saved run; memory.py's token_estimate gives the cost line.
03Incident drills ch 9

Do not wait for a bad supplier page in production. Rehearse it. Make the model fail its first drawer on purpose. Feed a page that contradicts the catalogue. Watch the gate catch it, watch the escalation fire, and time how long recovery takes.

Picture it: A fire drill. Everyone learns where the exits are while nothing is burning.
from agent_lab.models import ScriptedModel
from agent_lab.agent import Agent

agent = Agent(model=ScriptedModel(fail_first=True),
              tools=build_registry(), max_steps=6)
result = agent.run("Glycerin")
assert result.ok
assert len(result.box.of_kind("gate_fail")) == 1
fail_first forces one bad drawer; the assert proves the gate caught it.
The trap: Testing only the happy path, so the first real failure is also the first drill.
In Formulaite: models.py: ScriptedModel(fail_first=True) is the built-in drill; scripts/check_gate_control.py runs it.
04Repeatable checks as code ch 10

Any check you run twice by hand should become a function. Store the checks in a list. Run the list every time. New rules are new functions, not new prompt text. This is what lets the gate grow without getting fragile.

Picture it: A pre-flight checklist printed and clipped to the dash, not remembered.
CHECKS = [
    check_all_sections_filled,
    check_inci_matches,
    check_use_level_in_range,
    check_not_banned,
    check_has_sources,
]
reasons = [r for c in CHECKS if (r := c(drawer, entry))]
Functions as values in a list; the comprehension keeps only the failures.
The trap: Adding rules to the prompt instead of the check list, so nobody can test them.
In Formulaite: gates.py: run_gates loops over exactly this kind of list; scripts/check_*.py are the repo-level version.
05Handoff packet ch 11

When a sub-agent finishes it must hand back a fixed packet. Status, values, sources, confidence, open questions. The coordinator merges packets into one drawer. A packet with low confidence or open questions becomes an escalation, not a guess.

Picture it: A shift handover note: what was done, what was measured, what is still unclear.
def merge(packets: list[Handoff]) -> IngredientDrawer:
    values, sources = {}, []
    for p in packets:
        if p.confidence < 0.6 or p.open_questions:
            raise Escalate(p.open_questions)
        values.update(p.values)
        sources += p.sources
    return IngredientDrawer.from_model_input(**values, sources=sources)
Merging stops at the first weak packet; the coordinator never fills a gap itself.
The trap: Accepting free-text summaries from sub-agents and letting the coordinator paper over the gaps.
In Formulaite: drawer.py: from_model_input is the merge target; agent.py's _handle_answer is where packets would be merged.
06Coordinator that never solves ch 11

The coordinator splits the goal, sends briefs, collects packets, merges and gates. It never answers a sub-question itself. If it starts filling gaps, delegation has failed and you should collapse back to one agent. Keep it boring.

Picture it: A head chef plates and checks. The moment they are chopping onions, the kitchen is understaffed.
def coordinate(inci: str) -> IngredientDrawer:
    packets = [run_sub_agent(Brief(inci, (s,)))
               for s in IngredientDrawer.REQUIRED_SECTIONS
               if s != "sources"]
    drawer = merge(packets)
    verdict = run_gates(drawer, catalogue_entry=catalogue_entry(inci))
    if not verdict:
        raise Escalate(verdict.reasons)
    return drawer
Four verbs: brief, collect, merge, gate. No research happens in this function.
The trap: A coordinator with its own read tools that quietly does the research itself.
In Formulaite: agent.py: Agent is a single loop today; a coordinate() wrapper above it would run one Agent per brief.
07Escalation packet for humans ch 11

Handoff to a human is also a protocol. When the agent stops early, it sends what it tried, what it found, and one clear question. The human should be able to answer in under a minute. No raw logs, no apology paragraphs.

Picture it: A lab tech asks: 'Catalogue says 5 percent, supplier says 10. Which one?' Not: 'I am confused about glycerin.'
The trap: Escalating with 'something went wrong' and the whole conversation attached.
In Formulaite: agent.py: when max_steps is hit or the gate fails twice, build the packet from box.of_kind('gate_fail') and the last tool results.
08Quality, speed, edit effort ch 12

The book's review prompt names three measures: quality, speed and edit effort. Trust is earned when all three improve. Quality is gate pass rate and reviewer approval. Speed is steps and seconds. Edit effort is how much the human changed before approving.

Picture it: A junior formulator is trusted when their sheets need fewer red-pen marks each month.
The trap: Measuring only speed, which rewards agents that guess fast.
In Formulaite: glassbox.py: log the human's edited drawer beside the proposed one so edit effort is a diff, not an opinion.
09Version drift control ch 13

Prompts, models, catalogues and gate rules all change. If you cannot say which versions produced a drawer, you cannot explain a change in quality. Stamp every run with the version of each. Compare runs only within the same stamp.

Picture it: Every batch record names the raw-material lot numbers. Change one lot and you know where to look.
STAMP = {
    "prompt": "rcc-v3",
    "model": DEFAULT_MODEL,
    "catalogue": catalogue_version(),
    "gates": "2026-09",
}
box.log("versions", inci, **STAMP)
One event at the start of every run carries every version in its meta.
The trap: Swapping the model and the prompt in the same week, then arguing about which one broke things.
In Formulaite: models.py: the ScriptedModel or ClaudeModel flag is one version; log it with the others in glassbox.py.
10Habit loop: act, practise, review, checkpoint ch 14

Every chapter ends with the same four moves. Take one action. Run one practice. Review the output. Ask one checkpoint question. Applied to an agent, this is a weekly rhythm: ship one change, run the scenarios, read five traces, ask what to adjust.

Picture it: A weekly stock-take. Same list, same day, so nothing is forgotten.
The trap: Big review sessions every quarter instead of small ones every week.
In Formulaite: Keep a runs/ folder from glassbox.py saves and read five at random each week; write the checkpoint answer in docs/.
11Edge cases: missing, ambiguous, contradictory ch 15

Three edge shapes cover most trouble. Missing: the INCI is not in the catalogue. Ambiguous: two names for one ingredient. Contradictory: the supplier page disagrees with the catalogue. Each needs a named outcome, not a guess. Contradiction means re-decompose or escalate.

Picture it: An unlabelled jar, two jars with the same label, or a label that disagrees with the certificate.
The trap: Treating every edge case as a retry.
In Formulaite: formulaite_tools.py: catalogue_lookup returns a string when missing; gates.py check_use_level_in_range catches contradiction.

01Fewer, simpler paths ch 16

Every branch in the workflow is a place to get lost. Merge overlapping tools. Keep one escalation path. Keep one approval screen. A support workflow with three routes is easier to trust than one with twelve.

Picture it: One clearly marked exit beats six unmarked doors.
The trap: Adding a special route for every new edge case until nobody can draw the flow.
In Formulaite: formulaite_tools.py keeps three tools; resist a fourth until a scenario proves the three cannot cover it.
02Measurable quarterly targets ch 17

Set a small number of targets for the agent each quarter. Gate pass rate above a line. Override rate below a line. Cost per drawer under a number. Targets turn 'the agent seems better' into a yes or no.

Picture it: This quarter: batch rejects under two percent. Everyone knows if it happened.
The trap: Ten targets, none owned, none measured.
In Formulaite: A scripts/report_runs.py that reads glassbox.py saves and prints the three numbers against the targets.
03One-page governance ch 18

Governance can be one page. Who may approve a catalogue write. Which actions run alone. Which never will. Who reviews traces and how often. Lightweight means readable in five minutes and enforced by code where possible.

Picture it: The lab safety sheet on the wall, not a forty-page binder in a cupboard.
POLICY = {
    "auto": {"catalogue_lookup", "read_supplier_page", "fill_drawer"},
    "human_gate": {"catalogue_write"},
    "never": {"catalogue_delete", "publish_to_app"},
}

def allowed(tool: str) -> str:
    return next(k for k, v in POLICY.items() if tool in v)
The policy is data the loop reads; changing governance is a one-line diff.
The trap: Writing policy in a document that the code never reads.
In Formulaite: gates.py: a policy dict beside the checks; agent.py consults it before every tool call.
04Scenario validation ch 19

A scenario is one full path through the decomposition. Happy path. Missing INCI. Contradicting page. Reviewer rejects. Each scenario has an expected outcome and an expected trace shape. Run all scenarios before any change ships.

Picture it: Stability testing: the same cream through heat, cold and light, with a pass line for each.
SCENARIOS = {
    "happy":      ("Glycerin", True),
    "missing":    ("Unobtainium", False),
    "contradict": ("Niacinamide", False),
}
for name, (inci, expect_ok) in SCENARIOS.items():
    r = Agent(model=ScriptedModel(), tools=build_registry()).run(inci)
    assert r.ok == expect_ok, name
Each scenario is a name, an input and an expected verdict.
The trap: Validating with one ingredient that always worked.
In Formulaite: scripts/check_offline_run.py is scenario one; add a scenarios/ folder that agent.py runs the same way.
05Sustaining the practice ch 20

A control that nobody runs decays. Retire checks that never fire. Keep the ones that catch things. Rotate who reads traces. Review the governance page each quarter. The aim is a small set of habits that survive a busy month.

Picture it: Calibration reminders in the calendar, not in someone's head.
The trap: Adding controls forever and never removing one.
In Formulaite: Keep the check list in gates.py short; delete a check_* function when a quarter of runs never triggers it.
06Staged promotion for new tools ch 21

A new tool enters at the lowest risk tier. First sandboxed with stub data. Then read-only in real runs. Then allowed to propose. Only after scenarios pass does it touch a write. Each stage is a governance decision, not a code change.

Picture it: A new supplier ships a sample first, then a pilot lot, then a full order.
STAGE = {"web_search": "sandbox"}   # sandbox -> read -> propose -> write

def promote(tool: str, scenarios_passed: bool) -> None:
    order = ["sandbox", "read", "propose", "write"]
    if scenarios_passed:
        STAGE[tool] = order[order.index(STAGE[tool]) + 1]
The stage list is the only path a tool can take upward.
The trap: Plugging a live web tool straight into the write path because the demo looked good.
In Formulaite: formulaite_tools.py: read_supplier_page is stubbed with local files, which is the sandbox stage; a live fetch would be the next stage.
07Policy becomes code and prompt ch 22

A policy that lives only in a document does nothing. Each policy line should exist twice. Once in the prompt's constraints block so the model knows. Once in a gate check so the code enforces. When the two disagree, the code wins.

Picture it: The sign says 'goggles on'. The door also will not open without the badge.
# policy line: never claim an ingredient treats a disease
CONSTRAINT = "Never state that an ingredient treats or cures a condition."

def check_no_forbidden_claims(drawer, entry):
    text = " ".join(str(getattr(drawer, n))
                    for n in drawer.REQUIRED_SECTIONS)
    if any(w in text.lower() for w in ("cures", "treats")):
        return "forbidden medical claim"
Same rule, two homes: the prompt and the check.
The trap: Trusting the prompt to enforce a policy the gate never checks.
In Formulaite: gates.py: check_no_forbidden_claims already exists; add the matching line to agent.py's system prompt.

Vocabulary

TermMeans

Risk tierRead, propose or write; decides how much control an action gets.
System surfaceEvery store, page and file the agent can read or write.
Sub-questionOne drawer section phrased as a question with a known answer shape.
Delegation briefWhat goes out: sub-question, allowed tools, budget, output shape.
Handoff packetWhat comes back: values, sources, confidence, open questions.
CoordinatorThe part that briefs, collects, merges and gates; it never researches.
Sub-agentA small loop with read tools, one brief and its own budget.
Deterministic gatePlain code that passes or fails a drawer with reasons.
Human review gateA checkpoint where a person approves, edits or rejects before a write.
Least privilegeEach sub-task gets only the tools it needs.
Step budgetA hard cap on tool calls per brief.
EscalationStopping early and handing a human one clear question.
Operational signalA per-run number such as gate failures or override rate.
Override rateHow often the human changes or rejects what the gate passed.
Version stampPrompt, model, catalogue and gate versions logged per run.
Incident drillA rehearsed failure run to prove gates and escalation work.
ScenarioOne full path through the decomposition with an expected outcome.
Staged promotionSandbox, read, propose, write; a new tool climbs one step at a time.
Governance pageOne page saying who approves what and what is never automated.

The pattern

  1. Write the scope: one INCI, one drawer.
  2. Split into sub-questions from REQUIRED_SECTIONS; keep dependent ones together.
  3. Brief each sub-question: role, context, constraints, read tools, budget.
  4. Collect handoff packets; escalate any with low confidence or open questions.
  5. Merge into a drawer and run the deterministic gate.
  6. Show the human one screen: drawer, reasons, sources; approve, edit or reject.
  7. Write to the catalogue only after approval; save the trace first.

Decisions

WhenUseNot
Sub-questions are independentone brief per group, run side by sideone long loop
One section depends on another, like use level on functionone brief covering bothtwo sub-agents that must reconcile
An action only readslogging and a step budgeta human gate
An action writes to the cataloguedeterministic gate, then human gateeither one alone
A packet has low confidence or open questionsescalate with one clear questionlet the coordinator guess
Quality drops after a changecompare runs within the same version stampargue from memory
A new tool looks usefulsandbox, then read, then propose, then writestraight into production
The coordinator keeps filling gaps itselfcollapse back to one agentmore sub-agents

Rules of thumb

DoDon't
Write the scope sentence before writing any prompt.Start from 'research this ingredient'.
Derive sub-questions from the drawer's fixed sections.Let the model invent the split each run.
Give every brief a budget, a tool list and an output shape.Delegate with a sentence of prose.
Put the human gate where the write happens.Gate every read.

Give sub-agents read tools only.Pass the full registry for convenience.
Save the Glass Box before every write.Save only successful runs.

Promote a new tool one stage at a time.Wire a live tool straight into the write path.

def coordinate(inci: str) -> IngredientDrawer:
    groups = [("inci_name", "function", "typical_use_level", "use_level_pct"),
              ("phase_and_solubility", "ph_range"),
              ("compatibility", "safety_notes")]
    packets = [run_sub_agent(Brief(inci, g)) for g in groups]
    drawer = merge(packets)                      # escalates on weak packets
    verdict = run_gates(drawer, catalogue_entry=catalogue_entry(inci))
    if not verdict:
        raise Escalate(verdict.reasons)
    return drawer

Human gate before the write

def publish(drawer, verdict, box, ask=input) -> str:
    box.save(f"runs/{box.run_id}.json")          # backup first
    print(drawer.to_dict()); print("gate:", verdict.reasons or "PASS")
    answer = ask("approve / edit / reject: ").strip()
    box.log("human_gate", drawer.inci_name, answer=answer)
    if answer != "approve":
        return answer
    catalogue_write(drawer)
    return "written"

Before you ship

  • Scope sentence written and it matches Agent.run's single INCI argument.
  • Every drawer section maps to a sub-question and a tool.
  • Every brief has a budget, a tool list and an output shape.
  • Sub-agents hold read tools only; the write tool sits behind the human gate.
  • The reviewer screen shows drawer, gate reasons and sources, with approve, edit, reject.
  • Glass Box saved before every write; the rollback path tested once.
  • Version stamp logged on every run.
  • Scenarios for happy, missing, contradicting and rejected paths pass before shipping.
06 · You're done when…
  1. Turn one INCI request into a list of Briefs from REQUIRED_SECTIONS, run each with a read-only ToolRegistry, and merge the Handoff packets into one drawer.
  2. Add a human gate before the catalogue write that shows drawer, gate reasons and sources, and prove from the Glass Box that a reject stopped the write.
  3. Run four scenarios (happy, missing, contradicting, rejected) with a version stamp on each and report three numbers: gate pass rate, override rate, steps per drawer.
