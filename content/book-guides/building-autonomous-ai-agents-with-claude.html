01 · Where this is going

An agent is a loop of reason, act, observe; every design choice exists to make one of those three parts more bounded, more inspectable, or more reliable.

Read this book when: Open it when the Formulaite research agent 'works' but you cannot say why it stopped, why it picked a tool, or whether it is safe to let it run alone.

01Answering versus acting ch 1

A normal model call returns text and stops. An agent's output makes something happen, and the result goes back to the model for the next decision. That feedback loop, not a clever prompt, is what makes it an agent. The risk moves too: a wrong action has already happened before anyone reviews it.

Picture it: A recipe card tells you what to do. A kitchen robot that stirs, tastes and adjusts the heat is acting. Only the second one can burn the pot.
The trap: Calling a long single prompt an 'agent' sets expectations of self-correction the system cannot deliver.
In Formulaite: agent.py is the acting side: the model's tool_use blocks are executed and the results fed back, so Formulaite research is a real loop.
02The autonomy spectrum ch 1

Autonomy is a dial, not a switch. The book names four stops: suggestion loop, bounded loop, checkpointed loop, fully autonomous. Pick the stop per action type with two questions: how reversible is it, and how costly is human review? One system can sit at different stops for different actions.

Picture it: Reading a supplier page is reversible, so let the agent do it alone. Publishing an ingredient to the live catalogue is not, so a person approves it.
The trap: Setting one autonomy level for the whole agent instead of one per action category.
In Formulaite: gates.py is where each Formulaite action gets its stop: reads run free, fill_drawer must pass the gate, catalogue writes wait for a person.
03Does this task need an agent? ch 1

Write the steps down before building. If you can list them all in advance, it is a workflow, and a workflow is cheaper and easier to debug. If the next step depends on what a search or a page returns, you need a loop. The middle option is a workflow with a few judgment points.

Picture it: Making tea is a fixed recipe. Working out why a batch of cream separated is a loop, because each test tells you what to try next.
The trap: Building a full loop that always takes the same path, paying agent cost for workflow behaviour.
In Formulaite: formulaite_tools.py fixes the shape (look up, read page, fill drawer) and agent.py adds judgment only where the supplier page is unknown.
04The reason-act-observe loop ch 2

Every agent is one cycle repeated. Reason about what to do next. Act by calling a tool. Observe the result. The observation becomes input for the next reasoning step, and the cycle repeats until a stopping condition fires.

Picture it: A formulator checks the viscosity, adds a little thickener, and checks again. Think, do, look. Repeat until the cream is right.
def run(goal, model, tools, max_steps=8):
    history = [goal]
    for step in range(max_steps):
        reply = model.reason(history)                 # reason
        if reply.is_final:
            return reply.answer
        result = tools.call(reply.tool, **reply.args)  # act
        history.append(result)                        # observe
    return "stopped: step budget hit"
One loop body, three lines that matter: reason, act, observe.
The trap: Logging only the action, so you cannot tell a bad decision from a bad execution.
In Formulaite: agent.py: Agent.run is this loop, and every reason, act and observe lands in glassbox.py as an Event.
05Three named failure modes ch 2

Each part of the loop fails differently. Reasoning failure: the wrong action was chosen, but it ran fine. Acting failure: the right intent, but the call was malformed. Observation failure: the action worked, but the result came back truncated, mislabelled or missing. Naming which one broke is most of debugging.

Picture it: Ordering the wrong ingredient is a reasoning failure. Typing the order code wrong is an acting failure. An unreadable delivery note is an observation failure.
The trap: Saying 'the agent got confused' instead of naming which of the three parts failed.
In Formulaite: glassbox.py tags each Event by kind, so a wrong search query and a broken page parse look different in the replay.
06Layered stopping conditions ch 2

A loop with no stop rule is not autonomous, it is unbounded. Use three families together. Goal-based: the model judges the task done. Resource-based: a hard ceiling on steps, time or cost. Escalation-based: pause and hand to a human when uncertain. Check escalation before the ceiling fires.

Picture it: A kitchen timer, a taste test, and a rule to call the head chef if the sauce looks odd. You want all three running at once.
MAX_STEPS = 8
for step in range(1, MAX_STEPS + 1):
    reply = model.complete(system, messages, tools)
    if reply.confidence < 0.6:            # escalation, checked first
        result = escalate(reply); break
    if reply.is_final and gate(reply):    # goal-based
        result = reply; break
else:
    result = "budget_exhausted"           # resource ceiling
The for-else: the else branch runs only when the loop was never broken out of.
The trap: Trusting the goal check alone; a model that is subtly wrong will confidently declare itself done.
In Formulaite: agent.py already has max_steps and the gate; the escalation trigger is the missing third layer to add.
07Instrument before it works ch 2

Decide what to log before the agent runs, not after. Store reasoning text, tool parameters and observation content as three separate records with a timestamp and an id. Tag each record by decision type, such as lookup, write or escalation check. Instrument for the failure you have not seen yet.

Picture it: A flight recorder is fitted before take-off, not after the crash.
@dataclass
class Event:
    step: int
    kind: str                     # "reason" | "act" | "observe" | "gate"
    tags: tuple[str, ...] = ()
    meta: dict = field(default_factory=dict)
    ts: float = field(default_factory=time.time)
One Event per part of the loop. kind and tags make the log filterable later.
The trap: Adding logging after launch, when the incident that needed the trace has already happened.
In Formulaite: glassbox.py is exactly this: GlassBox.log(kind, *tags, **meta) writes one Event per decision and replay() plays them back.
08A tool schema is a contract ch 3

The schema is the model's entire view of a tool. A vague description does not produce a vague call; it produces a confident, specific, wrong one. A good schema says what the tool achieves, what each parameter means and its valid range, what happens at the edges, and when to prefer this tool over its neighbours.

Picture it: A label on a raw-material drum. 'Acid' is useless. 'Citric acid 50 percent, use at 0.1 to 0.5 percent, never mix with bleach' lets a new hire use it safely.
@registry.tool(
    description=(
        "Return the catalogue entry for ONE ingredient by INCI name. "
        "Use this before reading any supplier page. "
        "Unknown names return an empty entry, not an error."
    ),
)
def catalogue_lookup(inci: str) -> str:
    """inci: exact INCI name, e.g. 'Glycerin'. Case-insensitive."""
    ...
The description states an outcome, a preferred use, and edge behaviour.
The trap: Writing the description for a developer who has seen the code, not for a model that has not.
In Formulaite: tools.py builds the input_schema from the function signature, so the description and docstring in formulaite_tools.py are the contract.
09Fewer, clearer tools ch 3

Every extra tool is one more distinction the model must make at call time. Overlapping tools cause the 'almost right' call. That is a selection failure, not a reasoning failure. Fix it by merging near-duplicates or rewriting descriptions so their uses cannot overlap. Audit every pair of tools periodically.

Picture it: Three spatulas that all sort of fit the pot. You grab the wrong one every time. One spatula per job ends the confusion.
The trap: Adding prompt instructions about which tool to prefer instead of fixing the tool set.
In Formulaite: formulaite_tools.py keeps three tools with no overlap: catalogue_lookup, read_supplier_page and fill_drawer.
10Test tools in isolation ch 3

Call each tool directly before wiring it to the model. Use edge inputs: empty strings, bad ids, huge pages. Trigger the error paths on purpose and check the error is clear. If a tool misbehaves under direct testing, no schema tuning will fix the agent. Re-run these tests regularly because tools drift.

Picture it: Test the oven with a thermometer before blaming the recipe.
def test_read_supplier_page_bad_url():
    with pytest.raises(ToolError) as err:
        registry.call("read_supplier_page", url="not-a-url")
    assert "url" in str(err.value).lower()

def test_catalogue_lookup_unknown_is_empty():
    assert registry.call("catalogue_lookup", inci="Nonexistium") == ""
Two direct calls, no model. One checks the error path, one checks the empty case.
The trap: Assuming a tool works because the agent used it successfully once.
In Formulaite: tools.py's ToolRegistry.call lets you hit each Formulaite tool from a test file with no model in the loop.

01Extended thinking budget ch 2

Extended thinking lets the model reason longer before acting. It pays off only on steps that are both ambiguous and high-stakes. Simple steps just get slower. If a step keeps failing despite plenty of thinking, fix the observation feeding it first.

Picture it: You do not deliberate over which spoon to use. You do deliberate before swapping a preservative in a product already on the shelves.
The trap: Turning thinking up everywhere and buying latency, not better decisions.
In Formulaite: models.py's ClaudeModel is where a thinking budget would be set, and only for the fill_drawer decision, not for lookups.
02Narrow tools and MCP for reuse ch 3

'Look up an order by id' is safer than 'run any SQL', because the tool itself limits what can happen. Use general tools only in open-ended domains, and wrap them in scope limits, a dry-run mode or an approval gate. MCP standardises how a model finds and calls tools on a server. Its value is reuse, so adopt it when more than one agent needs the connection.

Picture it: A pipette fixed at 1 ml versus an open jug. The narrow tool cannot overpour.
The trap: Choosing MCP for a one-off connection that only one agent will ever use.
In Formulaite: formulaite_tools.py's read_supplier_page reads one page by url; a shared supplier-page MCP server matters once the catalogue app needs it too.
03Steps you can verify ch 4

A goal like 'research glycerin' is not executable. Break it into steps, each with its own success evidence. A step is small enough only when you can say what would prove it done. Write the assumption each step rests on, and what to do if its check fails.

Picture it: 'Copy the users table, then confirm the row count and ten sample records match' is checkable. 'Migrate the table' is not.
The trap: Steps that are each verifiable but together miss what the original goal required.
In Formulaite: drawer.py's REQUIRED_SECTIONS are the verifiable steps: each section either has content and a source or it does not, and gates.py checks each one.
04Hybrid planning ch 4

Plan-then-execute makes the whole plan first, then follows it. Easy to review, brittle when reality differs. Interleaved planning replans after every step. It adapts well but can drift. Use both: a reviewable plan per phase, replanning inside each phase. Put phase boundaries at real milestones you can verify.

Picture it: Plan the whole product launch on paper, but let the lab adjust the batch on the day.
The trap: Drawing phase boundaries to keep plans short rather than at points where progress can be checked.
In Formulaite: agent.py could hold a phase plan (find sources, extract facts, fill drawer) while models.py replans within each phase.
05Premise failure is a legal outcome ch 4

Some plan mismatches mean the plan's basic premise was wrong. The sign is escalating departures, each step needing a bigger patch. The right move is to stop and re-decompose. Give the model explicit permission to return 'needs re-decomposition' alongside 'done' and 'failed'.

Picture it: If every stability test reveals a new incompatible ingredient, the formula concept is wrong. Stop patching and reformulate.
The trap: Telling the model to be persistent, so it patches forever instead of admitting the plan is broken.
In Formulaite: drawer.py could carry a status field with a needs_redecomposition value that gates.py treats as an honest stop, not a failure.
06Context window versus memory ch 5

The context window is what the model sees on this call. Memory is a store you write to and read from on purpose. Treat context as small, curated working memory. Write a fact to memory the moment you learn it, sorted into facts, decisions with reasons, and open questions.

Picture it: Your desk holds today's papers. The filing cabinet holds everything else, in labelled folders.
memory = {"facts": {}, "decisions": [], "open_questions": []}

def learn(kind, key, value=None, why=None):
    if kind == "fact":
        memory["facts"][key] = value           # e.g. CAS number
    elif kind == "decision":
        memory["decisions"].append((key, value, why))
    else:
        memory["open_questions"].append(key)
Three buckets, written at the moment of discovery, not in a later clean-up pass.
The trap: Stuffing every past message into every call until the window is full of noise.
In Formulaite: memory.py's Conversation is the context window; a separate facts store beside it would be Formulaite's persistent memory.
07Summarise prose, keep facts verbatim ch 5

Long runs must be summarised. Narrative, meaning what was tried and why, compresses well. Exact identifiers, numbers and error messages do not, because their whole value is the exact text. Keep them in a small key-facts table beside the summary. Re-summarise from the raw log, never from the last summary.

Picture it: You can paraphrase the story of the batch. You cannot paraphrase the CAS number.
@dataclass
class KeyFacts:
    cas_number: str | None = None
    supplier_url: str | None = None
    last_error: str | None = None      # exact text, never paraphrased

summary = "Tried two supplier pages; the first one failed."
facts = KeyFacts(cas_number="56-81-5", last_error="404 on /glycerin")
Prose in one place, exact values in a typed record right next to it.
The trap: A summary of a summary of a summary, each round dropping something.
In Formulaite: memory.py's token_estimate tells you when to summarise; a KeyFacts record in drawer.py keeps the CAS numbers safe.
08State drift and re-verification ch 5

State drift is acting on a picture of the world that has changed. The agent looks confident and coherent, just wrong. It happens on long runs, shared resources and after pauses. The defence: right before any consequential action, re-check the specific facts that action depends on.

Picture it: You checked the stock room this morning. Before starting the batch, check again; someone may have used the last drum.
def publish_ingredient(drawer):
    entry = catalogue_lookup(drawer.inci)   # fresh read, right now
    if entry.get("banned"):
        return escalate("ingredient is now banned")
    return catalogue.write(drawer)
The lookup happens immediately before the write, not at the start of the run.
The trap: Trusting a belief because the model states it confidently.
In Formulaite: gates.py's run_gates(drawer, catalogue_entry=...) should receive a fresh catalogue read, not the one from step one.
09Resumable step ledger ch 5

A long task may be paused or crash. Persist the task's own progress: which steps are verified, in flight, or not started. On resume, never just continue. Re-verify every in-flight step first. Idempotent actions make this easy, because any uncertain step can simply be redone.

Picture it: A lab notebook with a tick, a dash or a blank next to every step. After lunch you know exactly where you were.
ledger = {"lookup": "verified", "read_page": "in_flight",
          "fill_drawer": "not_started"}

def resume(ledger):
    for step, status in ledger.items():
        if status == "in_flight":
            ledger[step] = verify_or_redo(step)
    return next(s for s, st in ledger.items() if st != "verified")
Three statuses only. In-flight steps get re-verified before anything else moves.
The trap: Resuming from where the process 'happened to be' with no record of what was half-done.
In Formulaite: glassbox.py's save and load already persist the run; a ledger dict in agent.py's RunResult would make a Formulaite run resumable.
10Transient versus deterministic failures ch 6

A timeout or a rate limit will probably clear, so retry it. Invalid input, a missing resource or permission denied will fail the same way every time, so never retry, escalate. Label every error at the point the tool is defined, so the loop never guesses from error text.

Picture it: The supplier's phone line is busy: call back. The supplier does not stock the item: calling back changes nothing.
class ErrorKind(Enum):
    TRANSIENT = "transient"
    DETERMINISTIC = "deterministic"

class ToolError(Exception):
    def __init__(self, msg, kind=ErrorKind.DETERMINISTIC):
        super().__init__(msg)
        self.kind = kind

raise ToolError("supplier page timed out", ErrorKind.TRANSIENT)
The kind travels with the exception, so the caller never parses the message.
The trap: Retrying a deterministic failure with small variations, guessing your way into risk.
In Formulaite: tools.py's ToolError is where the transient flag belongs; agent.py's _handle_tool then retries only transient ones.
11Safe retries ch 6

Even a transient failure needs structure. Wait longer between attempts, doubling each time. Cap the attempts. Make actions idempotent with an operation id, so a repeat has the same net effect. If that is impossible, check the current state before retrying.

Picture it: If the order form might have gone through, check the order list before submitting it again. Otherwise you get two deliveries.
def retry(fn, attempts=3, base=0.5):
    for n in range(attempts):
        try:
            return fn()
        except ToolError as e:
            if e.kind is not ErrorKind.TRANSIENT or n == attempts - 1:
                raise
            time.sleep(base * 2 ** n)
Backoff doubles each time; deterministic errors are re-raised at once.
The trap: One generic retry wrapper on every tool, including ones that create records.
In Formulaite: A retry helper in tools.py wrapping read_supplier_page; fill_drawer is safe to repeat because gates.py re-checks the whole drawer.
12Confidence signals and partial results ch 6

Ask the model for a confidence signal, not just an answer. Route low confidence to the escalation stop. When part of a task fails, keep what succeeded. Report three buckets: succeeded, failed with a cause, never reached.

Picture it: Eight of ten drawer sections filled, two flagged 'no source found'. Far more useful than a blank drawer.
report = {
    "succeeded": ["inci", "function", "use_level"],
    "failed": {"safety": "no supplier page reachable"},
    "never_reached": ["sources"],
    "confidence": 0.55,
}
if report["confidence"] < 0.6:
    escalate(report)
Three named buckets plus one number a human can act on.
The trap: Discarding a whole run because one step failed.
In Formulaite: drawer.py's missing() already lists the gaps; add a confidence field and let gates.py escalate below a threshold.

01Sub-agent delegation ch 4

A coordinator breaks the task apart, dispatches sub-agents and assembles the results. It never solves sub-problems itself. Use it only when the sub-problems are truly independent. Give each sub-agent a minimal, scoped view. If the coordinator spends its time reconciling contradictions, collapse back to one agent.

Picture it: A project lead hands research, drafting and checking to three people. If they keep contradicting each other, the split was wrong.
The trap: Delegating tightly coupled steps and paying coordination cost for nothing.
In Formulaite: agent.py could dispatch one Agent per ingredient in a formula, since ingredient drawers are independent, and merge the drawers.
02Circuit breakers ch 6

Aggressive retries across many runs can push a struggling service into an outage. A circuit breaker watches a dependency's failure rate. Past a threshold it opens: calls fail fast for a cooldown, then it closes again. Size the cooldown to the dependency's real recovery time, and surface every trip to a human.

Picture it: A fuse. When the line overheats it cuts the power, rather than letting every appliance keep pulling current.
class Breaker:
    fails, open_until = 0, 0.0
    def call(self, fn, threshold=5, cooldown=60):
        if time.time() < self.open_until:
            raise ToolError("breaker open", ErrorKind.TRANSIENT)
        try:
            out = fn(); self.fails = 0; return out
        except ToolError:
            self.fails += 1
            if self.fails >= threshold:
                self.open_until = time.time() + cooldown
            raise
Open means fail fast; the cooldown gives the dependency time to recover.
The trap: A cooldown picked at random: too short flaps, too long blocks a recovered service.
In Formulaite: A Breaker around read_supplier_page in formulaite_tools.py, with each trip logged as a glassbox.py Event.
03Least privilege for agents ch 7

Grant only the access the current task needs. An agent's task is known in advance, so you can scope precisely. Scope data visibility too, not just actions. Audit the grants whenever the task changes, because permission creep is small reasonable expansions piling up.

Picture it: The intern gets the key to the sample cupboard, not the master key to the building 'in case'.
READ_ONLY = ToolRegistry(catalogue_lookup, read_supplier_page)
FULL = ToolRegistry(catalogue_lookup, read_supplier_page, fill_drawer)

agent = Agent(model=model, tools=READ_ONLY)   # research-only run
The registry passed to the agent is its permission scope. Nothing outside it exists.
The trap: Granting access 'in case the agent needs it later'; that is live risk today.
In Formulaite: tools.py's ToolRegistry is the permission boundary: the research agent gets catalogue_lookup and read_supplier_page, never a catalogue write tool.
04Approval gates where they matter ch 7

A gate on every action turns the agent back into manual work. No gate removes the last catch. Gate actions that are irreversible, touch the outside world, or cross a threshold. Show the reasoning and evidence at the gate. Watch reviewer fatigue: too many gates become rubber stamps.

Picture it: You do not sign off every stir of the spoon. You do sign off before a batch ships.
def needs_approval(action):
    return action.irreversible or action.external or action.amount > LIMIT

if needs_approval(action):
    verdict = ask_human(action, reasoning=reply.text, evidence=facts)
    box.log("gate", action.name, verdict=verdict)
Three checkable criteria. The human sees the reasoning, not just a yes or no.
The trap: Gates placed out of general caution, with no specific risk named.
In Formulaite: gates.py handles the deterministic gate; a human gate before an accepted drawer is written into the catalogue belongs in agent.py.
05Sandbox and staged promotion ch 7

A sandbox is an isolated copy where mistakes are cheap to reverse. It must resemble production closely or it proves nothing. Promote in stages: sandbox, read-only in production, low-stakes writes, gated high-stakes writes, unattended. Trust is earned stage by stage, not granted once.

Picture it: A trainee formulator works on lab batches, then small pilot batches, then production, and only later runs a line alone.
The trap: Treating a clean sandbox run as proof the agent handles everything production will send.
In Formulaite: models.py's ScriptedModel plus the local supplier files under agent_lab/data is the Formulaite sandbox; ClaudeModel on read-only tools is stage two.
06Audit logs as a second line of defence ch 7

Least privilege, gates and sandboxes prevent. Logs detect what prevention missed. Record not just the action, but the stated reasoning, the permission scope, whether it passed a gate, and the result. Review a sample on a schedule, not only after an incident.

Picture it: CCTV in the lab. It does not stop a spill, but it shows exactly what happened and who was there.
The trap: A log that records 'action X at time T' and nothing else, which supports no real review.
In Formulaite: glassbox.py Events should carry scope and gate_verdict in their meta, so a Formulaite trace answers 'should this have happened'.
07Outcome versus trajectory evaluation ch 8

A single answer is right or wrong. An agent can reach the right answer by a clean path or by luck after many wrong turns. Score both: outcome (was the drawer correct) and trajectory (step count, tool-call error rate, retries). Report them separately, never as one number.

Picture it: Two students get the same exam mark. One knew the material; one guessed. The next exam will separate them.
def score(box, drawer, expected):
    outcome = drawer == expected
    trajectory = {
        "steps": box.steps,
        "tool_errors": len(box.of_kind("tool_error")),
        "retries": len(box.of_kind("retry")),
    }
    return outcome, trajectory      # never collapse into one number
The Glass Box already holds the trajectory; the drawer holds the outcome.
The trap: A good trajectory score taken as proof the outcome is right, or the reverse.
In Formulaite: glassbox.py's of_kind and steps give the trajectory metrics; gates.py's verdict on the drawer is the outcome score.
08A living eval set ch 8

Cases the developer imagined miss the failures they did not imagine. Mix sources: about 40 percent real historical cases, 25 percent adversarial edge cases, 20 percent production failures folded back in, 15 percent developer-written. Include hard cases. Give the set an owner and prune stale cases.

Picture it: A tasting panel of real customers, hostile critics and last month's complaints, not just the chef's friends.
The trap: An eval set frozen at launch that never absorbs a real production failure.
In Formulaite: A folder of ingredient cases (real drawers, tricky INCI names, past gate failures) that agent.py runs in a loop with ScriptedModel.
09Variance-aware regression testing ch 8

The same inputs can give a different trajectory each run. One pass proves little. Run boundary cases several times and track the pass-rate history. Run the whole suite after every change, because a fix for one case often breaks another. Keep deterministic checks single-run.

Picture it: A cream that passes stability nine times in ten is different from one that passes every time. You need the count.
The trap: Re-running only the case the fix was aimed at.
In Formulaite: gates.py checks stay single-run; the model-driven fill_drawer cases run five times each and the pass rate is stored per case.
10Human baseline ch 8

An eval score alone does not say whether the agent is good enough. Compare it to a domain expert working the same cases under the same limits. Study where they diverge: failing the cases humans also find hard is fine; failing easy ones signals a structural problem. Refresh the baseline as the task changes.

Picture it: Eighty percent against a formulator who scores seventy-five is a hire. Eighty against one who scores ninety-eight is not.
The trap: Picking a round-number target like 90 percent with nothing to anchor it.
In Formulaite: Have a formulator fill ten drawers by hand, then compare with the agent's drawers built from the same catalogue and supplier pages.
11Leading indicators with alerts ch 9

Do not wait for a loud failure. Track median steps to completion, retry rate, escalation-gate rate and approval override rate. A rising override rate means judgement is drifting. Put alert thresholds on these, and read a weighted sample of full traces on a schedule.

Picture it: A rising number of batches returned for rework tells you the line is drifting before a recall does.
The trap: A dashboard nobody checks, which is the same as no monitoring.
In Formulaite: A small script that loads saved glassbox.py runs and reports steps, retries and gate failures per week.
12Cost and latency as design constraints ch 9

A cheap demo run compounds at thousands of runs. Reuse the safety levers as cost levers: thinking only on hard steps, curated context, hard ceilings on steps and retries. Measure end-to-end latency with tool and retry delays included. Set targets before launch and revisit them as scale changes.

Picture it: A one-cent difference in a raw material is nothing on one jar and everything on a million.
The trap: Optimising cost and latency separately and quietly trading one for the other.
In Formulaite: memory.py's token_estimate and agent.py's max_steps are Formulaite's cost controls; log both per run in glassbox.py.
13Incremental rollout and model upgrades ch 9

Ship to a small slice first and expand only when real metrics match what the evals predicted. Keep a fast rollback path. A new model version changes judgement and tool choices, not just capability. Re-run the full eval suite, including trajectory and human baseline, before switching.

Picture it: A new supplier for the same ingredient still gets a pilot batch before it goes into every product.
The trap: Treating a model upgrade like a routine library bump.
In Formulaite: models.py's one-flag swap between ScriptedModel and ClaudeModel is the upgrade point; run the eval folder against both before flipping it.

The pattern

  1. State the goal with the evidence that would prove it done.
  2. Loop: reason, act with one narrow tool, observe, and log all three.
  3. Check escalation first, then the goal, then the step ceiling.
  4. Write exact facts to memory the moment you learn them.
  5. Classify every failure: transient gets backoff retry, deterministic escalates.
  6. Re-verify state right before any irreversible action; gate it if external.
  7. Score outcome and trajectory separately; fold real failures into the eval set.

Decisions

WhenUseNot
Steps are fixed and known in advancea plain workflowan agent loop
Fixed steps with a few runtime choicesa workflow with judgment pointsa full agent loop
The next step depends on what a tool returnsa single reason-act-observe loop with layered stopsa workflow that guesses
Sub-problems are independent, like one drawer per ingredienta coordinator with sub-agentsone overloaded context
A step is both ambiguous and high-stakesextended thinking on that stepthinking on every step
A tool error is a timeout or rate limitbounded backoff retryescalation or blind repeats
An action is irreversible or touches the outside worlda human approval gate with reasoning shownan ungated call or a gate on everything
An integration will be reused by several agentsMCPa bespoke one-off connection

Skeletons

Loop with three stop layers

for step in range(1, MAX_STEPS + 1):
    reply = model.complete(system, conv.as_api(), tools.to_api())
    box.log("reason", text=reply.text)
    if reply.confidence < 0.6:
        result = escalate(reply); break            # escalation
    if reply.is_final:
        verdict = run_gates(reply.drawer, catalogue_entry=fresh())
        if verdict: result = reply.drawer; break   # goal
    for call in reply.tool_uses:
        conv.add_tool_results([run_tool(call)])    # act + observe
else:
    result = "budget_exhausted"                    # ceiling

Tool error with a retry class

class ErrorKind(Enum):
    TRANSIENT, DETERMINISTIC = "transient", "deterministic"
class ToolError(Exception):
    def __init__(self, msg, kind=ErrorKind.DETERMINISTIC):
        super().__init__(msg); self.kind = kind

def retry(fn, attempts=3):          # backoff only for TRANSIENT
    for n in range(attempts):
        try: return fn()
        except ToolError as e:
            if e.kind is not ErrorKind.TRANSIENT or n == attempts - 1: raise
            time.sleep(0.5 * 2 ** n)

Re-verify, then gate, then write

def publish(drawer, box):
    entry = catalogue_lookup(drawer.inci)        # fresh state
    verdict = run_gates(drawer, catalogue_entry=entry)
    if not verdict:
        return escalate(verdict.reasons)
    if needs_approval(drawer):                    # irreversible write
        ok = ask_human(drawer, reasoning=box.of_kind("reason")[-1])
        box.log("gate", "human", approved=ok)
        if not ok: return "rejected"
    return catalogue.write(drawer)

Before you ship

  • Goal, ceiling and escalation stops all defined and tested before the first real run.
  • Every tool description states outcome, valid ranges, edge behaviour and when to prefer it.
  • Every tool called directly with edge inputs and its error paths triggered on purpose.
  • Exact ids, numbers and error text kept verbatim, separate from the prose summary.
  • Consequential actions re-verify their dependent state immediately before running.
  • Permissions scoped to the current task; gates sit at irreversible or external actions.
  • Eval set mixes real, adversarial and production-failure cases; trajectory scored beside outcome.
  • Full traces captured and a weighted sample read by a human on a schedule.
