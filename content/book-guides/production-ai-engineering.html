  2. Find the gate event and read its PASS or FAIL reasons.
  3. Lower max_steps to 2 and watch the budget_exhausted event appear.
  4. Add a check_has_sources rule to gates.py and re-run.
  5. Write down which event tells you why the run stopped.

  1. Create one Deadline per run and pass remaining seconds into every tool call.

  3. Add a circuit breaker that opens after five supplier failures and falls back to catalogue-only.
  4. Write a trajectory test: catalogue_lookup MUST run before fill_drawer.
  5. Run ScriptedModel(fail_first=True) and assert the run stops safely.

  1. Tag every tool with a risk class and run a policy chain before execution.
  2. Emit tool_requested and tool_completed events with prompt version and token counts.
  3. Build a 50-ingredient golden set and set thresholds for grounded, safe and schema-valid drawers.
  4. Compute cost per accepted drawer from Glass Box token counts.

01System health is not AI quality ch 1

A server can be up and fast while its answers are wrong. The book calls these two dimensions operational correctness and AI-output quality. You need a separate signal for each. A green dashboard proves nothing about the drawer being right.

Picture it: A kitchen scale can be switched on and working perfectly while you weigh the wrong ingredient.
The trap: Treating HTTP 200 and low latency as proof that the agent did its job.
In Formulaite: glassbox.py records the gate verdict next to each model reply, so a run can look healthy and still show FAIL.
02Productionising means removing assumptions ch 2

A prototype silently assumes the model answers, inputs are clean and cost is tiny. Production replaces each assumption with a timeout, a validator, a budget or a test. The book's table of assumptions is the checklist. Write the assumption down before you replace it.

Picture it: A recipe scribbled for yourself assumes your oven. A published recipe states temperatures, times, and what to do if the cake sinks.
The trap: Believing a demo that worked ten times is evidence it will work ten thousand times.
In Formulaite: models.py ScriptedModel exists so the loop runs without assuming an API key and a network are available.
03Separate generation from validation ch 2

The model generates. A separate deterministic step decides whether the output is acceptable. Validation checks schema, allowed values and business rules. Bad output goes to a fallback or an error, never straight into the app.

Picture it: The chef plates the dish; the pass checks it against the ticket before it leaves the kitchen.
def validate(output: dict) -> list[str]:
    reasons = []
    if output.get("category") not in {"billing", "shipping"}:
        reasons.append("category not allowed")
    if output.get("priority") not in {"low", "high"}:
        reasons.append("priority not allowed")
    return reasons          # empty list means PASS
The model never sees this function; it only sees the reasons when they come back.
The trap: Asking the model to check its own answer instead of checking it in code.
In Formulaite: gates.py run_gates is exactly this step; agent.py sends the reasons back as an error tool_result.
04The tool gateway ch 3

The model never calls a tool directly. Its request passes a gateway that validates parameters, checks permission, applies limits and writes an audit line. Capability is granted explicitly, never implied. High-impact tools get stronger checks.

Picture it: A hotel guest asks reception for a room key. Reception checks the booking before handing one over.
def gateway(registry, call, *, allow: set[str]):
    if call.name not in allow:
        raise ToolError(f"{call.name} not permitted")
    tool = registry[call.name]
    args = tool.validate(call.input)     # schema check
    result = tool(**args)
    audit.log(tool=call.name, args=args, ok=True)
    return result
Allowlist first, schema second, execute last, audit always.
The trap: Letting registry.call(name, **input) run anything the model names.
In Formulaite: tools.py ToolRegistry.call is the seam where this gateway belongs; today it only checks that the name exists.
05The agent execution budget ch 4

Agents can loop forever, call tools unexpectedly and burn tokens. The book demands four explicit limits: max execution time, max model calls, max tool calls and max tokens. The loop checks them every step. When one runs out, the agent stops cleanly and says why.

Picture it: A shopping trip with a set amount of cash, a set time and a set list. When any of them runs out, you go home.
from dataclasses import dataclass

@dataclass
class Budget:
    seconds: float = 60.0
    model_calls: int = 8
    tool_calls: int = 12
    tokens: int = 20_000

    def exhausted(self, used: "Budget") -> bool:
        return (used.seconds >= self.seconds or used.model_calls >= self.model_calls
                or used.tool_calls >= self.tool_calls or used.tokens >= self.tokens)
One object holds all four limits, so the loop asks one question per step.
The trap: Capping steps only, and forgetting that one step can cost 30 seconds and 15,000 tokens.
In Formulaite: agent.py has max_steps only; a Budget object would replace it and log budget_exhausted with the reason.
06Conversation history is not memory ch 6

History is the raw transcript. Memory is a small, chosen record of what still matters. Sending the whole transcript every call gets slow and costly, and eventually overflows the context. Keep raw history, structured state and a summary as three separate things.

Picture it: Your lab notebook is history. The sticky note on the fridge saying 'glycerin at 3 percent works' is memory.
The trap: Letting the message list grow without bound and calling that memory.
In Formulaite: memory.py Conversation is history; a separate drawer-state object would be the structured memory.
07Memory needs provenance and an expiry ch 6

A model guess must never quietly become a stored fact. Every memory record carries a source, a confidence and an expires_at. Retrieval drops expired records. Conflicts are settled by a written rule, not by the model.

Picture it: A supplier's claim on a datasheet is labelled 'supplier says'. Your own test result is labelled 'measured'. You trust them differently.
memory = {
    "content": "Glycerin use level 3 percent",
    "source": "tool_result",      # user_explicit | tool_result | model_inference
    "confidence": 0.9,
    "created_at": "2026-09-07",
    "expires_at": "2027-09-07",
}
source and expires_at are the two fields that stop false memory.
The trap: Storing 'user prefers X' because the model inferred it once.
In Formulaite: drawer.py sources is the start of provenance; a memory store in memory.py would add source and expires_at.
08Request validation protects resources ch 7

Every incoming request is checked before any expensive work: required fields, types, lengths, size limits, allowed values. A giant input becomes giant tokens, cost and latency. Rejecting early is cheaper than failing late.

Picture it: The bouncer checks tickets at the door, not after everyone is inside and the bar has run dry.
MAX_INCI_LEN = 120

def validate_request(inci: str) -> str:
    inci = inci.strip()
    if not inci:
        raise ValueError("inci is required")
    if len(inci) > MAX_INCI_LEN:
        raise ValueError("inci too long")
    return inci
The limit is a number you chose from real requirements, not a guess.
The trap: Validating only the shape of the input and forgetting its size.
In Formulaite: agent.py Agent.run should validate inci before the first model call; today it trusts it.
09Validate configuration at startup ch 11

Config values such as timeouts, retries and model names steer behaviour. Bad values should fail at start, not after traffic arrives. Load config once, type it, check ranges, then hand one object to the app. Secrets are a separate thing.

Picture it: You check the oven is set to Celsius before you bake, not when the cake burns.
import os

def load_config() -> dict:
    cfg = {"model": os.environ.get("MODEL_NAME"),
           "max_retries": int(os.environ.get("MAX_RETRIES", "3")),
           "timeout_s": float(os.environ.get("REQUEST_TIMEOUT_SECONDS", "30"))}
    if not cfg["model"]:
        raise SystemExit("MODEL_NAME missing")
    if cfg["max_retries"] < 0:
        raise SystemExit("MAX_RETRIES must be >= 0")
    return cfg
One loader, one validation, one typed object.
The trap: Scattering os.environ.get across many files so nobody can list what the app needs.
In Formulaite: models.py reads its settings from the environment; a load_config() there would validate them at import time.
10Transport success is not semantic success ch 12

The model can return HTTP 200 and valid JSON with a wrong answer. Failures split into deterministic (same cause, same failure) and probabilistic (fails some percent of the time). Each needs a different fix. Describe probabilistic failures as rates, not as 'it failed'.

Picture it: The courier says 'delivered'. The parcel contains the wrong ingredient.
The trap: Retrying a wrong-but-valid answer as if it were a network error.
In Formulaite: gates.py turns a semantic failure into an explicit FAIL verdict, so agent.py never treats it as success.
Intermediate
0 / 12 got it
01Relevance is not permission ch 5

The most relevant document may be one this user must not see. Authorisation filters retrieval before the search, not after the text reaches the model. Once a document is in context, it is too late. Metadata such as tenant and access_level makes the filter possible.

Picture it: The pharmacy has the drug you asked about. The pharmacist still checks your prescription before handing it over.
The trap: Filtering results after the model has already read them.
In Formulaite: formulaite_tools.py read_supplier_page should accept only URLs from an approved supplier list, decided before the fetch.
02Context is a budget ch 5

More context is not better context. Extra chunks add cost, latency and contradictions. Rank candidates, keep the most relevant first, and stop at a token budget. Compression is allowed but must itself be evaluated.

Picture it: A recipe card goes on the counter while you cook, not the whole cookbook.
def build_context(chunks, budget_tokens: int) -> list[str]:
    chosen, used = [], 0
    for chunk in sorted(chunks, key=lambda ch: -ch["score"]):
        cost = len(chunk["text"]) // 4
        if used + cost > budget_tokens:
            break
        chosen.append(chunk["text"])
        used += cost
    return chosen
Sort by score, then fill until the budget is spent.
The trap: Setting top_k high because 'the model can handle it'.
In Formulaite: memory.py token_estimate is the budget signal; a build_context() would cap how much supplier text enters the prompt.
03Durable job state machine ch 10

Long work runs behind a queue with a job ID. The job's state lives in storage, not in a worker's memory. States are few and named: CREATED, QUEUED, RUNNING, SUCCEEDED, FAILED, RETRYING, DEAD_LETTERED. A crashed worker can be recovered because the state survives.

Picture it: An order ticket on a rail. Each stage stamps it, and if a cook goes home the next one reads the ticket.
from enum import Enum

class JobState(str, Enum):
    CREATED = "CREATED"
    QUEUED = "QUEUED"
    RUNNING = "RUNNING"
    SUCCEEDED = "SUCCEEDED"
    FAILED = "FAILED"
    RETRYING = "RETRYING"
    DEAD_LETTERED = "DEAD_LETTERED"
Each state is a string, so it can be saved and read back from a database.
The trap: Acknowledging the queue message before the result is safely stored.
In Formulaite: A batch 'research 200 ingredients' job would wrap agent.py runs in this state machine, one job per INCI name.
04Idempotency key ch 10

Queues deliver at least once, so the same job can run twice. An idempotency key names the logical operation, not the attempt. Before doing a side effect, check whether that key already has a result. Then a duplicate run is harmless.

Picture it: A numbered receipt. If the till prints twice, the shop sees the same number and does not charge you again.
import hashlib, json

def idem_key(tenant: str, op: str, inci: str, config_version: str) -> str:
    raw = json.dumps([tenant, op, inci, config_version])
    return hashlib.sha256(raw.encode()).hexdigest()[:16]

done: dict[str, dict] = {}
key = idem_key("t1", "fill_drawer", "Glycerin", "v3")
if key not in done:
    done[key] = run_research("Glycerin")
The key is built from what the operation is, never from a timestamp.
The trap: Confusing deduplication (stop duplicates) with idempotency (make duplicates safe).
In Formulaite: Saving a drawer from drawer.py should be keyed by tenant + INCI + catalogue version, so a retried run overwrites instead of duplicating.
05Deadlines flow downhill ch 13

Timeouts are hierarchical. The user's deadline is split among API, orchestrator, model and tools. Each call gets only the time left: T_remaining = T_deadline minus T_elapsed. Starting a ten-second call with three seconds left is a bug.

Picture it: A relay race. Each runner gets what is left on the clock, not a fresh clock.
import time

class Deadline:
    def __init__(self, seconds: float):
        self.end = time.monotonic() + seconds

    def remaining(self) -> float:
        return max(0.0, self.end - time.monotonic())

deadline = Deadline(30)
tool_timeout = min(8.0, deadline.remaining())
min() means the tool call can never outlive the request.
The trap: Every layer picking its own timeout, so the model keeps working after the caller gave up.
In Formulaite: agent.py would create one Deadline per run and pass remaining() into each formulaite_tools.py call.
06Backoff with full jitter ch 13

Retry only transient errors, and wait longer each time. Exponential backoff doubles the delay. Full jitter picks a random wait up to that delay. Then thousands of clients do not retry in the same second. One layer owns retries.

Picture it: After a power cut, if every fridge restarts at once the grid trips again. Staggered restarts keep it up.
import random, time

def retry(fn, attempts: int = 4, base: float = 1.0, cap: float = 8.0):
    for n in range(attempts):
        try:
            return fn()
        except TransientError:
            if n == attempts - 1:
                raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** n)))
random.uniform(0, ...) is the full jitter; the cap stops the wait growing forever.
The trap: Retrying at three layers, so one request becomes twenty-seven attempts.
In Formulaite: read_supplier_page in formulaite_tools.py is the only call that should retry; agent.py must not retry on top of it.
07Circuit breaker ch 13

When a dependency keeps failing, stop calling it. CLOSED lets calls through and counts failures. OPEN rejects fast. HALF-OPEN lets a few probes through and closes again on success. It does not fix the dependency; it limits the damage.

Picture it: A fuse box. After too much current it trips, you wait, then you try one switch before turning everything back on.
class Breaker:
    def __init__(self, threshold: int = 5, cooldown: float = 30.0):
        self.failures, self.open_until = 0, 0.0
        self.threshold, self.cooldown = threshold, cooldown

    def allow(self) -> bool:                 # the OPEN check
        return time.monotonic() >= self.open_until

    def record(self, ok: bool) -> None:
        self.failures = 0 if ok else self.failures + 1
        if self.failures >= self.threshold:
            self.open_until = time.monotonic() + self.cooldown
allow() is the OPEN check; the first call after cooldown is the HALF-OPEN probe.
The trap: Counting 400 Bad Request as a dependency failure and opening the circuit on your own bug.
In Formulaite: One Breaker per supplier domain in formulaite_tools.py; the agent falls back to catalogue-only research while it is open.
08The degradation ladder ch 13

When something fails, step down one rung at a time. The rungs are: full answer, answer without private knowledge, cached result, deterministic response, explicit failure. A degraded system must say what it lost. A confident answer built on missing data is worse than an honest 'not available'.

Picture it: No fresh basil? Use dried, then skip the garnish, then tell the guest. Never pretend it is there.
The trap: Falling back to a cached or secondary answer that quietly skips a check or exposes data.
In Formulaite: If read_supplier_page fails, agent.py should fill the drawer from the catalogue and mark sources as 'catalogue only'.
09Token budgeting before execution ch 15

Estimate input, output and expected tool tokens before calling the model. Check the estimate against the quota. Accept, reject or route cheaper. One user request can fan out into six to ten internal operations, so count those too.

Picture it: You check the trolley total before the till, not after the card is declined.
def admit(prompt: str, max_out: int, expected_tools: int, quota: int) -> bool:
    est = len(prompt) // 4 + max_out + expected_tools * 800
    return est <= quota
A rough estimate is enough; the point is deciding before spending.
The trap: Limiting requests per minute and forgetting that one request can carry 80,000 tokens.
In Formulaite: memory.py token_estimate feeds an admit() check in agent.py before each model.complete call.
10Test properties, not strings ch 16

Two different sentences can both be right. So tests check properties: valid schema, allowed values, required facts present, forbidden content absent, pass rate above a threshold. Exact-match tests still belong on deterministic code such as parsers and gates.

Picture it: A cake test checks it rose, is cooked through and tastes of lemon. It does not compare the cake to a photo pixel by pixel.
def test_drawer_properties(drawer):
    assert drawer.inci_name.lower() == "glycerin"
    assert 0 < drawer.use_level_percent <= 10
    assert drawer.sources                      # at least one
    assert "cures" not in drawer.claims.lower()

def test_pass_rate(results):
    assert sum(r.ok for r in results) / len(results) >= 0.95
The first test is a property test; the second is a statistical test.
The trap: Asserting output == expected_string and then marking every rewording as a bug.
In Formulaite: gates.py checks are property tests; a pytest file would run them over a folder of recorded drawers.
11Tool selection and tool execution are separate tests ch 16

Question one: did the model pick the right tool? Question two: was the chosen tool executed safely? The second must hold even when the model is wrong. Test execution with hand-written tool requests and no model at all.

Picture it: The waiter may write the wrong order. The kitchen still checks allergies before cooking whatever arrives.
The trap: Only testing with a model in the loop, so a safety bug hides behind a lucky model.
In Formulaite: tools.py ToolRegistry.call can be tested with hand-built ToolUseBlock inputs, leaving models.py out entirely.
12Trajectory invariants: Must and May ch 18

An agent's sequence of tool calls is its trajectory. Do not demand one exact path; several are valid. Write invariants instead: things the run MUST do and things it MAY do. Add limits such as max steps and allowed tools only. Then inject failures and check it stops safely.

Picture it: A driving test. You must stop at the red light and check your mirrors. You may take either route to the shop.
MUST = {"catalogue_lookup", "fill_drawer"}
MAY = {"read_supplier_page"}

def check_trajectory(box) -> list[str]:
    called = [e.meta["tool"] for e in box.of_kind("tool_call")]
    called += ["fill_drawer"] * len(box.of_kind("gate"))
    reasons = [f"missing {t}" for t in MUST if t not in called]
    reasons += [f"forbidden {t}" for t in called if t not in MUST | MAY]
    if box.steps > 8:
        reasons.append("too many steps")
    return reasons
The invariants read straight from the Glass Box, so no model is needed to check them.
The trap: Writing a test that fails whenever the agent reorders two harmless calls.
In Formulaite: glassbox.py of_kind('tool_call') is the trajectory; a check_trajectory() in a test file asserts the invariants.

01Golden dataset and release thresholds ch 17

A golden dataset is a curated, versioned, owned set of inputs with expected behaviour. Score each quality dimension separately: correctness, relevance, groundedness, safety, schema validity. Set a threshold per dimension. A change ships only if every threshold holds against the baseline.

Picture it: A reference batch of your best cream. Every new batch is compared to it on colour, feel and stability, not on one overall mark.
THRESHOLDS = {"correct": 0.95, "grounded": 0.93, "safe": 0.99, "schema": 0.995}

def failed_gates(scores: dict) -> list[str]:
    return [k for k, minimum in THRESHOLDS.items() if scores.get(k, 0) < minimum]

failed_gates({"correct": 0.96, "grounded": 0.91, "safe": 1.0, "schema": 1.0})
# -> ["grounded"]   so the release is rejected
One threshold per dimension; a single averaged score would have hidden the grounding drop.
The trap: Collapsing five metrics into one '95 percent overall' score.
In Formulaite: A golden set of 50 ingredients with expected drawers, run through agent.py with ScriptedModel, is the baseline for any gates.py change.
02AI events on the trace ch 20

Logs say what happened, metrics say how much, traces say where. AI adds events for decisions: request_received, retrieval_completed, model_called, tool_requested, tool_completed, response_validated. Each event carries request id, model and prompt version, tokens and latency. Trace the logical steps, not just HTTP.

Picture it: A flight recorder logs each control input, not just take-off and landing.
box.log("tool_requested", inci, tool=call.name, step=step,
        prompt_version="v12", request_id=run_id)
box.log("tool_completed", inci, tool=call.name, ok=True,
        latency_ms=143, tokens_in=820, tokens_out=0)
box.log("response_validated", inci, passed=verdict.passed,
        reasons=list(verdict.reasons))
The same request_id on every line is what makes the run diagnosable later.
The trap: Logging full supplier pages and prompts into ordinary logs, turning observability into a leak.
In Formulaite: glassbox.py Event already has kind, tags and meta; add prompt_version and token counts to every model_reply event.
03Sampling-based hallucination monitoring ch 21

There is no hallucination=true field. Compare claims against the retrieved evidence. Run cheap heuristics on every response, a judge model on a sample, and humans on critical cases. Report the rate together with its denominator.

Picture it: Quality control tastes a spoon from every batch, sends one jar a day to the lab, and recalls on a lab failure.
The trap: Reporting a low hallucination rate that was measured only on easy cases.
In Formulaite: gates.py check_has_sources is the cheap heuristic; a sampled judge comparing drawer claims to the supplier page is the next layer.
04Cost per workflow ch 22

One request can trigger many model and tool calls. Add them up: cost of the workflow is the sum of every call. Divide by successful outcomes to get cost per completed task. Track distributions, not just averages. A cheaper model that causes retries can cost more.

Picture it: The price of a cake is flour plus eggs plus oven time plus the two you burnt.
PRICE_IN, PRICE_OUT = 3.0, 15.0     # per million tokens, from config

def call_cost(tokens_in: int, tokens_out: int) -> float:
    return tokens_in / 1e6 * PRICE_IN + tokens_out / 1e6 * PRICE_OUT

def workflow_cost(box) -> float:
    return sum(call_cost(e.meta["tokens_in"], e.meta["tokens_out"])
               for e in box.of_kind("model_reply"))
Prices come from config; the sum runs over every model event in the run.
The trap: Quoting cost per request when an agent request is really twelve calls.
In Formulaite: A workflow_cost() reading glassbox.py events gives cost per accepted drawer, reported next to the gate pass rate.
05Risk is influence times authority times impact ch 25

Injection is only as dangerous as the tools behind the model. A supplier page may carry hidden instructions. Retrieved content can be relevant without being trusted. Reduce authority and impact, and injection becomes a contained input problem.

Picture it: A prank note in the suggestion box is harmless. The same note handed to someone holding the keys is not.
The trap: Trying to block attack phrases instead of limiting what the model can do.
In Formulaite: read_supplier_page output in formulaite_tools.py is untrusted data; the model can only propose fill_drawer, which the gate checks.
06The layered tool execution path ch 25

Valid JSON is not valid authorisation. A tool request passes schema, allowlist, authorisation, parameter validation, policy, a risk check, human approval if required, then execution. Each layer answers one question. Tool authority must not exceed required authority.

Picture it: Airport security: ticket, passport, bag scan, gate check. Each step asks a different question.
def execute(call, user):
    args = schema_check(call)                 # is the structure valid?
    assert call.name in ALLOWLIST             # is this tool permitted?
    assert authorised(user, call.name)        # may this caller use it?
    args = validate_params(call.name, args)   # are the arguments valid?
    assert policy_allows(call.name, args)     # permitted right now?
    if RISK[call.name] == "high":
        await_approval(call.name, args)
    return run_tool(call.name, args)
The order matters: cheap structural checks first, human approval last.
The trap: One combined 'is this ok?' function that mixes syntax and authority.
In Formulaite: tools.py ToolRegistry.call becomes this chain; a RISK table in formulaite_tools.py marks fill_drawer as a write.
07Approval bound to an action fingerprint ch 26

Human approval must show the exact action and parameters, not the model's explanation. Bind the approval to a fingerprint of tool plus arguments. If the arguments change after approval, the fingerprint changes and execution stops.

Picture it: You sign a cheque for a named amount. Changing the amount after signing makes it void.
import hashlib, json

def fingerprint(tool: str, args: dict) -> str:
    raw = json.dumps({"tool": tool, "args": args}, sort_keys=True)
    return hashlib.sha256(raw.encode()).hexdigest()

approved = fingerprint("publish_drawer", {"inci": "Glycerin"})
if fingerprint(call.name, call.input) != approved:
    raise ToolError("action changed after approval")
sort_keys=True makes the same arguments always hash the same way.
The trap: Approving 'the model wants to publish' and then letting different parameters run.
In Formulaite: A publish_drawer tool in formulaite_tools.py would require a fingerprint approval, logged in glassbox.py.
08The audit trail ch 26

Every security-sensitive action writes one append-only line. It holds timestamp, request id, user, tool, action, resource, authorisation result, approval id, result and policy version. It links to the trace and never stores secrets. It answers who, what, which policy, which tool, what changed.

Picture it: A lab logbook in ink: dated, signed, never torn out.
The trap: Logging the API key or the full document because it was handy.
In Formulaite: glassbox.py tool_call events gain user_id, authorization_result and policy_version, saved with GlassBox.save.
09Model routing under constraints ch 30

Choose the least expensive model that reliably meets requirements. Routing picks per request: simple tasks to small models, hard ones to large. The goal is minimum cost subject to quality, latency and availability floors. The router itself must be observable.

Picture it: You do not hire a master perfumer to label jars. You do hire one to fix a scent that has gone wrong.
def choose_model(task: str, tokens_in: int, budget_left: float) -> str:
    if task == "extract_use_level" and tokens_in < 2_000:
        return "small-fast"
    if budget_left < 0.01:
        return "small-fast"
    return "general"
Every branch is a rule you can log and test; no model decides the routing.
The trap: Routing hard tasks to a cheap model and paying it back in retries and complaints.
In Formulaite: models.py ModelClient is the socket; a router that returns ScriptedModel or ClaudeModel per task is a third implementation.
10The AI release manifest ch 32

A release is more than code. Record application version, prompt version, model version, retrieval configuration, tool definitions, evaluation dataset version, config version and container digest. Rolling back means restoring the compatible set. If a prompt can change behaviour, it belongs in the release process.

Picture it: A batch record lists every ingredient lot. A recall needs the whole record, not just the label.
RELEASE = {
    "app": "1.4.0",
    "prompt": "ingredient-research/v12",
    "model": "claude-sonnet-4-5",
    "catalogue": "2026-09-01",
    "tools": ["catalogue_lookup", "read_supplier_page", "fill_drawer"],
    "eval_set": "golden-v3",
    "config": "cfg-27",
}
Print this at startup and stamp it on every Glass Box run.
The trap: Rolling back the app but leaving the new prompt and model in place.
In Formulaite: agent.py SYSTEM_PROMPT and models.py DEFAULT_MODEL get version labels, written into every glassbox.py run header.
11Keep deterministic logic outside the model ch 35

If a rule can be coded reliably, code it. Never ask the model whether a user is authorised or whether a value is in range. The model handles language, judgement and generation. Everything else is ordinary software, which is cheaper and testable.

Picture it: You use a thermometer to read the temperature, not a taster's opinion.
The trap: Putting 'only answer if allowed' in the system prompt and calling it access control.
In Formulaite: gates.py check_use_level_in_range and check_not_banned are deterministic rules that never pass through the model.
12The final production decision ch 38

The readiness review ends in an explicit call: GO, CONDITIONAL GO with owners and deadlines, or NO-GO. It reviews architecture, security, reliability, performance, cost, evaluation, observability, deployment and operations together. Evidence decides, not a good demo.

Picture it: A product launch gate. The formula does not ship because it smells nice. It ships when stability, safety and cost data are in.
The trap: Treating an impressive demo as evidence of readiness.
In Formulaite: A readiness checklist for the research agent lives next to agent.py; each line points at a Glass Box run or an eval result.
05 · Cheat sheet

Production AI Engineering: From AI Prototypes to Reliable, Secure, Scalable Systems — cheat sheet

Everything on one sheet.

Vocabulary

TermMeans
OrchestratorThe code that runs the loop: prompt, model, tools, validation. It coordinates, it does not absorb.
Tool gatewayThe checkpoint between a model's tool request and the real function: validate, authorise, limit, audit.
Execution budgetFour caps per run: max time, max model calls, max tool calls, max tokens.
DeadlineOne end time for the whole request; every downstream call gets only what is left.
Transient errorA failure that may vanish if you try again: 429, 502, 503, a timeout on a read.
JitterRandom spread added to retry waits so clients do not all retry in the same second.
Circuit breakerCLOSED, OPEN, HALF-OPEN: stop calling a dependency that keeps failing, probe later.
Idempotency keyA stable name for a logical operation so running it twice has one effect.
Graceful degradationLosing capability one rung at a time while staying honest about what is missing.
ProvenanceWhere a memory or claim came from: user, tool result, model inference, imported data.
TrajectoryThe sequence of tool calls an agent made on the way to its answer.
Golden datasetA curated, versioned, owned set of inputs with expected behaviour, used as the baseline.
GroundednessWhether each generated claim is supported by the evidence the app supplied.
Quality gateA threshold a change must meet before it moves to the next release stage.
Admission controlEstimating token demand and checking quota before the model is called.
Release manifestThe versions that define behaviour: app, prompt, model, retrieval, tools, eval set, config.
Audit trailAppend-only record of who asked, what the model proposed, which policy allowed it, what ran.
Cost per workflowThe sum of every call in one request, divided by successful outcomes.

The pattern

  1. Validate the request and authorise the user before any model call.
  2. Set one deadline and one budget: time, model calls, tool calls, tokens.
  3. The model proposes: a prose answer or a tool call.
  4. The policy layer checks schema, allowlist, arguments and risk; the executor runs the tool.
  5. Results go back; the deterministic gate says PASS, or FAIL with reasons.
  6. Every step writes an event with request id, versions, tokens and latency.
  7. Evals and cost per accepted drawer read the trace and gate the next release.

Rules of thumb

DoDon't
Enforce authorisation in code before retrieval or tool execution.Ask the model whether the user is allowed.
Give every network call a timeout derived from the remaining deadline.Let each layer pick its own timeout.
Retry only transient errors, with backoff and jitter, from one layer.Retry at client, API and SDK at the same time.
Cap steps, tool calls, model calls and tokens on every run.Trust the model to stop on its own.

Stamp request id, prompt version, model version and tokens on every event.Log full prompts and secrets into ordinary logs.

Skeletons

Bounded agent loop

def run(agent, inci, budget, deadline):
    convo = Conversation(); convo.add_user(f"Research {inci}")
    for step in range(1, budget.model_calls + 1):
        if deadline.remaining() <= 0:
            return stop("deadline")
        reply = agent.model.complete(system=SYS, messages=convo.as_api(), tools=TOOLS)
        box.log("model_reply", inci, step=step, tokens=reply.usage)
        if not reply.tool_uses: return finish(reply.text)
        convo.add_assistant(blocks(reply))
        convo.add_tool_results([policy_execute(c, deadline) for c in reply.tool_uses])
        if gate_passed(): return finish("accepted")
    return stop("budget")

Protected supplier fetch

breaker = Breaker(threshold=5, cooldown=30.0)

def fetch(url: str, deadline) -> str:
    if not breaker.allow():
        raise ToolError("supplier circuit open")
    try:
        text = retry(lambda: http_get(url, timeout=min(8.0, deadline.remaining())))
        breaker.record(ok=True)
        return text
    except TransientError:
        breaker.record(ok=False)
        raise

Tool policy chain

RISK = {"catalogue_lookup": "read", "read_supplier_page": "read", "fill_drawer": "write"}

def policy_execute(call, user, deadline):
    if call.name not in registry: raise ToolError("unknown tool")
    args = registry[call.name].validate(call.input)
    if not authorised(user, call.name):
        raise ToolError("not authorised")
    if RISK[call.name] == "write" and not approved(call):
        raise ToolError("needs approval")
    result = registry.call(call.name, **args)
    audit(user=user, tool=call.name, args=args, ok=True)
    return result

Before you ship

  • Every model and tool call has a timeout derived from the run deadline.
  • The run stops by itself at max steps, tool calls or tokens, and logs why.
  • Tool requests pass schema, allowlist, authorisation and parameter checks before execution.
  • Supplier page text and tool results are treated as data, never as instructions.
  • Every Glass Box event carries request id, prompt version, model version and token counts.
  • A golden set with a threshold per dimension runs before any prompt, model or catalogue change.
  • Cost per accepted drawer and p95 latency are on the dashboard, not only averages.
  • Rollback restores prompt, model and catalogue together, and has been rehearsed once.
06 · You're done when…
  1. Run the research agent with a deadline and a four-part budget, and point at the Glass Box event that says why it stopped.
  2. Inject a supplier timeout and a poisoned supplier page, and show the run degrades to catalogue-only without any unsafe tool call.
  3. Run a 50-ingredient golden set before and after a prompt change and give a GO or NO-GO from the per-dimension scores and cost per accepted drawer.
