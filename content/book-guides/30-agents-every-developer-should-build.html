01 · Where this is going

Every agent is the same loop, perceive, reason, plan, act, learn, wrapped in modules that talk through a broker; what changes across the thirty agents is which module gets the hard job.

Read this book when: Open it once the basic tool loop works and you want a catalogue of proven architectures to borrow: retrieval, extraction, validation, recovery, arbitration and monitoring.

Steps for rung 1: A proxy-then-tool-loop drawer filler with a Glass Box

  1. Write the system prompt in agent.py as five blocks: identity, rules, capabilities, output format, hierarchy.
  2. Print as_tool_schema() from drawer.py and the registry schema from tools.py; fix any vague description.
  3. Run Agent.run('Glycerin') and watch the loop: model proposes, ToolRegistry.call executes, result returns.
  4. Make IngredientDrawer.from_model_kwargs reject a payload with missing sections instead of accepting it.
  5. Replay the GlassBox and read each Event aloud: input, prompt, tool call, verdict, final action.

  2. Attach a source label to every chunk the tool returns and make check_has_sources in gates.py use it.
  3. Add an alias map to catalogue_lookup so a trade name resolves to the INCI key before lookup.
  4. Make run_gates return reasons the model can act on and cap the fix loop in agent.py at three rounds.

01The cognitive loop ch 1

An agent is not one prompt. It cycles through five phases: perceive the input, reason about what it means, plan the steps, act with tools, and learn from the result. Each phase is a separate function you can test and swap.

Picture it: A formulator reading a brief: note what was asked, work out what kind of product it is, list the lab steps, run them, then write down what to do differently next time.
def create_action_plan(reasoning_result):
    intent = reasoning_result["intent"]
    priority = reasoning_result["priority"]
    if priority == "urgent":
        return ["escalate_to_human", "log_urgent_case"]
    if intent == "billing_issue":
        return ["fetch_account_details", "analyze_billing_history",
                "generate_explanation", "offer_resolution"]
    return ["draft_general_reply"]
Planning only names the steps. It never knows how the account is fetched or how the reply is phrased.
The trap: Stuffing all five phases into one giant prompt, so nothing can be tested on its own.
In Formulaite: agent.py — Agent.run() is the loop; models.py perceives and plans, formulaite_tools.py acts, and glassbox.py is where learning starts.
02The cognition core is a broker, not a brain ch 1

The core does not know everything. It routes between five layers: Profile for tone and rules, Planning for steps, Knowledge for facts, Tools for action and Reasoning for validation. Intelligence comes from clean handoffs, not from one big mind.

Picture it: A production manager on the factory floor: she weighs nothing herself, she passes the job between QC, the mixing room and the label desk.
async def process_query(self, query, user_id, context):
    core_state = {"query": query, "user_id": user_id, "context": context}
    await self._apply_profile(core_state)
    plan = await self.planner.decompose(core_state)
    core_state["plan"] = plan.steps
    core_state["knowledge"] = await self.knowledge_base.retrieve(core_state)
    if "check_billing" in plan.steps and "billing_api" in self.tools:
        core_state["billing"] = await self.tools["billing_api"].invoke(user_id)
    draft = await self._compose_response(core_state)
    validated, flags = await self.reasoning.validate(draft, core_state)
    return {"response": validated,
            "action": "escalate" if flags.requires_escalation else "reply"}
Each await hands off to one layer; the core only carries the state dictionary between them and validates before replying.
The trap: Letting the model be the broker, so a timeout in one layer silently becomes a made-up answer.
In Formulaite: agent.py — Agent composes model, tools, glassbox and gate; it owns no clever logic of its own, it coordinates.
03Proxy agent: sanitise, constrain, parse, validate ch 1

A proxy agent turns messy human text into one validated object and forwards nothing else. Strip dangerous input first. Ask the model for JSON only. Parse it, check every required key, and reject anything malformed. It is boring in exactly the right places.

Picture it: Goods-in at a warehouse: the courier can say anything, but only a delivery note with every field filled gets stamped and passed inside.
EXPECTED_KEYS = {"intent", "category", "priority", "user_email", "requires_human"}
def sanitize_support_text(text: str) -> str:
    cleaned = re.sub(r"<script.*?>.*?</script>", "", text, flags=re.I | re.S)
    return re.sub(r"\s+", " ", cleaned).strip()
def build_ticket_payload(user_query: str) -> dict:
    raw_response = chain.run({"query": sanitize_support_text(user_query)})
    payload = json.loads(raw_response)
    missing = EXPECTED_KEYS.difference(payload.keys())
    if missing:
        raise ValueError(f"Missing required keys: {sorted(missing)}")
    return payload
EXPECTED_KEYS.difference(payload.keys()) lists what the model forgot; a missing key raises instead of passing junk on.
The trap: Trusting that JSON-looking text is valid JSON with the right keys.
In Formulaite: drawer.py — IngredientDrawer.from_model_kwargs plus missing() is the proxy step: fill_drawer output becomes a typed object or it is rejected.
04Model decides, code executes ch 1

The runtime loop is small. The model reads the messages and the tool list. It answers or asks for tool calls. Your code runs the tools, appends each result, and calls the model again. The loop ends when the model stops asking.

Picture it: A chef calling out orders: the chef never touches the fryer, the line cooks do, and each plate comes back to the pass before the next call.
messages.append(message.model_dump(exclude_none=True))
while getattr(message, "tool_calls", None):
    for tool_call in message.tool_calls:
        try:
            arguments = json.loads(tool_call.function.arguments or "{}")
            tool_result = run_tool(tool_call.function.name, arguments)
        except Exception as exc:
            tool_result = {"error": str(exc)}
        messages.append({"role": "tool", "tool_call_id": tool_call.id,
                         "content": json.dumps(tool_result)})
    response = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
    message = response.choices[0].message
while getattr(message, 'tool_calls', None) keeps looping only while the model still wants a tool; a failed tool becomes an error dict, not a crash.
The trap: Forgetting a step budget, so a confused model can loop forever.
In Formulaite: agent.py — the same while-loop lives in Agent.run(); tools.py ToolRegistry.call() is run_tool with an allow-list and max_steps is the budget.
05A tool schema is a menu of actions ch 1

Each tool is shown to the model as a name, a description of when to use it, and a JSON schema for its inputs. The model does not understand the API. It picks from a menu and fills in the blanks. Good descriptions decide how well it picks.

Picture it: A restaurant menu: the diner cannot enter the kitchen, but a clear dish name and description gets the right order placed.
tools = [{
    "type": "function",
    "function": {
        "name": "search_knowledge_base",
        "description": "Search the support knowledge base for recovery steps, "
                       "policy guidance, or troubleshooting instructions.",
        "parameters": {
            "type": "object",
            "properties": {"query": {"type": "string",
                                     "description": "The customer issue or search phrase."}},
            "required": ["query"],
            "additionalProperties": False}}}]
additionalProperties False means the model cannot invent extra arguments; the description says when, not just what.
The trap: Writing a description like Gets information, then blaming the model for choosing the wrong tool.
In Formulaite: tools.py — Tool builds this shape from a Python signature; drawer.py as_tool_schema() is the fill_drawer menu entry.
06Pick the simplest brain: reactive, deliberative, hybrid ch 1

A reactive agent maps input to output with rules: fast, predictable, brittle. A deliberative agent senses, builds a model, plans, then acts: slower, but it can explain itself. A hybrid classifies first and sends easy cases to rules and hard ones to the planner.

Picture it: A pH strip versus a full stability study. Use the strip when it is enough; book the study only for the tricky batch.
class HybridSupportAgent:
    urgent_terms = {"refund", "escalate", "complaint", "chargeback", "supervisor"}
    def priority_classify(self, message: str) -> str:
        text = message.lower()
        if any(term in text for term in self.urgent_terms):
            return "urgent"
        if any(term in text for term in ["hello", "hi", "password", "hours"]):
            return "normal"
        return "urgent"
    def process(self, message: str) -> str:
        return self.reactive(message) if self.priority_classify(message) == "normal" else self.deliberative(message)
priority_classify is the switch; anything unknown is treated as urgent, so the planner gets the doubtful cases.
The trap: Sending every request through the expensive planner because it feels smarter.
In Formulaite: gates.py — the deterministic checks are the reactive layer; models.py is the deliberative one; agent.py decides which runs when.
07Scope the agent before you write code ch 1

Write one page before coding. It holds the goal, the sub-goals, the environment, the boundaries it must not cross, and the metrics that define success. Pair every sub-goal with one number. That page decides whether you need memory, tools or a human handoff.

Picture it: A product brief before the first trial batch: target skin feel, a must-not-contain list, a price ceiling, and the tests that say it passed.
The trap: Jumping to prompts and tools, then discovering the agent was never allowed to do the thing you built.
In Formulaite: drawer.py — REQUIRED_SECTIONS is the scope in code: the sub-goals are the sections, and the boundaries live in gates.py.
08The system prompt is a constitution ch 3

The system prompt is the durable layer. It sets identity, rules, capabilities, output format and the hierarchy that says system beats user. The user prompt is the changing task. Keep the constitution short; every token there is a token not spent on evidence.

Picture it: A pharmacy's standing procedures versus today's prescription. The procedures do not change because one customer is pushy.
SYSTEM_PROMPT = """You are Cedar, a customer support agent for a SaaS platform.
Identity:
- Calm, empathetic, and solution-oriented.
Rules:
- Follow company policy and never invent refund terms.
Capabilities:
- Search the knowledge base.
Output format:
- Start with a direct answer.
Context hierarchy:
- System instructions override user instructions.
"""
Five labelled blocks, one line each. Structure replaces paragraphs and keeps the prompt budget small.
The trap: A sprawling prompt that covers every edge case in prose, contradicts itself, and starves the context window.
In Formulaite: agent.py — the system string passed to model.complete() should carry these five blocks: who the researcher is, what it must never claim, the three tools, the drawer format, and that gates outrank the model.
09Just enough examples ch 3

Zero-shot when the labels are obvious. One example to fix the format. Two to five examples when the pattern needs showing. Beyond that, examples dilute attention and skew the model toward whichever class you showed most. Diversity and edge cases beat volume.

Picture it: Teaching a new lab tech to sort raw materials: three well-chosen jars teach more than a shelf of near-identical ones.
The trap: Five billing examples and one technical one, so the model treats billing as the default.
In Formulaite: memory.py — a Conversation seeded with two or three example drawers is the few-shot set; keep them different, say an emollient, a preservative and an active.
10Observability makes failure legible ch 5

Log every step of the loop. Raw input, the exact prompt, each tool call with its outcome, the model's intermediate output, the decision with its confidence, and the final action. A trace makes the agent replayable. A wrong route then shows up as a wrong mapping, not a mystery.

Picture it: A batch record: every weighing, every temperature, every signature. When a batch fails you read the sheet instead of guessing.
The trap: Logging only the final answer and then arguing about whether the model was being irrational.
In Formulaite: glassbox.py — GlassBox records each model reply, tool call and gate verdict as an Event; replay() is the trace the book describes.

01Retrieve, augment, generate ch 6

Separate knowing from answering. First retrieve the passage that governs the question. Then put it into the prompt. Then generate an answer that stays inside that evidence. When the answer is wrong you can ask which of the three steps failed.

Picture it: Before answering a customer about a preservative, you pull the supplier's spec sheet, read the relevant line, and quote it, rather than answering from memory.
def build_vectorstore(docs):
    splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
    chunks = splitter.split_documents(docs)
    embeddings = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
    return FAISS.from_documents(chunks, embeddings)

def build_qa_chain(vectorstore):
    llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
    retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
    return RetrievalQA.from_chain_type(llm=llm, chain_type="stuff",
                                       retriever=retriever, return_source_documents=True)
k=4 is how many chunks reach the model; return_source_documents=True is the start of provenance.
The trap: Making the model smarter when the real fix is making the system better informed.
In Formulaite: formulaite_tools.py — read_supplier_page is the retrieve step; models.py generates the drawer from the returned text, not from memory.
02Provenance runs in parallel ch 6

Provenance is not a footnote added at the end. It is a second track that runs beside the pipeline, collecting source ids, timestamps and confidence as the work happens. Every claim must point back to the passage that produced it. If the evidence is partial, say so.

Picture it: Lot numbers on every raw material: you can trace any finished jar back to the drum it came from.
The trap: Adding citations afterwards from memory, which is how a wrong policy version gets cited.
In Formulaite: drawer.py — the sources field is the provenance track; gates.py check_has_sources fails a drawer whose sections cannot point back to a page.
03Entity linking: one ingredient, many names ch 6

The same thing is named differently across sources: a marketing name, an internal code, a SKU. Without a canonical entity, retrieval fragments and the agent misses half the record. Map every alias to one id before you search.

Picture it: Glycerin, glycerol, glycerine and the trade name on the drum are one substance. The catalogue needs one key for all of them.
The trap: Searching for the trade name only and concluding there is no safety data.
In Formulaite: formulaite_tools.py — catalogue_lookup(inci) should resolve trade names and CAS numbers to the INCI key before it looks anything up.
04Confidence is the gate between raw text and data ch 6

A document pipeline has five stages: triage, preprocessing with OCR, layout parsing, schema-driven extraction, validation. OCR must emit a confidence per token and that number must survive downstream. High-confidence text flows on. Low-confidence text goes to a fallback or a human.

Picture it: A faded label on a drum: you do not guess the percentage, you flag it and check the certificate.
CONFIDENCE_THRESHOLD = 60
@dataclass
class OcrToken:
    text: str
    confidence: float
def preprocess_and_ocr(pdf_path: str) -> List[OcrToken]:
    tokens = []
    for page in convert_from_path(pdf_path, dpi=300):
        data = pytesseract.image_to_data(page, output_type=pytesseract.Output.DICT)
        for text, conf_raw in zip(data["text"], data["conf"]):
            if text.strip() and float(conf_raw) >= CONFIDENCE_THRESHOLD:
                tokens.append(OcrToken(text=text.strip(), confidence=float(conf_raw)))
The threshold is the gate: a token below 60 never becomes a field value, but it is still visible for review.
The trap: Silently promoting a low-confidence number into the record because it looked plausible.
In Formulaite: formulaite_tools.py — a PDF path in read_supplier_page would use this stage; drawer.py fields should carry a confidence next to each value.
05Tool contracts with a safe wrapper ch 7

A registry entry is a contract: name, description, input schema, output schema and the function. A safe wrapper validates the input before the call, runs the function under a timeout, and validates the output before it returns. Malformed input fails fast; slow APIs time out; exceptions become structured errors.

Picture it: A locked cabinet with a checklist on each drawer: what you may put in, what comes out, and a timer on the door.
def safe_tool(input_model, output_model, timeout_seconds: int = 5):
    def decorator(fn):
        @wraps(fn)
        def wrapped(payload):
            validated = input_model.model_validate(payload)
            def run():
                return output_model.model_validate(fn(validated.model_dump())).model_dump()
            with ThreadPoolExecutor(max_workers=1) as executor:
                future = executor.submit(run)
                return future.result(timeout=timeout_seconds)
        return wrapped
    return decorator
Two model_validate calls bracket the real function; future.result(timeout=...) turns a hang into a TimeoutError.
The trap: Validating the tool name but not its arguments, so the model can pass a made-up field to a live system.
In Formulaite: tools.py — Tool.__call__ and _schema_from_signature are the contract; wrap read_supplier_page in this safe_tool pattern in formulaite_tools.py.
06Reasoning core and execution engine are different parts ch 7

Think, Plan, Act. The reasoning core turns a request into a plan of tool calls. The execution engine runs the plan: it tracks state, retries transient failures, and stops cleanly when a step keeps failing. The reasoning core never mutates anything itself.

Picture it: The formulator writes the batch instructions; the technician runs them and notes each step. Neither does the other's job.
def execute_plan(plan, registry):
    state = {"steps": []}
    for step in plan:
        spec = registry.get(step["tool"])   # unknown tool raises before anything runs
        for attempt in range(1, 4):
            try:
                result = spec.function_ref(step.get("args", {}))
                state["steps"].append({"tool": step["tool"], "result": result})
                break
            except Exception as exc:
                if attempt == 3:
                    raise RuntimeError(f"Execution failed for {step['tool']}") from exc
registry.get raises on an unknown tool before anything runs; three attempts, then a clean RuntimeError, and the caller gets state back.
The trap: Letting the planner call APIs directly, so a bad plan and a bad call are impossible to tell apart.
In Formulaite: agent.py — the Agent is the execution engine; models.py is the reasoning core that only proposes ToolUseBlocks.
07Name the failure ch 7

Tool failures come in four kinds. Input validation errors: the arguments do not fit the schema. Runtime failures: the call was valid but the service timed out. Semantic mismatches: the call worked but the answer does not fit the question. Unavailability: the dependency is down. Each kind needs a different fix.

Picture it: Wrong units on the order form, the supplier's phone line down, the right product but the wrong grade, the supplier closed for the holidays.
class ToolRuntimeError(Exception):
    """Raised when a tool starts correctly but fails while executing."""

class ToolUnavailableError(Exception):
    """Raised when an external dependency is offline or inaccessible."""

@dataclass
class TicketCreationTool(CustomerTool):
    allowed_categories: List[str]
    def validate_input(self, payload):
        if payload.get("category") not in self.allowed_categories:
            raise ValueError(f"Invalid category {payload.get('category')!r}")
Distinct exception classes let the caller branch on the kind of failure instead of parsing error text.
The trap: Catching Exception and retrying everything, including the validation errors that will never succeed.
In Formulaite: tools.py — ToolError is one class today; split it into input, runtime, mismatch and unavailable so gates.py and agent.py can respond differently.
08The recovery ladder ch 7

Recovery is layered. A safe wrapper retries transient errors with backoff. A fallback chain tries a second route to the same goal. Confidence-based switching discards a weak result and picks another tool. Failure memory blocks a sick tool for a while. Escalation hands the human the full context.

Picture it: Supplier A is out: try the approved alternate, reject the sample that looks off, note not to call A this week, and if nothing works ring the formulator with the whole story.
The trap: Retrying forever against a service that is down, and calling that resilience.
In Formulaite: formulaite_tools.py — read_supplier_page should fall back to the cached catalogue text; agent.py should mark the tool blocked after repeated ToolError.
09Three memories, three triggers ch 5

Working memory is the current conversation in the prompt: fast, but bounded by tokens. Episodic memory is what happened before, per user, with timestamps. Semantic memory is what is true: the fact base. Route by trigger: the current turn, a reference to the past, or a factual question.

Picture it: The notes on today's bench, last month's batch records, and the ingredient reference book. You reach for a different one depending on the question.
The trap: Letting the model answer a policy question from a remembered chat instead of the source of truth.

10Cost-aware routing with a budget ch 4

Not every request deserves the biggest model. Classify the query into simple, moderate or complex. Send simple ones to a cheap model, cache repeated answers with a time-to-live, and keep a per-session budget that can refuse the expensive model. Monitor tokens per session and cache hit rate.

Picture it: You do not send every sample to the external lab. Routine checks happen on the bench; only the odd ones go out.
@dataclass
class BudgetTracker:
    session_budget_usd: float
    spent_usd: float = 0.0

        return self.spent_usd + MODEL_COST.get(model_name, 0.0) <= self.session_budget_usd
    def charge(self, model_name: str) -> None:

11Generator plus validator loop ch 10

Generation and judgement are different jobs. One agent drafts. A validator checks the draft against hard constraints and returns not just pass or fail but instructions to fix it. The generator revises. Cap the retries; after that, a human reviews.

Picture it: The copywriter drafts the label; regulatory reads it against the claims list and sends back exactly which words to change.
def validate_against_brand(response: str, guidelines: dict) -> dict:
    forbidden_terms = guidelines["forbidden_terms"]
    required_tone = guidelines["required_tone"]
    lowered = response.lower()
    violations = [term for term in forbidden_terms if term.lower() in lowered]
    tone_ok = required_tone.lower() in lowered
    instructions = ""
    if violations:
        instructions += f"Remove forbidden terms: {violations}. "
    if not tone_ok:

    return {"passed": not violations and tone_ok, "instructions": instructions}
The return carries instructions, not just a verdict; that is what makes the loop actionable.
The trap: A validator that only says FAIL, so the generator guesses what to change.

02Tool gating inside defence in depth ch 4

Assume each control can fail and stack them. Validate input, enforce a schema on model output, govern memory, gate tools, harden interfaces, observe behaviour. Tool gating is the middle layer. It means an allow-list, per-tool parameter validation, and a logged rejection for anything outside it.

Picture it: Goggles, a fume hood and a locked acid cabinet. Any one can fail; together they make an accident expensive.
def whitelist_tools(allowed_tools):
    def decorator(func):
        @wraps(func)
        def wrapper(tool_name: str, *args, **kwargs):
            if tool_name not in allowed_tools:
                logger.warning("Blocked unauthorized tool call: %s", tool_name)
                raise PermissionError(f"Tool not allowed: {tool_name}")
            if tool_name == "search_kb" and not str(kwargs.get("query", "")).strip():
                raise ValueError("search_kb requires a non-empty query")
            return func(tool_name, *args, **kwargs)
        return wrapper
    return decorator
The decorator checks the name and the parameters before func ever runs; the warning line is the audit trail.
The trap: Hardening the prompt and leaving the tool layer open, which is the attacker's path of least resistance.
In Formulaite: tools.py — the @registry.tool decorator can carry this gate; glassbox.py should record every blocked call as an Event.
03Safety check before autonomous action ch 5

Before the agent acts on its own, run a plain function with three questions. Is the action within the limit for this tier? Does the agent hold the data permission it needs? Could the action harm the customer if wrong? Return ok plus a list of violations. Any violation means revise or escalate.

Picture it: Before releasing a batch: is it within the allowed use level, do we hold the certificate, and what happens if we are wrong?
def autonomous_safety_check(decision_context, planned_actions):
    violations = []

04Escalation is a feature, not a failure ch 5

Uncertainty is a first-class state. Perception must also ask: is this safe, in scope, and clear? If not, the loop must not proceed to action. The agent should be able to say: I can do this safely, I need clarification, a person can do this, or this is unsafe and blocked.

Picture it: A good technician stops and asks when the label is smudged. Guessing the concentration is the failure, not asking.

05Fact-checking is a control mechanism ch 8

Split a statement into atomic claims. Retrieve evidence for each from sources with known provenance. Let a natural language inference model label each pair as entailment, contradiction or neutral. Weight sources by credibility: a database row beats a blog post. Aggregate into one confidence and act on it.

Picture it: The drawer says up to 5 percent and skin-safe. Check the first against the supplier sheet and the second against the safety assessment, separately.
def fact_check(claim: str, evidence: str) -> Dict[str, object]:
    claim, evidence = (claim or "").strip(), (evidence or "").strip()
    if not claim or not evidence:
        return {"label": "NEUTRAL", "score": 0.0}
    tokenizer = AutoTokenizer.from_pretrained(MODEL_NAME)
    model = AutoModelForSequenceClassification.from_pretrained(MODEL_NAME)
    # Premise = evidence, hypothesis = claim.
    inputs = tokenizer(evidence, claim, return_tensors="pt", truncation=True, max_length=512)
    with torch.no_grad():

    raw_label, score = _select_best_nli_label(outputs.logits[0], _id_to_nli_label(model))

07Five metrics and the improvement loop ch 1

Measure task success rate, average response time, user satisfaction, tool invocation latency and fallback frequency. Define success strictly: closed, not reopened, within policy. Then run deploy, measure, analyse, modify, re-evaluate. Each metric points to a different layer to fix.

Picture it: Yield, batch time, complaints, supplier lead time and how often you had to rework. Different numbers, different fixes.
class EvaluationReport:
    def __init__(self, entries: list[TelemetryEntry]) -> None:
        if not entries:
            raise ValueError("EvaluationReport requires at least one telemetry entry.")
        self.entries = entries
    @property
    def task_success_rate(self) -> float:
        resolved = sum(1 for entry in self.entries if entry.resolved)
        return resolved / len(self.entries)
    @property
    def fallback_frequency(self) -> float:
        return sum(1 for entry in self.entries if entry.fell_back) / len(self.entries)
Each metric is a @property computed from the same telemetry list; JSON lines in, numbers out.
The trap: Counting a ticket as resolved the moment it closes, so a flattering number hides reopened cases.
In Formulaite: glassbox.py — GlassBox.of_kind('gate') and of_kind('tool_call') give resolved, fell_back and latency per run; a scripts/ checker can build this report.
08Closed-loop control with a human where risk changes ch 9

A planner turns patterns into one testable hypothesis. Changes to prompts or thresholds pause for human approval. Validate on held-out cases before deploying, and keep rollback.

Picture it: Adjusting a recipe: measure the complaints, propose one change, test it on a small batch, and keep the old recipe on file.
The trap: Changing the prompt on intuition after every bad ticket and calling it learning.

09Fault-tolerant scanning: ingestion separable from synthesis ch 13

A research agent scans many sources, clusters what it finds, then synthesises. Treat each source as its own dependency with its own rate limit, budget, cache and circuit breaker, and deduplicate before interpreting. If one source fails, the clustering state stays untouched and the report never learns the noise as fact.

Picture it: Three suppliers, three phone lines. If one is down you do not rewrite the formula; you note the gap and carry on.
class CircuitBreaker:
    def __init__(self, failure_threshold=3, recovery_timeout_seconds=60):
        self.failure_threshold, self.recovery_timeout_seconds = failure_threshold, recovery_timeout_seconds
        self.failures, self.opened_at = 0, None
    def allow_request(self) -> bool:
        if self.opened_at is None:
            return True
        return (time.time() - self.opened_at) >= self.recovery_timeout_seconds  # half-open probe
    def record_failure(self) -> None:
        self.failures += 1
        if self.failures >= self.failure_threshold:
            self.opened_at = time.time()
Three failures open the breaker; after the cooldown one probe request is allowed through.
The trap: Letting one noisy source dominate the synthesis because it returned the most results.
In Formulaite: formulaite_tools.py — give read_supplier_page a per-domain CircuitBreaker and dedup by URL plus title; the drawer never learns a 503 as a fact.

11Calibrate before you narrate ch 12

A confidence score only means something if 80 percent confident is right about 80 percent of the time. Raw model certainty is not that. Score first, calibrate, then write the explanation, so the polished story does not inflate the number. Below a threshold, escalate rather than bluff. Show users a word, staff a number.

Picture it: A pH meter is calibrated before you read the sample, not adjusted afterwards to match what you expected.
class TemperatureScaler:
    """Calibrate a raw logit into a probability using temperature scaling."""
    def __init__(self, temperature: float = 1.0) -> None:
        if temperature <= 0:
            raise ValueError("temperature must be greater than 0")
        self.temperature = temperature
    def calibrate(self, logit: float) -> float:
        scaled = logit / self.temperature
        if scaled >= 0:
            return 1.0 / (1.0 + math.exp(-scaled))
        z = math.exp(scaled)
        return z / (1.0 + z)
A larger temperature softens overconfident scores; the output is the number you are willing to say out loud.
The trap: Generating a confident explanation first, then attaching a score that drifts up to match it.
In Formulaite: drawer.py — a confidence field per section, set from evidence scores before the model writes prose; gates.py escalates below the threshold.
12Priorities before preferences ch 17

When values compete, order them. Satisfy the highest-priority constraint first, then optimise the next only inside what is already safe. A strict order beats a weighted average because a low-priority gain can never erode a high-priority guarantee. Watch a metric's distribution over time; drift gets a staged response: log, increase oversight, restrict, halt.

Picture it: Safety limit first, then regulatory claims, then skin feel. A nicer texture never buys you an over-limit preservative.
@dataclass
class BehavioralDriftDetector:
    baseline_window: int = 1000
    alpha: float = 0.05
    def record_action(self, metric_value: float) -> bool:
        if not self._baseline_ready:
            self._baseline.append(float(metric_value))
            self._baseline_ready = len(self._baseline) >= self.baseline_window
            return False
        self._current.append(float(metric_value))
        result = ks_2samp(self._baseline, list(self._current), alternative="two-sided")
        return result.pvalue < self.alpha
A two-sample KS test compares the recent window with the baseline; p below alpha means the behaviour moved.
The trap: Averaging safety against satisfaction, so a happy-customer score can outvote a rule.
In Formulaite: gates.py — order the checks: check_not_banned, then check_use_level_in_range, then softer checks; a drift detector on the gate-fail rate belongs beside glassbox.py.

The pattern

  1. Scope: goal, sub-goals, environment, boundaries, metrics, on one page.
  2. Constitution: identity, rules, capabilities, output format, hierarchy in the system prompt.
  3. Loop: model proposes a tool call; registry validates; safe tool runs; result returns with a source label.
  4. Ground: retrieve, augment, generate; provenance runs in parallel.
  5. Validate: a deterministic gate checks the draft and returns fix instructions; cap the retries.
  6. Escalate: low confidence, out of scope, or conflicting evidence goes to a human with the dossier.
  7. Measure: five metrics from the trace; deploy, measure, analyse, modify, re-evaluate.

Safe tool with a typed contract and a timeout

def safe_tool(input_model, output_model, timeout_seconds=5):
    def decorator(fn):
        @wraps(fn)
        def wrapped(payload):
            validated = input_model.model_validate(payload)
            def run():
                return output_model.model_validate(fn(validated.model_dump())).model_dump()
            with ThreadPoolExecutor(max_workers=1) as executor:
                return executor.submit(run).result(timeout=timeout_seconds)
        return wrapped
    return decorator

    result = tool.run(payload)

Before you ship

  • The system prompt has identity, rules, capabilities, output format and hierarchy, and it is short.
  • Every tool has an input schema, an output schema, a timeout and a logged rejection path.
  • Every drawer field carries a source label and a confidence.
  • Each drawer claim was checked against its cited passage as entailment, not just similarity.
  • The gate returns reasons the model can act on, and retries are capped.
  • Low confidence, out of scope and conflicting evidence each have a named escalation status.
  • Task success, response time, tool latency and fallback frequency are computed from the trace.
  • Gate order puts banned ingredients and use limits before softer quality checks.
