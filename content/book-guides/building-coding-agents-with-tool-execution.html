Building Coding Agents with Tool Execution

DeepLearning.AI × E2B · 10 lessons · ~67 min · six-step Python exercise, no API key

An ordinary agent can only do what somebody wrote a function for. This course gives the model one tool — run this code — which removes the list entirely, and then spends half its length on the consequence: code you did not write, running somewhere. Start on the Walkthrough for the idea in plain English, then go to Build it yourself and run the forty lines on your own machine.

A question nobody wrote a function for

Every agent you have read about so far has a fixed list of things it can do. Someone decided in advance: it can search, it can send an email, it can look up an order. Ask it something outside the list and it is stuck.

This course's whole idea is one tool that removes the list. The model is allowed to write a small program, hand it to your code, and read back what it printed. Nobody has to anticipate the question.

Step through it below. It runs in plain English by default and there is a toggle in the corner for the technical names. Eight frames, then the whole loop at once.

The definition, and why it is worth memorising

The course gives one sentence: an agent is an LLM calling tools in a loop with context. Four nouns, and each one is a place where things go wrong.

The nounWhat it is in codeWhere it goes wrong
LLMOne function that takes messages and returns a replyPicked for the wrong reason — cost, speed and tool-calling reliability are three different axes
ToolsA dict of name → function, plus a JSON schema per tool that the model is shownA tool per question, instead of one that can be composed
LoopA while with a hard max_stepsNo maximum. The course sets 5; any number beats none
ContextA list of messages that only ever growsFat tool results and full stack traces — see the Context tab

What is new here versus every other guide on this shelf. Guides 1–14 build agents from fixed tools. This one gives the model a code interpreter as its tool, which is a different bargain: far more capable, and far less containable. That is why half the course is about where the code runs, and why this guide has an isolation tab at all.

The course's own notebooks need an API key, an E2B account and a paid model. This is the same mechanism stripped to plain Python 3, so you can run it on your laptop tonight and read every line. Step 1

A tool is a function plus a description of itself

You write an ordinary Python function. Then you write a second thing — a JSON object describing that function in English — because the model never sees your code, only the description. The two are joined by a dictionary.

def mean_salary(grade):
    rows = [r for r in ROWS if r["grade"] == grade]
    return sum(r["salary"] for r in rows) / len(rows)

SCHEMA = {"name": "mean_salary",
          "description": "Mean salary for one grade, e.g. 'G5'.",
          "parameters": {"grade": "string"}}

TOOLS = {"mean_salary": mean_salary}      # name → the actual function
The registry and the schema are two separate objects. Change the description and the model behaves differently without a line of logic changing.
Step 2

The loop, with a model you can read

The model here is a hard-coded list of replies, so the loop is completely deterministic. You see the messages list grow, the tool get called, the result get appended, and the loop exit — with no network and nothing hidden.

while step < MAX_STEPS:
    reply = fake_model(messages)
    if reply["type"] == "text":          # the exit condition
        break
    result = TOOLS[reply["name"]](**reply["args"])
    messages.append({"role": "tool", "content": str(result)})
The exit condition is “the model stopped asking for tools”, not “the task is done”. Those are different, and confusing them is how agents loop forever.
Step 3

One tool to replace all the others

Now delete mean_salary and give the model execute_code(code) instead — exec() with stdout captured. The same question is answered by code the model wrote on the spot, and so are questions you never anticipated.

def execute_code(code):
    buf = io.StringIO()
    try:
        with contextlib.redirect_stdout(buf):
            exec(code, {"ROWS": ROWS})
    except Exception as e:
        return f"{type(e).__name__}: {e}"      # short. structured. not a traceback
    return buf.getvalue().strip()
Capturing stdout is what turns “run some code” into “a tool that returns a value”. And the except line is the whole error philosophy in one place — the model reads this string, so it must be short enough to act on.
Step 4

Why this is dangerous — demonstrated, not asserted

The registry contains exactly one tool. No file tool. No shell tool. Then the step asks the model for something innocuous, and the code it writes imports os and prints your username and operating system.

TOOLS = {"execute_code": execute_code}    # one tool. no file access. supposedly.

{'result': "['agent_lab.py', 'people.csv']", 'error': None}
{'result': 'somapym Darwin', 'error': None}

It listed the folder and named you. It could as easily have written, moved or deleted. Nothing here was malicious — the point is that nothing stopped it.

Not registering a file tool does not mean the agent cannot touch files — open is reachable through execute_code. This is the entire security argument of lesson 4, and you produce the evidence yourself instead of believing a slide. The Isolation tab is what to do about it.
Step 5

Watch the context grow

The step prints, per turn, how much the messages list is carrying and how much that turn added. Turns 0 and 1 each dumped the whole table into the context — about 550 characters apiece. Turn 2 returned the answer only: fourteen characters. Same question, roughly forty times less context.

turn     added   total   ~tok   this turn added
0          551     576    144   ██████████████████████
1          551    1127    281   ██████████████████████

Nothing is ever removed from a messages list, so growth is the default state and tool results are the cause. The fix, in order of what it buys you: return the answer rather than the data it came from; clip logs and repeated errors; paginate anything that lists files or rows. Compression, on the Context tab, is what you do when all three are already true.
Step 6

The whole agent, in about forty lines

Everything above assembled into one function, printed to the screen so you can read it in one sitting. This is the same shape as the course's lesson-3 agent and the same shape as the lesson-7 one; the difference between them is which environment the code runs in and what the system prompt says.

There is no framework in here. Once you have seen the forty lines, every agent framework becomes a question of what it adds on top — which is the right way to evaluate one.

The two changes to make afterwards. Swap fake_model for a real API call and the file becomes a working agent. Swap exec for a sandbox's run_code and it becomes the course's lesson-5 agent. Those are one line each, which is the strongest argument the course makes: the shape does not change.

The flow, end to end

your question │ ▼ messages[] ──────────────► the model ──── "call execute_code(code=…)" ▲ │ │ ▼ │ look the name up in TOOLS │ │ │ ▼ └──── append the result ◄────────── run it (locally, or in the sandbox) │ stop when: the model stops asking ◄────┘ or max_steps is hit

Everything else in the course is a variation on that diagram, and the variations are smaller than they look:

  • Lesson 3 builds it with exec() running on your own machine.
  • Lesson 5 changes exactly one line — execute_code passes the code to the sandbox's run_code instead of to exec. Nothing else about the shape changes.
  • Lesson 6 changes only the system prompt to make a data analyst. No new tools; pandas arrives through execute_code like everything else.
  • Lesson 7 adds the file tools and copies them into the sandbox, so they run there rather than on your machine.

The three ideas actually worth taking

The registry and the schema are separate thingsdesign

The function does the work; the JSON schema is what the model is shown. A tool is those two things plus a line in a dict. Keeping them separate is what lets you change how the model understands a tool without touching what it does.

Errors are structured and shortcontext

Their ToolError exists so a missing file produces "file does not exist" rather than forty lines of traceback. The error goes into the context, and context is the scarce resource. A model can act on one line; it cannot act on a stack trace, and the stack trace costs you room you will want later.

Runtime summarisationthe portable one

The one algorithm here worth lifting whole into your own code: pick a ceiling, compress the oldest turns when you hit it, re-inject the summary as a normal-looking pair of messages. About thirty lines. The Context tab walks through it frame by frame.

Four answers, and the arrow that tells the truth

Step 4 of the exercise proves that an agent with no file tools can still read your files. So the question stops being “what tools did I register” and becomes “where does the generated code actually run”. The course gives four answers, each better and more expensive than the last.

Reading this honestly

Two things are true at once, and it is worth holding both.

The technical steps are sound. Containers really do share the host kernel. gVisor really does intercept syscalls in user space, at a real performance cost, with real compatibility gaps. Firecracker really does give each microVM its own guest kernel, and really does run AWS Lambda and Fargate. None of that is marketing; it is the mainstream position, and I checked it independently — see the Verified tab.

The last step is commercial. The chain ends “…self-hosting microVMs is operationally heavy, therefore use a managed sandbox provider”, and the course is taught by E2B, who sell one. The operational burden is genuine and widely reported. Whether it justifies buying rather than building is a decision about your team, not a fact about kernels — and it is the one step in the argument where the teacher has an interest.

What to actually do, for the size of thing you are building. For an agent operating on files you already have and code you would have written anyway, running locally is a considered choice, not negligence — that is what Claude Code and Cursor do. The moment the agent runs code from somewhere you did not read, or acts on data you did not write, you need a boundary, and a container is not one.

Context rot, and the thirty lines that fix it

The messages list only ever grows. Every tool result is appended and nothing is removed, and tool results are the fat ones — file listings, compiler output, error stacks. Past some point the model gets measurably worse at using what it has: the course calls this context rot, and names three mitigations — keep tool results small, keep errors short and structured, and compress at runtime.

The first two are discipline. The third is an algorithm, and it is the single most portable thing in the course.

The detail that makes it work. The summary is re-injected as a synthetic user message plus an assistant acknowledgement, not as a system note. The conversation therefore still has the alternating shape the model expects, so nothing above the compression layer has to know it happened. That is the bit people get wrong when they reimplement it.

Ten ways to get this wrong

Most of these are things the course demonstrates and then does not name. They are ordered roughly by how quickly they will bite you.

  1. Assuming that not registering a file tool means the agent cannot touch files. It reaches open through execute_code. Lesson 5 demonstrates this without quite saying it.
  2. Returning raw tool output into the context. A full table where a single number would do is the fastest way to context rot.
  3. Returning stack traces to the model. Short structured errors are what let it recover; forty lines of traceback just spend context.
  4. Writing a loop with no maximum step count. The course sets 5. Any number is better than none.
  5. Treating a container as a security boundary. It shares the host kernel.
  6. Reading the SWE-bench standings off a leaderboard screenshot dated October 2025.
  7. Taking “~30k tokens” as a measured threshold. It is uncited in the course.
  8. Building a tool for every question. One execute_code answers the questions you did not anticipate — which is the entire premise.
  9. Skipping the system prompt. Lesson 6 changes only the prompt to turn a generic agent into a data analyst.
  10. Letting a build-vs-buy decision be made for you by the people selling one side of it.

The one to tattoo somewhere. Number 1. An agent with a code interpreter has every capability the interpreter has, regardless of what else you did or did not register. Your tool list is a description of what you expect it to do, not a boundary on what it can do. The boundary is the environment, and only the environment.
